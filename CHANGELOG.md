### Added
- feat(configure,plan,breakdown,verify,agents): an end-to-end test lane — a user flow DECLARED at `/devforge:plan`, OWNED by a `qa-engineer` task at `/devforge:breakdown`, and RUN once per feature at `/devforge:verify` when an e2e command is configured (`90-E2E-TEST-LANE-PLAN.md`, Phase 0 ratified + Phases 1–5 built, 2026-08-27). **The origin is a question and a sweep, not an incident.** One maintainer question — are end-to-end tests needed in the emitted pipeline, and what would adding them take — triggered an `src/` sweep that found three things. The emitted instruction set contained **no web-e2e concept at all**: the only end-to-end vocabulary anywhere was mobile-only and advisory, in `qa-engineer` and its `qa-reviewer` mirror, so a web project installing this framework got an acceptance-criteria verifier, a four-reviewer panel, a full-suite regression gate and six decomposition gates — and no notion that a user flow can be exercised end to end. **There was no test-tier taxonomy to hang one on** — one `test_command` per package plus a flat command array, with nothing distinguishing unit from integration from e2e. And e2e detection already existed in the setup helper, **was never invoked by any command, and could not have been used if it were**, its only reader filtering the value out; that detector is left exactly as unused as it was, which is honest rather than tidy. **There was no consumer incident behind this, no failing run, and no measurement** — a predicted-gap change in the artifact-language-guard's class, and it must be described that way wherever it is summarized. **The obvious cheap move was rejected on correctness, not cost.** Putting the e2e suite in the ordinary test command would run it **per task**, re-paying it up to three more times per failing task through the self-repair cap, for a signal that is feature-level by nature; and it is broken by construction inside the regression gate, whose baseline half runs in a detached worktree with nothing built and nothing served, where an app-dependent suite fails for reasons unrelated to the feature and **the gate then reads its own failure as a failing baseline and stops gating. A gate that silently disarms itself is worse than no gate.** **Four pieces.** (1) **One top-level `E2E_COMMAND` config key**, seeded by `/devforge:configure` from the package manifests it already parses — a `@playwright/test`, `playwright` or `cypress` dependency identifies the runner and that package's own script is the value, **with the existing don't-guess rule inherited verbatim**: a runner with no script that runs it yields an empty field, and no ecosystem default is ever invented. Its load-bearing property is that it is **invisible to the per-task check and to the regression gate**, which read only the per-package test command and the primary test command — a mechanical consequence, not a promise. (2) **A declaration point**: a new architect sub-question at `/devforge:plan` asks which acceptance criteria describe a user-visible flow only a full-stack run can verify and what the minimal scenario is for each, feeding a conditional `### E2E Scenarios` table in `plan.md`. Empty answers are explicit, and a feature with no such criterion gets no subsection at all. (3) **An owner**: `/devforge:breakdown` reads that table straight from `plan.md` — no schema change, no new task header field, no new agent-assignment row — and renders a dedicated `qa-engineer` task under the test-authoring row that already exists. The task carries two escape-hatch-free rules: write the tests in the framework the project's configuration names, and when that configuration is empty the task is BLOCKED and says so rather than choosing a framework the project has not adopted; and put the e2e spec files in a dedicated e2e directory the package's ordinary test command does not match, because Playwright and Vitest/Jest share the `*.spec.ts` convention and an e2e spec the unit glob can reach gets run by the wrong runner at the next task, burning self-repair rounds on a failure that is not a defect. `qa-engineer`'s `## Mobile Testing` section is renamed `## End-to-End Testing` and carries a web block beside the mobile one, **with every mobile bullet byte-identical**. (4) **An execution seat**: a new fail-soft `/devforge:verify` PHASE 4.5 runs the configured command **once, at HEAD, in the real working tree** — never a worktree, never the merge-base, never twice — and always exits 0, reporting `off`, `inconclusive`, `e2e-clean` or `e2e-failing`. The framework starts no application: the suite owns its own lifecycle, and the runtime-assisted AC channel stays a separate, uncoupled channel this run neither reads nor writes. A timeout is `inconclusive`, never `e2e-failing` — a suite that ran out of clock has not reported a defect. **Honest bounds, stated rather than argued away.** **The run is ADVISORY and gates nothing**: no status changes the verdict, the result reaches `verification.md` only as one line in the verdict's reasons, and there is no new blocker — so a ratifier will see APPROVED printed beside a red suite, which is the accepted cost of shipping the lane before there is any flake policy, and the strengthening trigger is an OBSERVED defect that reached a consumer despite a failing status having been surfaced. **The declaration is checked by nothing**: no seventh decomposition gate was added, no validator, no header field — a plan that declares three scenarios and a task set that covers none produces no error. **The claim is visibility, not enforcement**, exactly as the regression-net declaration already claims. The placement rule is likewise authoring guidance that nothing verifies. **This is a local pipeline and makes no CI claim** — the framework writes no CI files and reads none, so a suite that runs at `/devforge:verify` and never in CI is a real bound, and it is the same bound every other check here already has. **When no e2e command is configured the entire lane is a clean, silent no-op** at every seat: no question at setup, no plan subsection, no task, no line in the report, and no nagging anywhere — a framework that tells a Python CLI project it has no browser tests has made itself worse. **Flake handling is explicitly out of scope**: no retries, no quarantine, no accounting — the lane runs the command once and reports what it returned. **The cost is one full suite run per `/devforge:verify` run** — not per task, not doubled — and **no number exists for it yet**; the consumer run is obligated to record the wall-clock delta as a number. **Build-verified, NOT consumer-validated** — the consumer e2e is a user-driven HARD GATE that has NOT run. Its three known-answer anchors are the declared happy path (`e2e-clean`, plus where the spec files landed and the wall-clock delta), the silent install (`off`, with the whole transcript diffed for the string `e2e`), and the broken flow (`e2e-failing`, with the verdict recorded as a string) — **the first two scored as a PAIR**, since a lane that fires on everything passes one and fails the other. **A clean run would be evidence that the lane works, never evidence that the missing e2e tests had cost anything.**
- feat(constitution,breakdown,implement,agents): the test OBLIGATION made as standing as the test RUN (`89-TEST-FOUNDATION-HARDENING-PLAN.md`, Phase 0 ratified + Phases 1–5 built, 2026-08-27). **The origin is a review question, not an incident.** One maintainer question — does the framework cover the code it generates with tests — triggered an `src/` sweep, and the sweep's split IS the change: **test RUNNING was already solid at three independent layers** (`/devforge:implement` PHASE 5's scope-aware `verify-touched`, `/devforge:verify` PHASE 4's assembled suite plus its baseline-diff regression gate, and `qa-reviewer`'s AC→test mapping) and **none of it is touched here**; **test OBLIGATION was soft everywhere it could have stood.** Constitution §3.4 was a bare `{{TESTING}}` placeholder, the task-file skeleton's four standing Done-When lines had no test analog, `### Always` item 8 was *"Lint everything"* with no counterpart, and a package whose `test_command` is `null` ran no tests SILENTLY while every Done-When box still ticked green. **Linting was obligated in three places and testing in one — that asymmetry was the finding.** **There was no consumer incident behind this, no failing run, and no measurement** — a predicted-gap change in the artifact-language-guard's class, and it must be described that way wherever it is summarized. **Four closures.** (1) A universal `**Tests are part of the change.**` block appended to `src/constitution.md` **§3.5, not §3.4** — the choice is mechanical, not editorial: `_UNIVERSAL_SECTIONS` is a closed eleven-entry tuple that omits `§3.4`, so `verify-universal-defaults` never looks there, while §3.5 parses as one whole-body rule and needed no parser change. ⚠ The consequence is accepted rather than hidden: a reader hunting testing rules still meets §3.4's placeholder, and nothing was added there. (2) A fifth standing Done-When line, `Tests pass on changed files (see Development Commands section)`, appended to the helper-owned fixed set — **the only Python in the change**, one list literal plus its tests, appended last rather than grouped beside the type-check and lint lines so no existing skeleton line moves and no new convention is smuggled in as formatting. It is deliberately UNCONDITIONAL, because a *"skip when the package has no test command"* clause is the escape hatch this repo's meta-rule forbids by name. (3) That unconditional line is kept honest INSTRUCTION-ONLY: when `verify-touched` returns a clean `pass` whose `test_commands_run` array is EMPTY — a field already on the wire that no spec had ever named — `/devforge:implement`'s approve path now passes the Tests condition as `--unverified-box`, so the task file keeps a durable `_(unverified — see Completion Notes)_` annotation instead of a falsely green tick. **A stderr warning from the helper was considered and NOT built**; it is recorded as the named strengthening arm with an observable trigger, and `verify-touched`'s own behavior is unchanged. (4) The obligated tests must be able to fail: three FALSIFIABLE clauses, each naming an observable SHAPE and never a quality — the words *meaningful*, *reasonable* and *adequate* appear nowhere in the emitted text — added to the same constitution block and mirrored in `qa-reviewer`'s existing Approach step 4 and Rule 3. They are expected-value provenance **scoped to the changed behavior** (running the implementation and recording its output is not a derivation; **a test pinning existing behavior the change does not alter is explicitly outside the clause**, so characterization tests written before a restructuring stay legitimate), *"for every test there is a change to the code under test that makes it fail"* with **three named vacuous shapes** (a mock's own configured return asserted back at it; a literal or just-assigned value asserted against itself; a call that asserts nothing about the result, the raised error, or the observable effect), and no restating what the type checker already proves. **This is defence in depth for the new checkbox, not an independent idea** — a checkbox is a target, and a vacuous test ticks it. The reviewer edit EXTENDS a sentence that already said *"Flag weak, vacuous, or implementation-coupled assertions"*, so what is new is **falsifiability, not the concept**: a bare adjective became three shapes a reviewer can point at. Emitted alongside: a sixteenth `### Always` Key Rule, **Test behavior changes**, a pure append leaving items 1–15 byte-identical. **Honest bounds, stated rather than argued away.** **Nothing here is a gate** — zero new PHASE-3.5 `verify-*` numbers, zero validators, zero new agents, zero new verdict values; the reviewer vocabulary is still exactly `ADEQUATE / GAPS FOUND`, with the three vacuous shapes floored at High so they force `GAPS FOUND` while the provenance and type-restating clauses take no floor. **Nothing MECHANICAL checks that a test is non-vacuous** — the check is an LLM reviewer judging LLM-written tests, weaker in one way than the regression-net declaration it sits beside, whose reader is a human opening a task file rather than a model in an autonomous loop. The claim is that the requirement is now WRITTEN and the reviewer is now INSTRUCTED with named shapes, **never that vacuous tests became impossible**, and no phase measured how many get through; mutation testing is the mechanical answer and is recorded as the named strengthening path with a trigger, deliberately not built. **NO coverage threshold was added at any layer** — the counter-argument that "coverage" is therefore unfalsifiable is accepted as a standing bound, not answered — so **none of this may be cited as evidence that generated code is covered.** ⚠ **Consumer-install drift is expected, by design and not a regression**: canonical §3.5 gained a rule, so `constitute_helper verify-universal-defaults` reports a §3.5 mismatch against any install whose `.devforge/constitute.json` predates this build and the WARN-only update-time drift check fires — **and shipping in the same release as the Fowler-gaps change shows consumers TWO drift findings, §3.5 and §3.6, not one.** Back-porting into shipped installs is an explicit NON-GOAL; they arrive via `install.sh` / `update.sh`. **One documentation repair rode along**, closing a gap the same sweep found: `/devforge:configure`'s spec never named `REGRESSION_GATE`, a live config key with an enum, a built-in `"full"` default, a `configure_helper set-regression-gate` setter and a documented `/devforge:verify` PHASE-4.3 consumer — **so the model running setup never surfaced it and the user never learned it existed.** It is now documented where `render-config` writes `project-config.json`, with **no new setup prompt and no count changes**: the schema carries 30 fields, the 29 that command sets are the 23 detected plus the 6 prompted, and the 30th is this key, which no phase sets. **Build-verified, NOT consumer-validated** — the consumer e2e is a user-driven HARD GATE that has NOT run. Its five known-answer anchors are a configured-test-command task (box ticked clean), a `null`-test-command task (box UNTICKED and annotated), the §3.5 drift finding, the Key Rule shipped and loaded, and **a planted vacuous test beside a genuine one in the same task** — **anchors 1 and 2 are scored as a PAIR, and so are the last anchor's two plants**, because a reviewer that catches the plant by flagging everything fails the other half. **That anchor is the only place the false-positive rate will ever be observed; nothing shipped here has measured it.**
- feat(fix): a cold lane inside `/devforge:fix` — an already-filed `bugs/NNN-*.md` becomes a third findings source, so a small bug noticed outside any feature has a proportional route that keeps every code gate (`88-COLD-FIX-BUGS-LANE-PLAN.md`, Phases 0–4, 2026-08-26). **The gap, in two halves.** v1 shipped a lightweight `/fix` for small localized bugs; plan 21 dropped it and plan 26 reintroduced `/devforge:fix` as something else — a gated remediation of pipeline findings, hard-locked to the post-`/devforge:implement`/pre-`/devforge:summarize` window. Both moves were right on their own terms, and their combined consequence was that a **cold** bug had exactly two routes: hand-fix it, bypassing every gate the framework exists to impose, or take it through the full ~10-command chain, which is disproportionate for a one-file defect. `/devforge:fix`'s own empty-list message said so out loud. Separately and independently: `bugs/` files had **no consumer at all** — two producers (`/devforge:report-bug`, `/devforge:verify` PHASE 9), a three-state status field, and nothing that ever read or advanced one; `/devforge:report-bug`'s forward pointer named `/devforge:research`, which contained zero `bugs/` references. **The lane is contained in ONE command; the main pipeline is byte-unchanged.** The rejected alternative was a "light lane" threading a `minor` classification through research/specify/plan/breakdown, declined on two independent grounds: ceremony cost lives in GATE COUNT rather than artifact size, so thinner artifacts would leave all ten gates standing; and an "if minor" branch inside the main chain is precisely the escape-hatch shape this repo's zero-escape-hatch policy forbids. **The trigger is mechanical, never a judgment.** The lane is entered when `$ARGUMENTS` names a path under `bugs/`, and the feature lane is the explicit complement — empty, a feature path, or anything else — so the two are a true partition with no third state to adjudicate. There is no flag, no severity threshold, and **no numeric scope cap**: v1's "escalates if the bug affects more than 5 files" guard is deliberately not reproduced, because file count is a proxy for the wrong quantity (a one-file change to a public contract is a scope change; a mechanical null-check repair across eight call sites is not). **Plan 26's ban on free-text intake is EXTENDED, not reversed** — a bug FILE is a written finding with a title, severity, evidence and a file table, so *"consumes findings, never invents them"* stays literally true, and there is still no argument form that turns typed prose into a working-list item. **A captured bug is NOT a confirmed bug**, and this is the lane's load-bearing step: `/devforge:report-bug` reads no source, so the cold lane reads the cited files, quotes the offending code, and **STOPS without remediating** when it cannot locate the defect — an unconfirmed bug routes to `/devforge:research`, and there is no degraded best-effort arm. Confirmation also SUPPLIES the touched-file set, so a bug filed with no `--file` still scopes correctly. **The back half is unchanged and is CALLED, not copied** — scope-aware verify with self-repair, the four-reviewer panel, the forcing-functions gate and the two-stage human hard gate all run exactly as they do for a feature. What the cold lane drops is only the three sub-phases that need a feature directory that does not exist (feature resolution, the `in-fix-window` gate, the `read-findings` call); **it drops no gate that is about the CODE.** ⚠ One protection IS genuinely lost and is recorded rather than argued away: the window gate also refused to run mid-`/devforge:implement`, and the cold lane has no such interlock. **The commit is final, not `[WIP]`.** `implement_helper wip-commit` gained an additive `--final` mode (`--scope` required with it, rejected without it, and rejected alongside the task triple) emitting `fix(<scope>): <title>` in standalone and keeping `[TICKET-ID] - <title>` in wrapper mode, because a wrapper's product repo has a commit convention this framework does not own — including its existing full-branch-name fallback, so a cold fix on `develop` reads `[develop] - <title>`, which is the ratified design and not a defect. **`--final` deliberately does NOT clear `.devforge/wip.md`**: a cold run wrote no marker, and clearing one it did not write would destroy another command's crash-recovery state. `/devforge:implement` passes neither new flag and is byte-unchanged. **One `bugs/` write, and its narrowness is the whole point.** `/devforge:fix` **CREATES no `bugs/` file, ever, in either lane** — `/devforge:report-bug` remains the sole creator. Its single write is a new `fix_helper close-bug` verb flipping **the one file it was handed by path** to `Fixed` with the `**Fixed**:` date and `## Fix Notes` filled, and only after the human hard gate approves. The verb refuses the close — writing nothing — when the file is missing, when its status is not `Open`/`In Progress`, or when its `## Fix Notes` body is no longer the placeholder, so **hand-written notes are never overwritten**. This is **not automatic bug closing**: nothing scans `bugs/`, nothing closes a bug the user did not name, and the manual flip remains the ordinary path. It collects a `close-bug` consumer that plan 26 chartered as a deferral and amends that plan's D4 in place, narrowly. **The bounce differs by lane, mechanically.** A cold bug that triages as a behavior or architecture change bounces to **`/devforge:research`** rather than `/devforge:specify`, because `/devforge:specify` blocks until a research or discover handoff exists in a feature directory and a cold bug has neither — naming it would name a command that refuses to run. That bounce writes **no re-entry seed** (the seed model is feature-scoped by construction, so there is nowhere to put one and no consumer that would find it) and leaves the bug `Open`; ⚠ the diagnosis is therefore spoken to the user and then lost, the same loss that was fixed for the in-window bounce, recorded as an accepted bound. **The conversational routing rubric is ADVISORY.** The emitted `CLAUDE.md`'s fix-or-file offer went from two arms to three — in-window repair, cold repair, and "this is a change, not a repair" → the full chain — with the discriminator stated as defect-repair-vs-change and **explicitly never file count**. ⚠ **It is model judgment with nothing checking it**; the only mechanical net in this change is the in-command bounce, which fires after the user has already typed the command. **Not covered, stated so it is not assumed:** the artifact language guard shipped separately rides `artifact_helper commit-artifacts` only, and the cold lane's code commit rides `implement_helper wip-commit --final`, so **that commit path is outside the language guard** exactly as per-task commits already are. **Build-verified, NOT consumer-validated** — the consumer e2e is a user-driven HARD GATE and has NOT run; its three known-answer anchors are a happy-path run (one clean `fix(scope):` commit plus exactly three changed bug-file fields), a scope-change bounce (names `/devforge:research`, writes no seed, leaves the bug `Open`), and the three-arm offer observed in conversation — with the first two scored as a PAIR, since a triage that bounces everything passes one and fails the other.
- feat(artifact,docs): an artifact language guard — file content and commit messages stay English regardless of the operator's Claude Code response-language setting (`87-ARTIFACT-LANGUAGE-GUARD-PLAN.md`, Phases 0–3, 2026-08-23). **The exposure.** Claude Code's `language` settings key — *"Have Claude respond in a language other than English"* — is an INSTRUCTION TO THE MODEL, not a filter over what the model writes, and nothing in it partitions terminal prose from file writes. So on a machine where that key is set, every prose artifact the pipeline produces sits in the blast radius: `spec.md`, `plan.md`, task files, research reports, code comments, commit messages. **The corpus is a machine input before it is a human one** — downstream commands re-read these files, and mechanical checks match English tokens: dead-code anchor tokens are matched verbatim, `/devforge:verify` selects a memory bucket by matching `## What Failed` / `## What Worked` / `## Known Pitfalls`, and the constitution splitter recognises bold English headers. There was **no incident behind this change and none is claimed** — the exposure is argued, not measured. **Two layers, and only the first shapes behavior.** (1) The emitted `CLAUDE.md` gained a fifteenth `### Always` Key Rule, **English in files**: all file content and commit messages stay in English (specs, plans, code, comments, docs) regardless of any operator response-language setting, which applies to conversation only — and **verbatim quotes of user-reported words may keep their original language**, a clause that exists so the rule does not forbid what the framework's own design requires an artifact to carry (a `/devforge:fix` re-entry seed whose provenance is `conversational (in-window user report; no report file)` quotes the user directly, and `/devforge:grill` findings may too). The rule deliberately names **no settings key** — a consumer-facing rule outlives any particular Claude Code surface, so hard-coding one would rot it. `README.md`'s `## Install` section gained the matching operator note: set `language` in `~/.claude/settings.json` (every project on your machine) or `.claude/settings.local.json` (this project only), never in `.claude/settings.json`, which `install.sh` overwrites. (2) `artifact_helper commit-artifacts` gained an **advisory** Cyrillic scan. After staging succeeds and before the commit, it enumerates the staged set with `git diff --cached --name-only -z` — the staged set, never `--paths`, which may name a directory whose whole subtree is staged — decodes each file with `errors="replace"`, and scans it plus the commit label for U+0400–U+052F, writing one `commit-artifacts: warning: …` line per offending file to **stderr**. **It never blocks.** Exit codes and both stdout JSON shapes are byte-unchanged, the entire detector body is one fail-soft `try`/`except` that emits a single `language check skipped` line on any error, and it deliberately does not append to `stage_errors`, which is an exit-1 channel. **Honest bounds, stated rather than argued away.** Advisory rather than fail-closed, because a legitimate non-English content class already exists in the ratified design (the quoted-user evidence above) and a hard fail would have needed a carve-out on day one — the kind this repo's zero-escape-hatch policy forbids; the strengthening trigger is a **first confirmed leak the warning failed to stop**, and until one is observed the warning has demonstrated only that it does not fire on clean input. Detection is **Cyrillic-only**, so an operator who sets a Greek, Japanese or Arabic response language gets the rule but not the tripwire. And the scan covers **one commit path** — `artifact_helper commit-artifacts`, which every pipeline command's artifact commit rides, but **not `implement_helper wip-commit`**, so a leak inside a per-task or `[WIP] fix:` code commit is invisible to this guard. **Build-verified, NOT consumer-validated** — the consumer observation is a user-driven HARD GATE and has NOT run; its known-answer anchor is one Cyrillic word committed through `commit-artifacts`, which must print the warning and still exit 0.

### Changed
- feat(grill,spec-check,fix): `/devforge:grill`, `/devforge:spec-check` and `/devforge:fix` are model-invocable — `disable-model-invocation: true` removed, so a blocked `/devforge:plan` / `/devforge:breakdown` offers the required check and runs it on the user's agreement instead of asking the user to type it, and `/devforge:fix`'s remediate-now arm runs on agreement; one agreement per command, never a chained cycle; the human-typed set narrows to the four setup commands (`93-MODEL-INVOCATION-CARVE-OUT-NARROWING-PLAN.md`, Phases 0–4; Phase 5 consumer e2e deferred). The three descriptions are trimmed to the model-invocable budget and their `src/CLAUDE.md` catalog entries take the short form; gate predicates and verdict ownership unchanged.
- feat(research,discover,specify,configure): a feature directory is allocated as `specs/<YYYY>/<MM>/<leaf>/` on a `spec/<ticket>` branch, an opt-in ticket gate guards intake, and a `Run by:` provenance line rides the four artifacts that leave the repository (`91-FEATURE-DIR-IDENTITY-AND-PROVENANCE-PLAN.md`, Phase 0 ratified + Phases 1, 1b, 2, 3, 4 and 5 built, 2026-08-28 – 2026-09-03). **The origin is a design conversation, not an incident**, and none is claimed. Two problems were raised together and kept separate: *identity* — `NNN` is a repo-local counter allocated by scanning `specs/`, so a directory name means nothing outside this repository, even though the framework already scrapes an `[A-Z]+-[0-9]+` ticket out of a wrapper source branch — and *volume*, where at a realistic ~8 features/month a flat `specs/` holds ~200 sibling directories after two years. **The rejected alternative is recorded because it generalizes.** Keeping `specs/` flat and having `/devforge:finalize` move completed features into `specs/archive/` was declined: features that die mid-pipeline never reach `/devforge:finalize`, so an archive driven by a terminal command collects the *completed* work — which is already orderly — and leaves the *abandoned* work in place. The invariant adopted instead binds every part of this change: **placement is decided at creation time, by a mechanism that already has to run, and never changes afterwards.** Intake allocation is such a mechanism; a finalize-time move is not. **The layout.** `/devforge:research` and `/devforge:discover` now allocate `specs/<YYYY>/<MM>/<leaf>/` at their confirmed save — the allocation year and month, then the ticket the run named, or its 2-4 word kebab-case slug when it named none — and create the matching `spec/<ticket>` (or `spec/<slug>`) branch. The bucket records the **allocation** date while a feature is an interval, so the tree is a **birth index, never a work index**: a feature opened in August and finished in October lives in `2026/08/`. `ls specs/2026/08/` is correspondingly opaque and "where is the auth thing, I don't remember the number" loses its directory-name answer — accepted, because the title lives in the tracker and a title duplicated into a directory name goes stale when the ticket is renamed. **Both shapes coexist and NOTHING migrates.** Directories allocated before this layout keep `specs/NNN-slug/` indefinitely; resolution reads both shapes and writes only the new one, and every one of the six depth-1 resolvers reads both — a resolver that silently stops seeing an old feature is a data-loss-shaped bug, not a cleanup. **Ordering degrades, and the degraded contract was re-stated rather than deleted.** A ticket-shaped leaf carries no leading digit, so on a mixed install `/devforge:implement` drains legacy features in `NNN` order first and then new-shape features in allocation-date order. That is coherent and defensible — it simply is not what *"the lowest-numbered incomplete feature"* said, so the **nine** sites stating that contract now describe what resolution actually does; the four task-level occurrences are untouched, because task numbering inside a feature's `tasks/` is unaffected. **One silent-gate defect closed in the same change.** `src/git-hooks/pre-commit-forcing-functions.sh` located `design-manifest.json` with `find … -maxdepth 2` and skips its check when nothing matches; under the new layout a manifest sits at depth 4, so that `find` would have matched nothing and **the hook would have stopped gating without saying so.** The depth is now 4, both depths plus the neither-carries-a-manifest case are covered by tests, and the skip-when-absent behaviour is deliberate and unchanged. **The ticket gate is opt-in, and it is discipline rather than verification.** A new `REQUIRE_TICKET` key in `.devforge/project-config.json` defaults to `false`, and `/devforge:configure` asks — with a `(Recommended)` marker that moves with `WORKSPACE_MODE`, a marker and never a pre-selected answer.
