## Command mission (what /finalize is for)

`/finalize` exists to own the ONE job nothing else in the pipeline owns: **the terminal PR-prep step** — surgical feature-completion docs + git history cleanup. Nothing else in the pipeline squashes the accumulated `[WIP]`/`[checkpoint]` commits `/implement` produced; nothing else does targeted, feature-driven `docs/` updates at feature-completion time. `/verify` owns the verdict, `/review` owns findings, `/summarize` owns the PR-ready narrative; `/finalize` owns the clean commit + the surgical docs that ship with it.

`/finalize` DISPATCHES the `tech-writer` agent (D1 — the INVERSE of `/summarize`'s agent-free D1): tech-writer runs in its Normal/surgical mode over the feature's changed files, retargeted to the LIVE Plan-F doc locations (`docs/<package>/<concern>/index.md` Hazards, `docs/<package>/architecture.md`, `docs/architecture.md`) — NOT the DROPPED `docs/features/<name>.md` tier. Then `/finalize` squashes (D4 — it MUTATES local git history), docs-first so the docs fold into the clean commit (D8).

**The boundary, stated explicitly:** `/finalize` runs NO finder ensemble, NO refutation engine, and NO verdict. It does not verify (that is `/verify`), does not find issues (that is `/review`), does not synthesize the PR narrative (that is `/summarize`). A future session must NOT wire any finder/refuter/verdict machinery into `/finalize` by analogy with `/review` or `/verify`.

### The /verify-vs-/summarize-vs-/finalize invariant

`/verify`, `/summarize`, and `/finalize` are three consecutive pipeline commands with non-overlapping jobs. This table is the invariant the plan must preserve:

| Axis | `/verify` | `/summarize` | `/finalize` |
|---|---|---|---|
| **Trigger** | in-pipeline, after `/review` | in-pipeline, after `/verify` approves | in-pipeline, after `/summarize` |
| **Reads** | spec ACs + assembled diff + `review.md` | spec + plan + tasks(+`## Completion Notes`) + git + `verification.md` | spec + plan + tasks + `summary.md` + the feature's changed files + git WIP/checkpoint commits (the changed-file list + git WIP/checkpoint commits are additions beyond plan 24's `/summarize` Reads entry — needed for the tech-writer brief + the squash detection) |
| **Writes** | `specs/[feature]/verification.md` + FLIPS spec `**Status**:` | `specs/[feature]/summary.md` | `docs/` (surgical tech-writer updates) + SQUASHES WIP/checkpoint → one clean commit (+ wrapper-mode source-repo squash) |
| **Job** | AC conformance + assembled mechanical + verdict | PR-ready feature narrative | surgical docs + git history cleanup (the terminal PR-prep step) |
| **Mutates input?** | **YES** — flips the spec to Complete | **NO** — read-only on inputs | **YES** — rewrites local git history (squash) + writes `docs/` |
| **Dispatches agent?** | YES — `ac-verifier` | **NO** — orchestrator-inline synthesis | **YES** — `tech-writer` (Normal/surgical mode) |
| **Pipeline next-step** | → `/summarize` | → `/finalize` | **TERMINAL** — "create a PR" (no command pointer) |

The `/finalize` "Mutates input? YES" cell is for a DIFFERENT reason than `/verify`'s: `/verify` writes back to the spec (it owns the Complete lifecycle transition); `/finalize` rewrites local git history (it squashes). Both contrast with `/summarize`'s "NO". And the `/finalize` "Dispatches agent? YES" cell is the deliberate INVERSE of `/summarize`'s "NO" (D1).

**Acknowledged overlap to flag** (consistency-over-invention): tech-writer's surgical `docs/` updates in `/finalize` conceptually overlap with `/generate-docs` (the whole-codebase structural doc author). The distinction a future session must hold: `/finalize` does TARGETED, feature-driven surgical doc updates at feature-completion time (tech-writer Normal mode, scoped to the feature's changed files); `/generate-docs` does stamp-gated whole-codebase regeneration (tech-writer Skeleton-Fill mode). ## Squash mechanics (the heart — from the draft, to be modernized)

- **WIP/checkpoint detection (the no-op gate):** `git log --oneline --grep="\[WIP\]" --grep="\[checkpoint\]" [DEFAULT_BRANCH]..HEAD` → if none, "Nothing to finalize" no-op (`finalize.md:41-45`). **Use the BSD-safe two-flag form shown above:** pass each prefix as its OWN `--grep` (git ORs multiple `--grep` patterns) — do NOT use the `\|` BRE alternation the draft wrote (`finalize.md:41-45`), which BSD/macOS git does not honor (this exact bug was fixed in `/summarize` — see `src/commands/summarize/main.md:96,99` and its inline note).
- **Wrapper/install repo squash base:** on a feature branch → `git merge-base HEAD [DEFAULT_BRANCH]`; on DEFAULT_BRANCH → fallback to the oldest `[checkpoint]` commit's parent (`finalize.md:85-87`). Compute via `_shared` `resolve_feature_scope`'s `merge_base` for the feature-branch case.
- **Already-pushed guard:** `git log --oneline origin/$(git branch --show-current)..HEAD` → if commits already pushed, SKIP squash + warn (don't rewrite shared history) (`finalize.md:88-102`).
- **Squash execution:** `git reset --soft [base] && git commit -m "<message>"` (`finalize.md:92-96`). Wrapper/install commit message: `feat([feature-name]): <spec title>` + Commit Convention attribution (per `COMMIT_ATTRIBUTION` config).
- **Wrapper source-repo squash:** `git -C $SOURCE_ROOT reset --soft [base] && git -C $SOURCE_ROOT commit -m "[TICKET-ID] - Description"` (`finalize.md:13-24,104`), NO AI traces (D5).
- **There is NO existing squash helper.** The `git reset --soft` / squash logic does NOT exist anywhere in `src/devforge/lib/` (verified this session — only unrelated `cmd_reset_*` STATE-FILE resetters exist). The squash EXECUTION verb is net-new (Phase 3). BUT the merge-base computation reuses `_shared/feature_scope.py` (D2), and ticket-ID extraction reuses `_extract_ticket_id` (`src/devforge/lib/_implement/_cmds_commit.py:171-186`, pattern `_TICKET_PATTERN = re.compile(r"\b([A-Z]+-[0-9]+)\b")` `:107`). **NOTE the live pattern is `[A-Z]+`, NOT the draft's `[A-Z]{2,}` at `finalize.md:18`** — reuse the live helper, do not re-author the regex.
