## Command mission (what /audit is for)

`/audit` evaluates the whole project (broad / hotspot mode) or a given path (narrow mode) for the **full quality spectrum** — bugs, dead code, inconsistency, code smells / bad practices, duplication, and constitution violations. This mission maps onto the command's already-shipped `CATEGORY_ENUM` + the `[CONSTITUTION-VIOLATION]` tag — it is an ANCHOR to the established taxonomy, NOT a new one:

| Mission wording | Existing taxonomy value |
|---|---|
| bugs (control-flow, off-by-one, inverted conditions) | `mislogic` |
| dead code | `mislogic` (the mislogic-checklist's "Dead / zombie code" section) |
| inconsistency (cross-file contradictions) | `mislogic` |
| inconsistency (diverged copies) | `duplication` |
| code smells / bad practices | `best_practice` + `system_design` |
| security vulnerabilities (injection, auth gaps, unsafe patterns) | `security` |
| constitution violations | the `[CONSTITUTION-VIOLATION]` tag (always Critical, never downgraded) |

(`blind_spot` completes the `CATEGORY_ENUM` — a catch-all for out-of-domain / borderline findings not fitting the above.)

This matches the LIVE command's documented purpose — the `main.md` frontmatter `description` + the `src/CLAUDE.md` `/audit` entry — so it is FRAMING, not a scope change. The plan does not widen or narrow what `/audit` hunts.

**The constraint this imposes on the plan:** the precision work recovers PRECISION (removes false positives) and must NOT shrink the spectrum or erode recall on any mission category. The refutation pass (Change A) filters false positives; it does not narrow the hunt. The mechanism that enforces recall-protection on the highest-cost categories — `security` findings and `[CONSTITUTION-VIOLATION]`-tagged findings — is the new high-stakes recall guard (D7, see `## Decisions`): an `uncertain` verdict on those categories is SURFACED in the headline as `[CONTESTED]`, never buried in the appendix.

## Problem / root cause (verified this session)

`/audit` over-reports false positives — it is structurally tuned to "always find a bug even when there is no bug." This is a design property of the current pipeline, not a tuning accident. Three findings, each verified against the live files:

### 1. The finder is explicitly ordered to over-report

`src/commands/audit/references/adversarial-preamble.md` ground rules (lines 24–37): rule 1 "Bias toward false positives over false negatives"; rule 2 "Do NOT soften findings. Do NOT add 'this is probably fine' disclaimers"; rule 3 "Do NOT assume good intent in unclear code"; rule 6 "You are looking for the bug the team missed. Assume it exists. Find it." The grounding caveats ("ONLY when grounded", lines 25–26, 36–37) constrain FABRICATION — they require a real verbatim quote — but they do NOT constrain CORRECTNESS: a real quote of perfectly correct code still satisfies every grounding rule. An agent told to assume a bug exists will manufacture one on clean code, quote it honestly, and pass.

### 2. The only filter checks GROUNDING, never CORRECTNESS

`src/devforge/lib/_audit/_validate.py` `validate_findings` runs exactly 5 checks (module docstring lines 7–21, enforced in `_check_finding` lines 183–235): (1) file exists, (2) line in range, (3) evidence is a whitespace-normalised substring of the file, (4) evidence non-empty / not `"..."`, (5) pattern non-empty. All five are HONESTY checks. A verbatim quote of correct code passes all five. There is NO "is this actually a defect?" gate anywhere in the pipeline — grounding is the only filter, and grounding ≠ correctness.

### 3. Every downstream stage AMPLIFIES — nothing SUPPRESSES

The pipeline is monotonic-upward on confidence/severity/score from validation onward:

- **`_consensus.py` `compute_consensus`** (single-pass) — groups by exact `(file, line, normalised-pattern)` SHA-1 hash; on a ≥2-distinct-agent group it tags `[CROSS-AGENT]` and BUMPS severity one level (`_bump_severity`, lines 124–136). No demotion path exists. (Exact-hash matches are rare because `pattern` is free text, so this fires seldom — but when it fires it only goes up.)
- **`_merge.py` `merge_passes`** (multi-pass `--passes >= 2`) — union = OR across K passes, so more passes ⇒ strictly MORE findings. Worse, `_annotate_representative` (lines 236–242) FLOORS confidence to `"Likely"` for any cluster seen in ≥2 passes via `_confidence_floor(rep.get("confidence", "Speculative"), "Likely")`. A false positive the model reliably re-generates (the same clean code reliably trips the same wrong heuristic) is **correlated error**, but the merger reads recurrence as corroboration and PROMOTES its confidence. (`_merge` does NOT bump severity on cross-agent overlap — that was deliberately removed per plan 12's post-validation fix — but it does floor confidence on cross-pass recurrence.)
- **`_rank.py` `_score_finding`** (lines 165–199) — `score = severity_weight × confidence_weight × cross_agent_bonus × recurring_bonus × pass_bonus`. Every multiplier is `>= 1.0`; `cross_agent_bonus` is 1.5, `recurring_bonus` 1.5/2.0, and `pass_bonus` adds a further 1.25 at `pass_count == 2` / 1.5 at `>= 3`. Nothing in the score ever ranks a finding DOWN.

So the whole stack is monotonic-upward, built on a finder ordered to assume bugs exist, with the sole filter checking honesty rather than correctness. The command structurally cannot NOT over-report.

### The antidote already exists in this repo — plan 17

`17-IMPLEMENT-PER-TASK-PANEL-PLAN.md` (SHIPPED) gave `/implement`'s PHASE 6 a review panel whose findings must be CONFIRMED before they gate, with reviewer conflicts surfaced as questions and `accept anyway` removed (its D4 — "all findings fixed before the human hard gate"). The `/audit` pipeline is missing exactly that REFUTATION/VERIFICATION stage — it GENERATES (agents) and GROUNDS (`validate-findings`) but nothing REFUTES. (The mechanism differs — `/audit`'s helper/orchestrator scratch-chain split, not plan 17's `merge-review-panel` verb — but the principle is the same: a finding earns its place by surviving an adversary, not by being generated.)

## The four changes (A is the spine; B/C/D layer on)

### A — Add a refutation / second-opinion pass (the spine; highest leverage)

After grounding-validation AND after consensus/merge, BEFORE recurring-mapping and ranking, run a SKEPTICAL pass over the deduped working list whose only job is to knock findings down. **Default verdict = NOT-a-bug** unless the skeptic can demonstrate the defect from the quoted code. Findings that fail refutation move to a "Dismissed / worth-a-glance" report appendix — they do NOT appear in Top-N or the main by-file findings. This inverts the pipeline default from "assume bug" to "assume correct unless proven," in a SEPARATE stage, so the finder stays high-recall (preserving the recall the multi-pass + full-spectrum investment bought) while precision is recovered in verification.

Design constraints A must honor:

- **Mirror the existing helper/orchestrator split exactly.** A subprocess helper has NO MCP/Task tools — it cannot dispatch agents or read code. So the ORCHESTRATOR dispatches the refuter agent(s) and they write verdicts to a `$WORKDIR` scratch file; a new helper verb consumes the verdicts + the working findings and partitions them. This is the SAME pattern as the live pipeline's `render-agent-brief` → agent writes `$WORKDIR/tmp-<agent>.md` → `consume-tmp` → `validate-findings`, and the same shape plan 17 used (orchestrator dispatches, helper does the deterministic merge). The refuter agents are themselves finders (D2), which ALREADY write their `$WORKDIR/tmp-<agent>.md` via shell redirection (`main.md:276`) — they carry `Bash` in their `tools` allowlist, so the read-only allowlist does NOT block the verdict-file write (claude-code-guide flagged read-only agents cannot use the Write tool; for these agents that is a non-problem — they write via Bash, not Write).
- **New reference file** `src/commands/audit/references/refutation-preamble.md` — the refutation preamble + a verdict output contract. The refuter writes its verdicts as a **fixed-format MARKDOWN block per finding** (mirroring the finder output contract that `consume-tmp` parses) — NOT JSON; agents produce robust fixed-format markdown, and the verdicts re-quote code full of quotes/braces that make agent-emitted JSON fragile. Per-finding contract fields: the finding ref/id being judged; a `Verdict:` ∈ `{confirmed, dismissed, uncertain}`; a one-line justification; and a per-branch evidence requirement that puts the burden of proof on CONFIRMATION, not dismissal. The verdict branches form a clean dichotomy — confirm bears the burden, dismiss is the default — each branch stating its own mandatory evidence (no "use judgment" middle ground):
  - **confirmed** — REQUIRES re-demonstrating the defect: re-quote the offending code + state why it is a defect, to the same grounding standard the finder is held to. This is the finder's burden, re-met by the skeptic.
  - **dismissed** — the DEFAULT when no defect is demonstrable. A counter-quote (the guard / code path that makes the finding wrong — e.g. the guard the finding claimed was missing) is provided WHEN ONE EXISTS, but absence of a counter-quote does NOT block a dismissal: confirmation bears the burden, not dismissal, so an undemonstrable finding is dismissed by default.
  - **uncertain** — when the refuter genuinely cannot resolve it from the code (e.g. a finding outside the author's specialty that the non-author refuter — broad but not the specialist — cannot decide). State what is unresolvable. Routes per D7 (category-aware): high-stakes `security` / `[CONSTITUTION-VIOLATION]` findings → the headline flagged `[CONTESTED]`; all other categories → the appendix (OQ-2).
  This plan SPECIFIES the contract fields; it does NOT write the full reference text (that is Step 1's authoring work, via instruction-author → instruction-reviewer).
- **New helper module + four verbs** in `src/devforge/lib/_audit/`. New module `_verify.py`. (1) `route-refutation` (NEW) is the deterministic cross-examination router: it groups the working findings by author (the finding's `agent` field — the representative author after consensus/merge dedup) and assigns each group a non-author refuter per the routing policy below, given the present-finders list from the Phase-1.2 agent-existence check. It returns a routing map — a list of `{refuter: <agent>, findings: [...]}` groups — and is testable with no LLM (pure deterministic selection). (2) `render-verify-brief` assembles the refuter prompt listing the findings to refute, mirroring the existing `render-agent-brief` — building it (not assembling the prompt inline at the orchestrator) keeps the refuter-prompt assembly testable via python-engineer → python-reviewer. With cross-examination it takes the refuter's ASSIGNED findings subset (one refuter group), not the whole working list. (3) `consume-verdicts` (NEW) parses one refuter's fixed-format markdown verdict file into a bare verdict array — it mirrors the existing `consume-tmp` (which parses the finder agents' fixed-format `$WORKDIR/tmp-<agent>.md` into a findings array); the refuter, like the finders, writes robust fixed-format markdown, not strict JSON. (4) `apply-verdicts` takes the full working findings array + the parsed verdict array (the merged verdicts across all refuters) and partitions category-aware per D7 — it returns confirmed / dismissed / appendix-uncertain / headline-contested buckets (or equivalent), routing `uncertain` verdicts by the finding's declared `category` + the `[CONSTITUTION-VIOLATION]` tag (high-stakes `security` / `[CONSTITUTION-VIOLATION]` → headline-contested; all other categories → appendix), and applying the verify confidence to confirmed findings. The verb partitions by declared verdict + category only; the burden-on-confirmation evidence rule itself lives in the refutation preamble, not the deterministic partitioner. All four verbs register in `_cli.py`'s `_SUBCOMMAND_REGISTRY` (the list at `_cli.py:1077`).

Each finding is refuted by a non-author FINDER — there is no separate skeptic agent. **Refuter selection (deterministic):** the refuter is the FIRST present finder, by the fixed priority order `[code-reviewer, architect, qa-reviewer, security-reviewer]`, that is NOT the finding's author (the finding's `agent` field — the representative author after consensus/merge dedup). The selection respects the present-finders list from the agent-existence check (Phase 1.2): only present finders are eligible refuters. **Sole-finder edge case:** if the finding's author is the ONLY present finder (a degenerate 1-finder audit), that sole finder self-refutes under the default-dismiss brief — degraded independence, explicitly noted in the report. ## Decisions (settled design choices — flip any during review)

### D1 — Refutation is a separate stage, inserted after merge, before recurring/rank

The skeptic pass runs on the DEDUPED working list (post-consensus / post-merge), not on raw per-agent output. Rationale: dedup first means the skeptic judges each distinct finding ONCE, not once per agent/pass that raised it — cheaper, and it judges the same representative the report will show. It runs BEFORE recurring-mapping and ranking so those stages operate only on survivors (a dismissed finding should never be ranked or recurring-tagged).

### D2 — Cross-examination routing — each finding refuted by a non-author finder; no 18th agent

**Charter check (what invalidated the prior design).** The earlier design assumed a suitable INDEPENDENT, GENERALIST, read-only reviewer existed OUTSIDE the four audit finders. The Step-1 charter check proved it does NOT. `design-auditor` is UI/visual/accessibility-only (`applies_to: ["web", "mobile"]`, chrome-devtools MCP tools — the wrong tool for backend/polyglot correctness, and it may not even install on a non-web project). `performance-analyst` is perf-only. `ac-verifier` is runtime acceptance-criteria verification, not a correctness skeptic. None is a generalist correctness reviewer. The only broad correctness reviewer in the roster is `code-reviewer` — which is itself one of the four finders. So a single non-finder skeptic is not viable: there is no agent that is both a generalist correctness reader AND outside the finder set.

**The replacement decision (user-confirmed 2026-06-14): CROSS-EXAMINATION ROUTING.** Each finding is refuted by a non-author FINDER. This keeps broad code-reading competence (a finder reads code in its general capacity) AND structural author≠refuter independence (the refuter is always a different finder than the author), with NO new 18th agent — cross-examination reuses the four finders.

**Refuter selection (deterministic, zero-escape-hatch).** The refuter is the FIRST present finder, by the fixed priority order `[code-reviewer, architect, qa-reviewer, security-reviewer]`, that is NOT the finding's author (the finding's `agent` field — the representative author after consensus/merge dedup). This uses the strongest generalist, `code-reviewer`, as the default refuter for everything it did not author, and routes `code-reviewer`'s own findings to `architect` (both broad code readers). Selection respects the present-finders list from the Phase-1.2 agent-existence check — only present finders are eligible refuters. **Sole-finder edge case:** if the finding's author is the ONLY present finder (a degenerate 1-finder audit), that sole finder self-refutes under the default-dismiss brief — degraded independence, explicitly noted in the report. This is the single named exception, not a slip-path: it fires ONLY when no other finder exists. No "use judgment" anywhere — the routing is priority order + author-exclusion + one named edge case.

**File-write mechanism — not a blocker.** claude-code-guide cautioned that read-only agents cannot use the Write tool, but the refuters are finders that ALREADY write `$WORKDIR/tmp-<agent>.md` directly via shell redirection (`main.md:276`) — they carry `Bash` in their `tools` allowlist, so the read-only allowlist does NOT block the verdict-file write. The refuter writes `$WORKDIR/verdicts-<refuter>.md` the same way.

No new `src/agents/*.md` file — plan 15's roster + the `generate-agents.py` build contract stay untouched. Rationale: independence is now STRUCTURAL per finding (author≠refuter always, except the named sole-finder case — no self-confirmation bias), and competence stays broad (a finder refutes, not a narrow non-finder, so the prior design's `uncertain`-from-incompetence on whole categories does not arise). The residual competence gap is narrower but real — a non-author finder may be outside the AUTHOR's specialty (e.g. a `security-reviewer` finding refuted by `code-reviewer`, who is security-aware but not the specialist) — and that gap is caught by D7's high-stakes `uncertain`→headline-`[CONTESTED]` guard (the safety net stays). That safe-degradation is made precise by D7: low-stakes `uncertain` → appendix (OQ-2), but high-stakes (`security` / `[CONSTITUTION-VIOLATION]`) `uncertain` is SURFACED in the headline as `[CONTESTED]`, not appendix'd. The only remaining escalation if v1 precision is still too low is OQ-1's N-vote panel (rung 2).

### D7 — Category-aware `uncertain` routing protects recall on high-stakes categories

The refutation stage (A) must not erode recall on the categories where the cross-examination refuter (D2 — a non-author finder, broad but possibly outside the author's specialty) is BOTH most likely outside its competence AND a miss is most costly: **`security` findings and `[CONSTITUTION-VIOLATION]`-tagged findings.** A non-author finder reads code in its general capacity — competent at `mislogic` / dead-code / `duplication`, but when refuting a finding outside its specialty (e.g. `code-reviewer` judging a `security-reviewer`-authored finding, or any finder judging a project-specific constitution rule) it may return `uncertain` from a specialty gap rather than from a genuinely undecidable finding — concentrated in exactly those two high-stakes categories. Sending those to the appendix would bury exactly the findings the human most needs to see.

**The routing rule (per-category, no judgment call):** `uncertain` verdicts route BY category.

- **High-stakes** — `security` findings and `[CONSTITUTION-VIOLATION]`-tagged findings → the HEADLINE, flagged `[CONTESTED]` (surfaced for the human, never buried), NOT the appendix.
- **All other categories** — `mislogic` / `system_design` / `best_practice` / `duplication` / `blind_spot` → the appendix (the OQ-2 lean).

**The constitution carve-out (NEW logic in `apply-verdicts`):** D7 adds a carve-out that Step 1 builds in `_verify.py`'s `apply-verdicts` — a "dismiss" verdict on a grounded `[CONSTITUTION-VIOLATION]` finding surfaces as `[CONTESTED]` in the headline rather than dropping to the appendix. The refuter can voice doubt, but cannot bury a grounded rule-break. (The existing "always Critical, never downgraded" rule governs the FINDER's severity output; this carve-out governs the REFUTER's verdict routing — they are separate mechanisms, and the carve-out is built fresh in `apply-verdicts`, not derived from the severity rule.)

Rationale: this keeps the human in the loop on the highest-cost categories while still letting the skeptic filter false positives in the lower-stakes ones — directly serving the Command mission (`## Command mission`), which lists constitution violations and (via bugs / security) the high-cost categories as part of the spectrum the precision work must not erode. The rule is a clean per-category partition plus a single constitution carve-out — no "use judgment" middle ground.
