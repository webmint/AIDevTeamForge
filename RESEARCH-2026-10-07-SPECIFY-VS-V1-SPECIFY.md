## Part 1 — Scope mapping: the one command whose v1 pair is itself

Unlike `/research` and `/discover`, `/specify` maps to v1 by name AND by job: v1 `/specify` took "a natural language description" and produced "an unambiguous, reviewable spec" at `specs/NNN-feature-name/spec.md`; v2 does the same into the feature directory intake allocated. The deliverable's skeleton did not change: **the same 9 sections** (Overview, Current State, Desired Behavior, Affected Areas, Acceptance Criteria, Out of Scope, Technical Constraints, Open Questions, Risks — v1 `:153-216`, v2 Steps 4.2–4.8), the same `Draft` status, the same closing instruction to run `/plan`, and v1's seven IMPORTANT RULES carried verbatim as v2 rules 1–7 (`:1024-1030`).

What DID change is the command's place in the chain, and it is the largest single difference:

| | v1 | v2 |
|---|---|---|
| Entry | `/specify "<description>"` is the pipeline's entry point; `/research` before it was optional ("Skip it when you already know what you want to build") | Phase 0.4 (`:98-140`) refuses to run without a pending intake handoff: *"there is NO cold-spec escape hatch, even for a feature the user researched externally"* (`:120`) |
| Who interrogates the user | `/specify` Phase 2 alone — six clarification areas, rounds of ≤5 questions, *"If the description is clear enough, skip to Phase 3"* (`:85-103`) | twice: the intake rubric (`/research` 6 dimensions or `/discover` 8), THEN `/specify` Phase 2's seven-category decision-point sweep (`:330-459`) |
| Idea → approved spec | one command; v1 median 11.5 min / 50 turns / 1 stop (17 runs) | two commands; `/research` 30–68 min / 172–258 turns / 12 stops + `/specify` 19 min / 197 turns / 2–4 stops |

So the honest v1 pair for *"how much does it cost to get from an idea to a spec"* is v1 `/specify` against v2 **intake + specify**, and the rubric cost the research and discover audits measured is, from this command's side, the price of `:120`. Part 4 item 2 records what that second interrogation layer actually receives from the first.

## Part 4 — Observations the v1 lens adds (not in the 10-05 audit)

1. **Same deliverable, ×11.6 the prose.** Nine sections, seven rules and the three Phase 0.2 git commands are v1 verbatim; every byte of growth is process (gates, setters, four header paths, two re-entry arms) and typing (EARS, kinds, change-kind). Of the 132 KB, ≈ 29 KB (Phase 0.4 + 0.5 + Step 4.1) describes paths a normal run does not take, and ≈ 26 KB is Phase 0 — against v1's 2.0 KB for the same branch logic. The 10-05 audit's F2 and plan 133 D6 own the diet; this item only records that the growth is not in the output.

2. **Two interrogation layers, no typed bridge between them (OQ-3 answered — see Part 5).** Five of the seven DP categories have an intake-dimension counterpart: `scope_boundaries` ↔ research `scope` / discover `functional_scope`; `existing_behavior` and `breaking_changes` ↔ research `unchanged_behavior`; `data_flow_state` ↔ discover `inputs_outputs`; `edge_cases` ↔ discover `edge_cases`; and discover's `non_goals` feeds nothing but §6, which Step 4.5 writes afresh. The rubric answers reach `/specify` only as `spec_seeds` (§4 / §7 / §8 / §9 entries and the design anchor) plus whatever the rendered report says in prose — and `discovery-report.md` has no scoping section at all. The spec's own sentence at `:356` (*"A `"one place"` answer to `/devforge:research`'s `scope` question names no surface"*) shows the authors were already reconciling the two layers by hand. This is the single most useful fact for OQ-1: whatever the batched scoping table becomes, its answers are today re-asked, not re-used, one command later.

3. **No proportionality clause anywhere in the file.** `/research` claims it at `:127` and `/discover` at `:116`, and `/specify` promises on their behalf that *"research for [a two-sentence bug] is a 30-second pass"* (`:120`) — but `/specify` itself scales nothing: ≥3 findings per source, ≥7 category entries, 7 AC subsections each populated or marked N/A, 4 blocking verifiers, the design stop, apply to a one-line bug fix exactly as to a migration. v1 had two scaling sentences (`:87`, `:103`); v2 replaced them with *"Ask every one of them anyway"* (`:332`). The fast path the whole intake story promises ends at `/specify`'s door.

4. **Half of the new typing has no reader.** Grep of `src/` outside `_specify/` and `commands/specify/` on 2026-10-07: consumed — `subsection` (via `_shared/spec_acs.py` → `_verify/_ac.py`, `_spec_check/_brief.py`, `plan_helper.py`, `breakdown_helper.py`), `spec_seeds` (`plan_helper.py`), `design_anchor` (`_design/`, plan, breakdown, review), spec stamps (plan, breakdown, finalize), EARS as text (`spec_acs.py`, spec-check's formalization guidance); **zero consumers** — `ears_variant`, `verification_command` (the shared parser skips `> Verification:` hint lines by design, `spec_acs.py:26-28`), `test_anchor` (the spec itself says `/verify` does not read it yet, `:716`), `change_kind`, `path_evidence`, `finding_ref` / `landed_in`. The second group is write-time forcing functions — legitimate, but it bounds what "losing quality" can mean: dropping `--test-anchor` today loses nothing downstream, and the EARS regex is a shape check on a sentence nothing parses by variant.

5. **The four phase gates are opt-in.** `phase1-finalize`, `findings-finalize`, `dp-finalize` and `phase3-finalize` each stamp a `*_finalized` flag; the only reader of those flags is `cmd_summary` (`_cmds_phase3.py:220-248`), the `summary` verb the spec never names. `cmd_render` (`_cmds_phase4_verify.py:470`), `_render.py`, `_cmds_phase5.py` and `finalize-handoff` contain no reference to them. A run that skips Phase 1.5 wholesale and never calls `findings-finalize` is blocked by nothing: `render` renders, `finalize-handoff` writes. This is consistent with the measured runs — 28 / 12 / 9 / 2 / 1 helper calls against a static minimum above 100 — and it means the as-written protocol has been executed on at most one measured run (the 63-call heavy run). Two consequences for the roadmap: (a) the measured 197 turns UNDERSTATE the protocol as written, so a batched rewrite (plan 133 D7) is partly formalizing what runs already do; (b) before anything is cut, one run must be read for which gates fired — the profiler's segment tables do not say.

6. **CBM is mandated five times and used zero times.** `:227` (§1.4 docs via graph), `:534-539` (Step 3.3 MANDATORY chain, `Read` ban on source files), `:657` and `:667` (citations *"traced through the codebase-memory-mcp chain … never asserted"*), `:918` (a future `trace_path` expansion). The diagnosis measured 0 CBM calls on every specify run (`:303`). For OQ-2 this is the cleanest data point of the three commands: on `/specify`, CBM's removal costs nothing that was ever measured, and the §5.2 / §4 citation standard already names `file:line` as the evidence, which Grep/Read produce equally well.

7. **The v1 approval was one stop; v2's normal path is five.** The 10-05 audit counted two from the heavy run; static reading gives five on the normal (imported) path — handoff pick, DP round, spec-type accept, design source, approve — and the plan-81 median was four. Two of the five are new questions whose answer is already in state: the spec-type accept/override re-confirms what `import-handoff` seeded (`:467`, `:490`), and the design source re-asks on every `request-changes` loop (F10) and on every project (plan 123). Research's F6 "cost gate stop" has no counterpart here — good — but the handoff pick (`:126`) is the same shape: a question whose normal answer is "yes, the most recent one".

8. **Sibling drift worth deciding once.** DP follow-up cap 3 (`:414`) matches discover's 3 and not research's 2; `record-risk` takes `Low|Med|High` (`:817`) while discover's effort enum spells `Medium` (discover audit finding 10); specify's memory-state paragraph (`:201-208`) is the third copy of the same semantics.

## Part 5 — OQ-3 closed: does `/specify` read the eight discover dimensions?

**No — neither typed nor as prose.**

- Typed: `_import_handoff_discover` (`_cmds_handoff.py:749-888`) reads `spec_seeds.spec_type_hint` / `constraints` / `affected_areas` / `risks` / `open_questions` / `design_anchor`, `plan_seeds.recommended_option_rationale`, `plan_seeds.build_vs_buy.recommendation` and `discover_completed_at`. The eight `DimensionRecord`s travel in `discovery_block.memo_dimensions` (`_discover/handoff_schema.py:744`, built at `_handoff_build.py:434`); `_specify/` contains zero reads of `memo_dimensions`, `discovery_block`, `scoping` or `intent` (the one `intent.feature_concept` read at `:958` is the `find-handoffs` summary line). Same shape on the research lane: `_import_handoff_research` (`:575`) reads the same `spec_seeds` fields; `symptom_summary` / `desired_summary` / `scope` have zero reads in `_specify/`.
- Prose: `discovery-report.md` renders Summary, Prior Art, Integration Surface, Fit Assessment, Design Options, Build vs Buy, Absence Probes, Derisk Plan, Constitution Constraints, Open uncertainties, Recommendation, Next step (`_discover/_cmds_core.py:343-548`) — no scoping section, so §1.6 cannot carry the answers either. `research-report.md` renders `## Symptom` (`_research/_render.py:118`), so research's symptom reaches `/specify` as prose; the other five dimensions do not.

Consequence for OQ-1: the rubric's value to `/specify` is exactly what the intake command distils into `spec_seeds` and its report — which is also what a batched scoping table would produce. Dimensions whose only consumer is the intake command's own gates (discover audit: `functional_scope`, `inputs_outputs`, `integration_points`, `non_goals`, `success_criteria` have 0 name-hits in specify) are candidates to drop or merge without any downstream loss, provided the intake report keeps the prose.

## Part 6 — Verdict in one paragraph

`/specify` is the one command whose v1 pair produced the same artifact from the same template, so the ×11.6 in prose and the ×4 in turns are pure process: a state machine with 59 verbs, four phase gates nothing enforces, and two forcing functions — findings enumeration and the decision-point sweep — that are the credited quality and most of the turns. Against v1 the honest unit is the chain: v1 reached an approved spec in one command and one stop; v2 reaches it through an intake command it refuses to run without, whose rubric answers it then re-asks as decision points because no typed field carries them across. The three decisions this comparison feeds are the ones already open — OQ-1 (one batched scoping table, decided once, with `/specify`'s categories in view so the same question is not asked twice), OQ-2 (CBM: mandated five times here, measured in use zero times), and plan 133's D7/D9 (batch the writes — but read one real run first, because the gates are opt-in and the measured runs already skip most of what the file mandates).
