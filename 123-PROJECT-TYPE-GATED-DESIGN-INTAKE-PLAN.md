# 123 — Project-Type-Gated Design Intake Plan

**Created**: 2026-09-26
**Status**: Stub — problem statement only. The plan body (findings, decisions, phases) is to be authored.

## Problem

Nothing in the setup chain establishes what kind of project this is by asking. `/devforge:configure` Phase 2 has the LLM pick `PROJECT_TYPE` from a "legacy 13-category taxonomy" ("Pick the label that best matches the composed `FRAMEWORKS` + `LANGUAGES` signal") and derive `PROJECT_NATURES` from `PROJECT_TYPE` + `FRAMEWORKS` by composition rules; the operator answers no question about either and meets both only inside Phase 2's bulk echo, confirmed with `Reply 'yes' to confirm all`. `project_natures` is a `string_array` and no member of `ENUM_FIELDS` in `src/devforge/lib/_configure/_schema.py`, so its vocabulary is advisory rather than validated at setter time — `src/commands/configure/main.md` calls it a `Closed vocabulary` regardless, a wording discrepancy already recorded as F14 of `101-NON-WEB-STACK-READINESS-PLAN.md`. The one signal a type gate could rest on is thus LLM-composed, operator-unconfirmed and unvalidated.

No intake site reads that signal. `/devforge:specify` Step 4.10 asks via `AskUserQuestion` `"What is this feature's design source?"` — four options, default `None — no UI, or no design reference`, feeding `specify_helper set-design-source` — and states verbatim that "This fires on every spec — a feature with no UI simply declares `none`"; `/devforge:research` and `/devforge:discover` each ask the same supplementary free-text prompt ("Is there a design reference for this feature's UI … If none, answer 'none'.") before recording an anchor through `research_helper set-design-anchor` / `discover_helper set-scope-design-anchor`. All three are unconditional, and a grep for `PROJECT_NATURES` / `project_natures` across `src/commands/` and `src/devforge/lib/` outside `_configure/` reaches only `src/devforge/lib/_review/`, `src/commands/review/main.md`, `src/commands/configure/main.md` and one field-listing line in `src/commands/constitute/main.md` — no intake command spec is among them. `src/constitution.md:151` compounds it: `### 3.8 Design Fidelity [universal]` — the built-UI sanity floor, the anchor/binding model, and the two orthogonal static/runtime checks — is written verbatim from `.devforge/templates/constitution.md` into every project's `.devforge/constitute.json` by `constitute_helper seed-universal` and shown as-is by `/devforge:constitute` Phase 3, so a CLI-, library- or Terraform-only project carries the whole section and its operator must react to it, a Phase 3 user override applied through `drop-section` being the only thing that removes it.

The build-side and forcing-function gates are already mechanical and are not what this plan re-gates: `/devforge:breakdown` PHASE 2.5 tests for `design/reference.html` and skips entirely when it is absent, `/devforge:review` PHASE 2.5 requires that reference plus `<feature_dir>/design-manifest.json`, `/devforge:review` PHASE 2.5b branches on `review_helper resolve-ui-scope`, and the `design_token_provenance` forcing-function offer in `/devforge:constitute` Phase 3 is suppressed — echo block and setter call both — when neither `design/styles.css` nor `design/reference.html` exists. Only the intake asks and the seeded 3.8 fire unconditionally.

The failure modes are asymmetric: a false "no UI" silently drops the design anchor that the whole anchor → binding → runtime-compare chain consumes, while a false "UI" costs one question. `src/devforge/lib/_review/_ui_scope.py` is the sole consumer of the nature signal for UI-ness — it reads `PROJECT_NATURES` from `.devforge/project-config.json` against `_UI_NATURES = frozenset({"web", "mobile", "desktop"})`, returns `{is_ui, platform_hint, natures, reason}`, and defaults `is_ui=True` on a missing or unreadable config and on an absent or empty field — and reusing that existing signal with its documented recall bias, rather than introducing a new config key, is the direction the maintainer approved; the reachable win is bounded to projects whose natures clearly exclude UI (`cli`, `library`, `infra`, `data`), since a monorepo carrying `web` among its natures is still asked, correctly. Whether any nature gate may reach 3.8 itself is open, and not a free edit: `constitute_helper forge-internal:verify-universal-defaults` compares the universal sections against the canonical `.devforge/templates/constitution.md` keyed on rule `name`, and `scripts/constitution-drift-check.sh` runs it — fixing only the intake asks is the alternative. Check overlap with plan 118 (the thin detection signal upstream of these same values) and plan 101 (F14, and its nature-scoped agent-pruning precedent).

## Origin

Maintainer request of 2026-09-25 — at initial framework setup it must be clear what type of project this is, because the design questions fire always, including where they are not needed. Not a consumer incident: no run is cited, nothing is measured, and the unconditional asks above are read from the command specs rather than observed in a run.
