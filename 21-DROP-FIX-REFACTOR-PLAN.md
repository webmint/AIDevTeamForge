## Why DROP, not rework (the anti-future-hallucination payload)

> **Note (2026-06-19):** D1 below is SUPERSEDED by `26-REINTRODUCE-FIX-PLAN.md` (D1 only). This section's reasoning is retained as the record for the `/refactor` drop and the cold-bug boundary, which both still stand. See plan 26 `## Why supersede plan 21 D1` for the D1 reversal.

`/fix` and `/refactor` are stale pre-pivot drafts at `src/_pending/commands/fix.md` (23.5K) and `src/_pending/commands/refactor.md` (25.3K). Neither is emitted, so neither exists in any installed target project — yet both are *described as live* across the consumer overlay (`src/CLAUDE.md`), crash-recovery prose, the verification-boundary line, and several agents. That described-but-absent state is exactly the future-hallucination seed the repo `CLAUDE.md` "Pre-empt future-session hallucination" rule warns about: a fresh session reading the consumer overlay would believe `/fix` and `/refactor` are shipping commands.

The decision to DROP rather than rework rests on a structural finding from the design discussion. It is recorded here in full so that no future session — seeing the phantom references being removed — mistakes the removal for an oversight and "restores" `/fix`.

### §1 — Every fast-path shape duplicates a piece the full chain already owns

Both commands are "fast paths" that bypass the spec → plan → breakdown → implement pipeline. Four distinct fast-path shapes were considered, and each duplicates something the full chain already owns:

- **Rework the draft as a standalone 2.0 command** → duplicates `/implement`'s back half (scope-aware verify → review panel → forcing-functions gate → WIP commit → crash recovery). The draft would re-implement machinery the live `/implement` already owns.
- **A thin command on a shared engine** → the command itself becomes a wrapper duplicate (a second entry point over the same engine, kept in sync by hand).
- **A "mini task-set" routed into `/implement`** → duplicates the breakdown → implement task contract (a second producer of `/implement`'s input). "Minified but still duplication" — and small duplicates are the ones that silently go stale.
- **An `/implement --fix "desc"` ad-hoc mode** → duplicates research's diagnosis front AND overloads `/implement`'s single responsibility (drain a feature's approved tasks).

This is not four unlucky designs. The fast path's pieces ARE the full chain's pieces (diagnosis, execution, the task contract), so any fast path re-instantiates one of them. **The duplication-free option set has exactly two members: the full chain (accept the overhead), or hand-fix (no framework machinery).**

### §2 — /refactor is an even clearer drop than /fix

`/refactor` is squeezed by existing tools from BOTH sides:

- Its FRONT half (phase 1 "detect SOLID/DRY/KISS / dead-code / naming opportunities") duplicates `/audit`'s analysis — `/audit` already hunts system design + best practices + duplication adversarially across the codebase.
- Its BACK half (apply → verify → review → commit) duplicates `/implement`.

There is no slice of `/refactor` that neither `/audit` nor `/implement` already covers.

### §3 — The empirical trigger

A real testForge20 e2e (`specs/001-catalog-tab-order`) drove a one-line comparator fix through the full pipeline and produced ~10K words of research / spec / plan / breakdown artifacts. That over-ceremony is real. But:

- The fix itself was correctly minimal (plan 18 working — scope fidelity held).
- The genuinely valuable pieces already have homes: the subtle diagnosis belongs to `/research`; a 293-line regression test in a previously-untested package belongs to a one-off test-writing task / `qa-engineer`.
- A one-liner edit needs no LLM at all.

So the over-ceremony argument does NOT motivate a fast-path command — it motivates hand-fixing, with the valuable pieces routed to the tools that already own them.

### §4 — The replacement workflow for small bugs (post-removal guidance)

State this explicitly so a future session does not read the removal as "small bugs are now unsupported":

1. The developer **hand-fixes** the change.
2. Writes / updates the test as a single **one-off task** (driven by the diff + diagnosis, not a 12-AC spec).
3. Runs the project's **verify commands** (tsc / lint / build / test).
4. Reviews the diff with the built-in `/code-review` skill (or `/audit --uncommitted` for a heavier adversarial pass).
5. The periodic safety net for ungated hand-fixes is the existing **`/audit`** (the "second-opinion" sweep), NOT a per-fix command.

**Escalation rule:** if you cannot tell what the test should cover from the diff + diagnosis, the change is not a small fix — run the full chain.

### §5 — The honest cost (knowingly accepted)

Hand-fixes lose two things a command would have given:

- The forced **regression test / verify gate**.
- The clean **attributed commit + memory entry**.

`/audit` catches bugs in accumulated hand-fixes but NOT missing provenance. This is the knowingly-accepted tradeoff: the duplication tax of ANY fast path (§1) was judged worse than this loss.

The framework is a feature pipeline. Small fixes are hand-fixed and run through existing tools (§4). Do NOT build `/fix`, `/refactor`, a routing edge, or an `/implement` fix-mode. The duplication-free option set has exactly two members (§1); a fast path is not one of them.

No `_wip.py` logic change, no test-assertion change.
