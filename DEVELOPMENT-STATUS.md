# AIDevTeamForge — Development Status

## What This Is

A reusable spec-driven development template for Claude Code. Combines a structured intake flow (research → specify → plan → breakdown → execute → review → verify → summarize → finalize) with enforced quality gates, specialized agents, and automated hooks.

## What's Built

### Commands

Every promoted command is emitted to `.claude/commands/devforge/<name>.md` and invoked as **`/devforge:<name>`** — the `devforge/` path segment is the namespace, so no forge command can collide with a same-named bundled or plugin skill. Each command's on-demand reference files are emitted OUTSIDE the command scan, to `.devforge/command-refs/<name>/`, so they never surface as phantom `/<name>:references:*` menu entries. Sixteen commands are model-invocable; four keep `disable-model-invocation: true` and are human-typed only (`init-forge`, `generate-docs`, `configure`, `constitute`) — narrowed from seven by plan 93 on 2026-09-03. The emitted set is the `_PROMOTED` tuple in `scripts/emitters/claude.py`. Three entries below are NOT in it and are not emitted into consumer projects: `execute-task.md` and `refresh-docs.md` are historical (no source file remains for either — `/devforge:implement` superseded execute-task per plan 07), and `release.md` is this repo's own maintainer command at `.claude/commands/release.md`. ### Update System
- `update.sh` — Manifest-driven update script with 4 strategies: overwrite (template-owned), three-way merge via `git merge-file` (agents + CLAUDE.md), smart merge (JSON/text), copy-if-missing
- **Three-way merge**: stores baseline snapshots of substituted templates in `.claude/agents/.baseline/` and `.claude/.baseline/`. On update, computes diff (baseline → new template) and applies it to current file — preserves all project customizations while propagating template improvements
- **Placeholder substitution**: delegates to `configure_helper substitute-file` (the single source of truth shared with `/devforge:configure`'s renderer — knows the singular↔plural aliases and composed `PACKAGE_STACKS` table); the merge gates on the verb's exit code rather than a raw `{{...}}` grep, so a legitimate `{{UPPERCASE}}` identity passthrough no longer false-skips a file while genuinely unresolved placeholders still skip it (prevents destroying agents with broken config values)
- `.devforge/project-config.json` — Machine-readable config written by `/devforge:configure`, stores all template variable values (including `TYPE_CHECK_COMMAND`, `LINT_COMMAND`, `COMMIT_ATTRIBUTION`) for `update.sh` placeholder substitution. The model keys — `CLAUDE_TIER_THINK` / `CLAUDE_TIER_DO` / `CLAUDE_TIER_VERIFY` / `CLAUDE_TIER_SECURITY` and their `CLAUDE_EFFORT_*` siblings — live in the same file but are **not** placeholder-substituted: they are read by `configure_helper apply-models`, which rewrites the `model:` / `effort:` frontmatter of `.claude/agents/*.md` **and of the eight mapped `.claude/commands/devforge/*.md`** directly
- `.claude/template-manifest.json` — Defines file ownership categories and update strategies; self-updates (template-owned)
- Config rebuild: when `.devforge/project-config.json` is missing, the update script rebuilds it from `.devforge/configure.yaml` via `configure_helper render-config` before substituting (replaces the retired `CLAUDE.md`-scraping migration)
- Constitution-drift check: `update.sh` (before the equal-version bail) and `install.sh`'s brownfield "leaving as-is" branch source `scripts/constitution-drift-check.sh` to compare an already-constituted target's universal constitution sections + forcing-function config keys against the canonical defaults; WARN-only and fail-soft (never mutates `constitution.md`/`constitute.json`), telling the user to re-run `/devforge:constitute`; greenfield silent-skips
- Repair guard: after the version read and the constitution-drift check (whose ordering is preserved), `update.sh` computes install completeness — `.devforge/lib` exists AND holds at least one top-level executable `*_helper` file — and on INCOMPLETE warns loudly and forces the apply, so a consumer tree carrying every VERSIONED artifact but none of the gitignored/untracked CODE dirs (plans 56 + 63) repairs itself. Deliberately version-independent: an incomplete install whose version is merely older would otherwise skip the equal-version bail and die at the apply confirmation instead. No new copy logic — the `templateOwned` apply loop already creates missing files; `--dry-run` exits before the apply and still changes nothing. `install.sh` now stamps `.claude/template-version` at the end of a successful **full** install (reading `.version` via `$PY_CMD`, fail-soft), so a fresh install's first update reports a known version instead of `(unknown)` and no longer suppresses the changelog-excerpt block; the `--only` surgical path does not stamp, by construction
- Non-interactive runs: a complete, up-to-date target without `--force` exits 0 as a no-op; a complete target on a differing version without `--force` prints a refusal on stderr and exits 1. Both previously died at an unguarded `read -r confirm` under `set -euo pipefail` — exit 1 with no `Aborted.` line and a dangling `[y/N]` as the only diagnostic
- Install-time preservation: `install.sh`'s bulk `cp -R` preserves an existing `.devforge/memory.md` and `.devforge/project-config.json` via a `_PRESERVE` loop (copy-not-move, with a pre-existing-backup check; `.devforge/*.preserve` is gitignored). Neither file can join the adjacent stray-user-state guard — that loop asserts a file must NOT exist in the framework source tree, and both genuinely ship as templates. `update.sh` can rebuild `project-config.json` from `.devforge/configure.yaml`; `install.sh` has no such path, which is why it must not clobber it

## Key Design Decisions

1. **User's workflow is primary** — spec-kit ideas adapted to serve hard gates + agents, not replace them
2. **Hard gates at every phase transition** — spec, plan, breakdown all require explicit user approval
3. **Per-feature storage** — everything in one feature directory, with tasks as individual numbered files in its `tasks/` subfolder. Two directory shapes coexist permanently (plan 91): `specs/<YYYY>/<MM>/<leaf>/` allocated at intake, and `specs/NNN-feature-name/` for directories allocated before that layout — every resolver reads both, nothing migrates
4. **Sequential numbering — tasks** — task files are numbered 001, 002... within their feature. Feature directories were numbered the same way until plan 91 replaced the number with the allocation month plus a ticket-or-slug leaf; task numbering is untouched by that change
5. **All agents as templates, `/devforge:configure` prunes** — `install.sh` generates the full agent set from `src/agents/*.md`; `/devforge:configure` prunes `.claude/agents/` to the project's natures
6. **Universal constitution rules pre-populated** — SOLID, DRY, KISS, error handling, code quality, workflow rules all built-in; `/devforge:constitute` preserves these `[universal]` sections verbatim and only populates `[project-specific]` sections
7. **Two-layer documentation** — implementing agents write inline docs (JSDoc/docstrings) as part of code; code-reviewer verifies inline docs per-task; tech-writer generates feature-level docs in `docs/` at `/devforge:finalize` time (once per feature, not per task). (the `/refresh-docs` incremental-refresh idea was closed OUTDATED — plan 28)
8. **Greenfield support** — all commands work for empty/new projects
9. **Check before build** — must search codebase for existing utilities before creating new ones
10. **Doc generation for existing projects** — `/devforge:generate-docs` builds the `docs/` knowledge base (concern → package → project tiers) for all agents
11. **Wrapper mode for client-invisible AI** — template wraps around existing project folder; zero Claude traces in the client's repo
12. **Cross-task contracts prevent silent drift** — each task declares Expects/Produces; preconditions catch upstream semantic errors before they compound, postconditions verify the task delivered what downstream tasks need
13. **Configurable AI attribution** — commits default to no Claude/AI mention; opt-in via the `COMMIT_ATTRIBUTION` config field that `/devforge:configure` writes. Rule stored in CLAUDE.md and enforced by all commit-creating commands

A command's `model:` is a **turn-scoped override**: it applies for that command's turn and the session model resumes afterwards. ### Context Maintenance (Phase 5.2)
- `/devforge:implement` maintains session state + memory after each task (crash-recoverable via the `.devforge/wip.md` marker)
- Writes a fixed-size (~40 line) sliding window to `.claude/session-state.md` with current progress, recent decisions, and modified files
- Three-tier context health check: light (no action), moderate (optional /compact), heavy (strongly recommend /compact)
- Session state is gitignored — it's a runtime artifact, not project state
- CLAUDE.template.md updated with rule 13 (session state) and Session Continuity section

### Crash Recovery (Phase 0 + WIP Checkpoints)
- `/devforge:implement` creates a WIP marker (`.devforge/wip.md`) and git checkpoint commits during execution
- Recovery Check (owned by `src/commands/implement/references/crash-recovery.md`) detects interrupted sessions and offers 4 options: resume, rollback+retry, rollback+skip, keep manual. WIP markers include a `Command` field identifying which command was interrupted, to prevent cross-command recovery confusion
- Git `[WIP]` commits preserve partial work at each phase. For `/devforge:implement`: WIP commits accumulate across tasks and are squashed by `/devforge:finalize` using `git merge-base`
- All workflow commits use scoped `git add` (specific files only, never `git add -A`) to prevent accidentally committing secrets or unwanted files
- `wip.md` is gitignored — only exists during active task execution
- In wrapper mode, WIP marker includes `## Source Repo Checkpoint` section; Phase 0 recovery also rolls back source repo WIP commits
