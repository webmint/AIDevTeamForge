# AIDevTeamForge — Development Status

## What This Is

A reusable spec-driven development template for Claude Code. Combines a structured intake flow (research → specify → plan → breakdown → execute → review → verify → summarize → finalize) with enforced quality gates, specialized agents, and automated hooks.

## What's Built

### Commands

Every promoted command is emitted to `.claude/commands/devforge/<name>.md` and invoked as **`/devforge:<name>`** — the `devforge/` path segment is the namespace, so no forge command can collide with a same-named bundled or plugin skill. Each command's on-demand reference files are emitted OUTSIDE the command scan, to `.devforge/command-refs/<name>/`, so they never surface as phantom `/<name>:references:*` menu entries. Seventeen commands are model-invocable; four keep `disable-model-invocation: true` and are human-typed only (`init-forge`, `generate-docs`, `configure`, `constitute`) — narrowed from seven by plan 93 on 2026-09-03. The emitted set is the `_PROMOTED` tuple in `scripts/emitters/claude.py`. Three entries below are NOT in it and are not emitted into consumer projects: `execute-task.md` and `refresh-docs.md` are historical (no source file remains for either — `/devforge:implement` superseded execute-task per plan 07), and `release.md` is this repo's own maintainer command at `.claude/commands/release.md`. See `63-SKILL-COLLISION-SUPPRESSION-PLAN.md` and `93-MODEL-INVOCATION-CARVE-OUT-NARROWING-PLAN.md`.

### Update System
- `update.sh` — Manifest-driven update script with 4 strategies: overwrite (template-owned), three-way merge via `git merge-file` (agents + CLAUDE.md), smart merge (JSON/text), copy-if-missing
- **Three-way merge**: stores baseline snapshots of substituted templates in `.claude/agents/.baseline/` and `.claude/.baseline/`. On update, computes diff (baseline → new template) and applies it to current file — preserves all project customizations while propagating template improvements
- **New-agent delivery**: an agent in the framework's current roster that the install's agent snapshot does not list is new, and the update installs it into `.claude/agents/` and adds it to the snapshot — only when `configure_helper decide-agent --file <source>` answers `keep`: its `applies_to` is `["all"]`, overlaps the install's `project_natures`, or is missing or unparseable — the rule `/devforge:configure`'s `prune-agents` applies — or the install has no natures set. A `drop` writes neither file, so a later nature change still delivers the agent, and any verb error keeps it (fail-open). An agent the user pruned via `/devforge:configure` is not new — the snapshot still lists it — so the update does not reinstall it (`101-NON-WEB-STACK-READINESS-PLAN.md`; build-verified by scratch update runs, NOT consumer-validated — no consumer incident, nothing measured, and the consumer e2e on a first real Unity project DEFERRED and NOT run)
- **Placeholder substitution**: delegates to `configure_helper substitute-file` (the single source of truth shared with `/devforge:configure`'s renderer — knows the singular↔plural aliases and composed `PACKAGE_STACKS` table); the merge gates on the verb's exit code rather than a raw `{{...}}` grep, so a legitimate `{{UPPERCASE}}` identity passthrough no longer false-skips a file while genuinely unresolved placeholders still skip it (prevents destroying agents with broken config values)
- `.devforge/project-config.json` — Machine-readable config written by `/devforge:configure`, stores all template variable values (including `TYPE_CHECK_COMMAND`, `LINT_COMMAND`, `COMMIT_ATTRIBUTION`) for `update.sh` placeholder substitution. The model keys — `CLAUDE_TIER_THINK` / `CLAUDE_TIER_DO` / `CLAUDE_TIER_VERIFY` / `CLAUDE_TIER_SECURITY` and their `CLAUDE_EFFORT_*` siblings — live in the same file but are **not** placeholder-substituted: they are read by `configure_helper apply-models`, which rewrites the `model:` / `effort:` frontmatter of `.claude/agents/*.md` **and of the eight mapped `.claude/commands/devforge/*.md`** directly
- `.claude/template-manifest.json` — Defines file ownership categories and update strategies; self-updates (template-owned)
- Config rebuild: when `.devforge/project-config.json` is missing, the update script rebuilds it from `.devforge/configure.yaml` via `configure_helper render-config` before substituting (replaces the retired `CLAUDE.md`-scraping migration)
- Constitution-drift check: `update.sh` (before the equal-version bail) and `install.sh`'s brownfield "leaving as-is" branch source `scripts/constitution-drift-check.sh` to compare an already-constituted target's universal constitution sections + forcing-function config keys against the canonical defaults; WARN-only and fail-soft (never mutates `constitution.md`/`constitute.json`), telling the user to re-run `/devforge:constitute`; greenfield silent-skips. The universal-section comparator, `constitute_helper forge-internal:verify-universal-defaults`, keys each rule on its identity `name` — the name `seed-universal` writes on every canonical rule — so a dropped or replaced universal rule is reported on every update until reverted, an added one carries no name and is not compared, and a state constituted before rule identities gets one `PRE_IDENTITY` line asking to re-run `/devforge:constitute`. Before `104-UNIVERSAL-SECTIONS-INTEGRITY-PLAN.md` it compared a heading against the four-value rule-tag enum and reported every universal rule MISSING even for an install matching the canon exactly, so the drift plans 86 and 89 (2.0.10) and plan 99 (2.0.12) told consumers to expect was indistinguishable from that artifact; whether any install also had real drift is NOT established. Evidence: the comparator defect was reproduced on a scratch state built through the real CLI, never a consumer incident, and nothing was measured on any consumer. **Build-verified, NOT consumer-validated**
- Repair guard: after the version read and the constitution-drift check (whose ordering is preserved), `update.sh` computes install completeness — `.devforge/lib` exists AND holds at least one top-level executable `*_helper` file — and on INCOMPLETE warns loudly and forces the apply, so a consumer tree carrying every VERSIONED artifact but none of the gitignored/untracked CODE dirs (plans 56 + 63) repairs itself. Deliberately version-independent: an incomplete install whose version is merely older would otherwise skip the equal-version bail and die at the apply confirmation instead. No new copy logic — the `templateOwned` apply loop already creates missing files; `--dry-run` exits before the apply and still changes nothing. `install.sh` now stamps `.claude/template-version` at the end of a successful **full** install (reading `.version` via `$PY_CMD`, fail-soft), so a fresh install's first update reports a known version instead of `(unknown)` and no longer suppresses the changelog-excerpt block; the `--only` surgical path does not stamp, by construction
- Non-interactive runs: a complete, up-to-date target without `--force` exits 0 as a no-op; a complete target on a differing version without `--force` prints a refusal on stderr and exits 1. Both previously died at an unguarded `read -r confirm` under `set -euo pipefail` — exit 1 with no `Aborted.` line and a dangling `[y/N]` as the only diagnostic
- Post-update advisories: `update.sh` sources `scripts/post-update-checks.sh` and calls its two WARN-only, fail-soft checks just before the `--dry-run` exit and again last, after the `Update complete` report; neither mutates user files. `forge_check_config_completeness` (only when a `project-config.json` exists) runs the template's `configure_helper verify` and lists each violation — an update never re-renders an existing `project-config.json`, so keys a newer configure schema adds stay missing until `/devforge:configure` is re-run; the warning adds that a model tier runs on the session's model (`inherit`) only when a `CLAUDE_TIER_*` key is reported absent or null. `forge_check_precommit_hook` resolves the active hook through `git rev-parse --git-path hooks/pre-commit` and, when that file carries the forcing-functions hook's marker line but differs from the shipped template, prints the re-copy command — `/devforge:constitute` installs the hook as a copy, and the update refreshes only `.devforge/templates/git-hooks/`
- Install-time preservation: `install.sh`'s bulk `cp -R` preserves an existing `.devforge/memory.md` and `.devforge/project-config.json` via a `_PRESERVE` loop (copy-not-move, with a pre-existing-backup check; `.devforge/*.preserve` is gitignored). Neither file can join the adjacent stray-user-state guard — that loop asserts a file must NOT exist in the framework source tree, and both genuinely ship as templates. `update.sh` can rebuild `project-config.json` from `.devforge/configure.yaml`; `install.sh` has no such path, which is why it must not clobber it

## Key Design Decisions

1. **User's workflow is primary** — spec-kit ideas adapted to serve hard gates + agents, not replace them
2. **Hard gates at every phase transition** — spec, plan, breakdown all require explicit user approval. The approval questions are explicit, and a reply that picks nothing never approves; the `Approved` status on `spec.md` / `plan.md` is written when the next command runs (implicit approval by invocation, kept by `98-DELEGATED-REPLY-ATTRIBUTION-PLAN.md` D5)
3. **Per-feature storage** — everything in one feature directory, with tasks as individual numbered files in its `tasks/` subfolder. Two directory shapes coexist permanently (plan 91): `specs/<YYYY>/<MM>/<leaf>/` allocated at intake, and `specs/NNN-feature-name/` for directories allocated before that layout — every resolver reads both, nothing migrates
4. **Sequential numbering — tasks** — task files are numbered 001, 002... within their feature. Feature directories were numbered the same way until plan 91 replaced the number with the allocation month plus a ticket-or-slug leaf; task numbering is untouched by that change
5. **All agents as templates, `/devforge:configure` prunes** — `install.sh` generates the full agent set from `src/agents/*.md`; `/devforge:configure` prunes `.claude/agents/` to the project's natures
    - The same keep/drop rule applies at delivery since 2026-09-23 (`101-NON-WEB-STACK-READINESS-PLAN.md`): `update.sh` delivers a new framework agent to an existing install only when the rule keeps it; an install with no natures set still receives it, and any error keeps it (fail-open). No consumer incident, nothing measured, and the consumer e2e on a first real Unity project is DEFERRED and NOT run. **Build-verified, NOT consumer-validated**
6. **Universal constitution rules pre-populated** — SOLID, DRY, KISS, error handling, code quality, workflow rules all built-in; `/devforge:constitute` seeds these `[universal]` sections verbatim with `constitute_helper seed-universal` — from `.devforge/templates/constitution.md`, the canonical copy `install.sh` ships and `update.sh` refreshes — and composes only the `[project-specific]` sections. A user can still drop or replace a seeded rule (`drop-rule` / `drop-section`), and the update-time drift check then reports it on every update until reverted (`104-UNIVERSAL-SECTIONS-INTEGRITY-PLAN.md`). Evidence: one defect (the forcing-functions block's label colliding with the constitution's own sub-section number) observed once by a user in a real run; four reproduced on a scratch state built through the real CLI, not consumer incidents; two found by reading; nothing measured on any consumer. **Build-verified, NOT consumer-validated**
7. **Two-layer documentation** — implementing agents write inline docs (JSDoc/docstrings) as part of code; code-reviewer verifies inline docs per-task; tech-writer generates feature-level docs in `docs/` at `/devforge:finalize` time (once per feature, not per task). (the `/refresh-docs` incremental-refresh idea was closed OUTDATED — plan 28)
8. **Greenfield support** — all commands work for empty/new projects
9. **Check before build** — must search codebase for existing utilities before creating new ones
10. **Doc generation for existing projects** — `/devforge:generate-docs` builds the `docs/` knowledge base (concern → package → project tiers) for all agents
11. **Wrapper mode for client-invisible AI** — template wraps around existing project folder; zero Claude traces in the client's repo
12. **Cross-task contracts prevent silent drift** — each task declares Expects/Produces; preconditions catch upstream semantic errors before they compound, postconditions verify the task delivered what downstream tasks need
13. **Configurable AI attribution** — commits default to no Claude/AI mention; opt-in via the `COMMIT_ATTRIBUTION` config field that `/devforge:configure` writes. Rule stored in CLAUDE.md and enforced by all commit-creating commands
14. **Tiered models, configurable per project, with NO framework default** — agents carry a `model_tier` in four values (think — api-designer, architect, devils-advocate, spec-formalizer; do — the ten implementation agents; verify — the five review/test agents; security — `security-reviewer` alone) and the generator emits `model: inherit` plus a `model_tier:` line. **The framework chooses no model anywhere**: `inherit` selects the main conversation's model, and every emitted command ships with no `model:` line at all. `/devforge:configure` Q11 asks a model and an effort level per tier across four calls, and `configure_helper apply-models` rewrites the `model:` / `effort:` frontmatter of `.claude/agents/*.md` **and of eight mapped commands** (`specify`/`plan`/`grill`/`breakdown` → think, `implement`/`fix` → do, `review`/`verify` → verify) from `CLAUDE_TIER_*` / `CLAUDE_EFFORT_*` — at setup Phase 5.4 and again on every `update.sh`, which **re-applies after the promoted-command re-emit** (that step overwrites command files) and **normalizes the snapshot before the agent merge** so a configured install's line does not conflict. A command's `model:` is a **turn-scoped override**: it applies for that command's turn and the session model resumes afterwards. The choice is **version-free**: Claude Code's `opus` / `sonnet` / `haiku` / `fable` aliases, offered only where a startup probe found the session can dispatch them, with a free-text arm for pinning a full model ID. **Effort is not validated against the model** — an unsupported level falls back silently, by Claude Code's documented behavior — and **a model excluded by an organization's allowlist is silently not used**
    - Was write-only until 2026-09-03: Q11's answers were stored and read by nothing, and the emitted `model:` was fixed at generation time (`92-AGENT-MODEL-AND-EFFORT-CONFIG-PLAN.md`)
    - The framework's own defaults were removed 2026-09-04 (`94-MODEL-OVERRIDE-AND-NO-DEFAULTS-PLAN.md`): the static tier map and `security-reviewer`'s `model_pin` are gone, `security` became the fourth tier with its own question, and an unanswered tier now inherits the session model rather than taking a value this repo picked. **Build-verified, NOT consumer-validated**
15. **Three-way merge for updates** — `update.sh` uses `git merge-file` with baselines to apply only template diffs, preserving all project customizations (setup-added items, custom sections, manual edits)
16. **AC verification is opt-in and project-conditional** — `/devforge:configure` asks if AC should be verified via browser (Chrome MCP), API calls, or code reading (the `ac_verification_mode` config field). Chrome MCP only installed for auto/browser-only projects. `/devforge:verify` Phase 2 launches the ac-verifier agent when enabled, with graceful fallback to code reading
17. **Per-task code review, feature-level review + verdict at epic level** — code-reviewer runs in `/devforge:implement`'s per-task four-reviewer panel (plan 17; panel-clean gates the per-task approve). `/devforge:review` owns the feature-level cross-task review (findings only); `/devforge:verify` owns the verdict — AC verification + assembled mechanical checks + the APPROVED/NEEDS WORK/REJECTED decision — and does NOT re-review
18. **Language-agnostic agent templates** — type safety rules use a `{{TYPE_SAFETY_RULES}}` placeholder that `/devforge:configure` substitutes based on detected language. No hardcoded TypeScript-specific items. Agent templates use `Inline docs` not `JSDoc`
19. **A reply that picks nothing is never the user's pick** — a reply that picks none of the offered options (a delegation such as "you decide" in any language, an evasive reply, or free text in the "Other" row that names no option) is never recorded, cited or acted on as the user's pick, and no option is taken because it is marked recommended. At a question that decides what the run does, the question is asked once more and a second such reply takes the option the command names for that reply — where it names none, the turn ends with nothing written; at a question that asks for content, the model supplies the answer, records it through the channel the command names for a model-supplied answer, and says it is its own choice. Emitted always-on as `CLAUDE.md` `### Never` item 7, with one sentence per open run-decision site naming its arm; recognizing a delegation is model judgment, not mechanical detection (`98-DELEGATED-REPLY-ATTRIBUTION-PLAN.md`). **Build-verified, NOT consumer-validated**
20. **Scope follows what the user sees** — minimality limits how a change is built, never which user-facing surfaces it covers. A surface shows the feature the user named only on cited user-visible identity evidence (the same title or heading; label, translation key or menu item; route; or tab or mode constant), and shared code or a shared data source is never that evidence, nor a reason to exclude. An evidenced surface is covered, excluded in the user's own words, or raised with the user; covering a surface takes an affected-area row and an acceptance criterion in the spec naming it, so only `/devforge:specify` covers one. When the model decides it there, the surface is covered unless the model can name what the user would see differently, every §6 exclusion the user did not state in their own words is recorded as `[excluded by the model] <item> (user sees: …)`, and a surface the model suspects but cannot evidence is deferred to a §8 open question rather than covered or excluded; at any other stage the model cannot cover an evidenced surface it decides, so it raises that surface and leaves it neither covered nor excluded. Emitted always-on as `CLAUDE.md` `### Always` item 17 and as one sentence appended to constitution §6.1 (the constitution outranks `CLAUDE.md`), with a feature-surface sweep in `/devforge:research` (Phase 2.4e), per-surface `scope_boundaries` decision points in `/devforge:specify`, a conditional `**Unconfirmed exclusions**:` line on `/devforge:plan`'s approval summary, and one sentence each in the architect and devils-advocate agents. Whether a surface shows the same feature stays model judgment: the identity evidence is model-cited and checked by nothing, and the sweep is a search step, not a gate (`99-SCOPE-FOLLOWS-USER-VISIBLE-BEHAVIOR-PLAN.md`; which stage covers, amended 2026-10-02 by `108-SCOPE-RULE-DOWNSTREAM-REGIME-PLAN.md` — a contradiction read out of this tree, no consumer incident recorded here, nothing measured). Evidence (plan 99): one observed instance, the discovery-side gap predicted, nothing measured. **Build-verified, NOT consumer-validated**
21. **Clarifying questions are asked in every mode** — `/devforge:specify`, `/devforge:plan` and `/devforge:breakdown` carry no auto-mode branch at all: every clarifying question, every escalation those phases raise and every approval gate is put to the user whichever Claude Code permission mode is on, and each of the three says so in one sentence, because auto mode nudges the model to keep working without stopping for clarifying questions *"though Claude still asks when your prompt or a skill explicitly relies on it"*. The framework's own mode signals are deleted with the branches (`detect-mode`, `--auto`, `DEVFORGE_AUTO_MODE`, the `mode` state key, both specify mode gates), and `set-dp-default-applied` now requires `--delegated-reply` on EVERY call, so a model-supplied default always carries the reply that handed the decision back. Alongside it: `/devforge:plan` gains an acceptance-criteria-conflict route (exactly one Risk Assessment row per conflict, no Key Design Decision picking a side, a conditional `**AC conflicts**:` summary line) and routes a file serving a user-facing surface the spec neither covers nor excludes to the architect's sub-question-6 escalation instead of noting it as an addition discovered during planning; `/devforge:breakdown` gains one shared escalation route before its Halt rule; a question round becomes ONE `AskUserQuestion` call with independent questions always bundled; specify's Step 5.1 lists every §8 deferral; and research check 12b's message names the whole `Phase 2.4 / 2.4b / 2.4c / 2.4e` family whose findings satisfy it. The ask sentence is model judgment set against a documented harness nudge — only specify has a mechanical backstop, and it forces a quoted reply to exist, not to be real — and an unattended auto-mode run now stops at its first question (`100-SCOPE-RULE-FOLLOW-UPS-PLAN.md`). Evidence: NO incident — five of the six items are gaps found by reading during plan 99's build, the sixth is a maintainer directive, and nothing was measured. **Build-verified, NOT consumer-validated**
22. **The project sets its command ceiling, and its natures decide which agents land** — the ceiling on each type-check / lint / build / test command that `implement_helper verify-touched` runs for `/devforge:implement`, `/devforge:verify` and `/devforge:fix` is per-project configuration: the `command_timeout` field, rendered as `COMMAND_TIMEOUT`, whose default `"120"` is the module constant every install used before, so an absent or invalid value bounds commands exactly as before. It is default-only like `regression_gate` — no prompt, no detection; set with `configure_helper set-command-timeout <seconds>` and then `render-config` — and a re-run of `/devforge:configure` resets both keys to their defaults. The ceiling changes WHEN a command is killed, never how a failure is classified: a timeout or any other non-code failure still enters self-repair, and the regression gate stays disarmed for a project whose suite needs compiled artifacts, by decision (`REGRESSION_GATE=off`). A new builder, `game-engineer` (`applies_to: ["game"]`), gives game-nature projects a code-writing owner named in `/devforge:breakdown`'s Agent Assignment table, and a nature-scoped agent reaches an install only where its natures apply — at `/devforge:configure`, whose `prune-agents` drops it, and now at update, where `update.sh` applies the same keep/drop rule through `configure_helper decide-agent` once per new agent; an install with no natures set still receives it, and any error keeps it (fail-open). Nothing measures the agent's competence, and its installation rests on `/devforge:configure` writing the literal nature `game` (`101-NON-WEB-STACK-READINESS-PLAN.md`). Evidence: NO consumer incident, none claimed, nothing measured — Phase 0 closed by delegation, with the model choosing every outcome, and the consumer e2e on a first real Unity project is DEFERRED and NOT run. **Build-verified, NOT consumer-validated**
23. **The per-task gate is human-centric by design, and `/devforge:implement` has no unattended form** — tasks drain one at a time in dependency order, and each stops at the PHASE 7 hard gate (Stage A decision questions if any were recorded, then a Stage B read of the diff, after which the orchestrator ends its turn and the user's reply opens the next); nothing the task produced commits before `approve`, and no `N`, range, `all` or auto-approve form exists. The maintainer's grounds (2026-10-03): one task's diff is a load a reader can hold and read well, a whole feature's at once is not; and in a dependency-ordered drain a defect found in task N is repaired before task N+1 builds on it, which no after-the-fact review can do. The cost is latency, not quality, accepted by decision: `RESEARCH-2026-09-27-V2-COST-DIAGNOSIS.md` records 75 stops and 76 h idle in one implement run (its L6), and in a 3-task run 5 stops and 7 h 10 min of human time in a 10 h 48 min wall, *"almost all of it idle between approvals"*. `110-IMPLEMENT-AUTO-APPROVE-PLAN.md` is DECLINED 2026-10-03 on this principle, its text kept as the record of the argument; the research file's L6 and §2.5 item 1 (build plan 110 first, the largest stop reducer) stand as a dated record; the stub `124-PIPELINE-COST-REDUCTION-PLAN.md`'s item 0, a dependency on plan 110, is re-pointed when that plan is authored; `111-WIP-MARKER-CONTRACT-PLAN.md`'s D5 is moot. Open, unowned and with no plan file as of 2026-10-03: `/devforge:breakdown` authors a per-task `Review checkpoint` field and reports a `**Review checkpoints**:` count, but `/devforge:implement` reads the field in no branch (plan 110's F8, 2026-09-23), so with every task a stop that count overstates selectivity. The remedy lanes named with the decision — a notification when the loop reaches a gate, and the gate's presentation (verify result, panel verdict, Stage A decisions) persisted to disk at the gate, before `approve`, for a returning reader (after `approve`, `.devforge/session-state.md` keeps the last three decisions and the task's Completion Notes carry `mark-complete --notes`) — exist nowhere in `src/` and have no numbered plan; any future cost reduction at this gate keeps the per-task human read. Evidence: one maintainer decision stated in conversation on 2026-10-03; two measured implement runs, both the research file's; nothing measured on reading quality; nothing built, so nothing to consumer-validate

### Crash Recovery (Phase 0 + WIP Checkpoints)
- `/devforge:implement` creates a WIP marker (`.devforge/wip.md`) and git checkpoint commits during execution
- Recovery Check (owned by `src/commands/implement/references/crash-recovery.md`) detects interrupted sessions and offers 4 options: resume, rollback+retry, rollback+skip, keep manual. WIP markers include a `Command` field identifying which command was interrupted, to prevent cross-command recovery confusion
- Git `[WIP]` commits preserve partial work at each phase. For `/devforge:implement`: WIP commits accumulate across tasks and are squashed by `/devforge:finalize` using `git merge-base`

- `wip.md` is gitignored — only exists during active task execution
- In wrapper mode, WIP marker includes `## Source Repo Checkpoint` section; Phase 0 recovery also rolls back source repo WIP commits
