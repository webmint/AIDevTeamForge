# 124 — Pipeline Cost Reduction Plan

**Created**: 2026-09-28
**Status**: Stub — problem statement and candidate levers only. The plan body (findings, decisions, phases) is to be authored. **Maintainer directive 2026-09-28: this plan is built AFTER every plan numbered 106–123 is built; it does not jump the numeric queue.**

## Problem

Measured on 2026-09-27 from local Claude Code transcripts (`RESEARCH-2026-09-27-V2-COST-DIAGNOSIS.md`, hereafter the research file; Part 1 §1 Method), a v2 pre-implement chain — `/devforge:research` through `/devforge:grill` — costs 2.3–3.7 h of framework and agent time plus 30–60 min of human answering, against ≈ 50 min for v1's research→breakdown (~40 min framework + ~10 min answering); its tokens are ≈ 260–400 k output and 60–100 M cache-read (+17 M agent cache-read) against v1's ≈ 160 k and 16 M. Python is not the cost: the Bash bucket is 1–3.5 min per v2 command run, under 5% of wall, and plan 70 measured helper cold start at ~80 ms per call. Per-turn cost is equal — 5–15 s of framework time per assistant turn on v2 against 8–17 s on v1 — so the cost is the count of turns (×2–4 per command) and of stops for the human (×3; research median 4 → 12), plus two mandatory commands v1 did not have, `/devforge:spec-check` (≈ 26 min) and `/devforge:grill` (≈ 65 min), about 1.5 h per feature. No dollar figure is given: the model mix differs between the two transcript populations (research file F7).

Where a turn's cost sits (research file Part 2 §2.1, medians): a v2 research run makes 92 tool calls; its 32 helper calls return 7 KB (0.3 KB per call), so helpers cost turns, not bytes, while its 45 CBM MCP calls return 196 KB of the run's 274 KB of tool-result bytes (72%). The model's own output is the largest context component — 91–144 k output tokens per research run against v1's 46 k — and the ~250 k-token cache-read at the median turn is ≈ 60 k of prose (research `main.md` ~50 k + `CLAUDE.md` ~9 k), ~70 k of tool results and ~130 k of accumulated own output. Assistant turns ≈ 2 × tool calls in both generations, so every helper call is also a narration turn; and the research file counts 28 instructions in `src/commands/research/main.md` and 37 in `src/commands/breakdown/main.md` that say "copy … VERBATIM into your next user-facing message", each putting a helper result into context twice (counted 2026-09-27 — the count moves with every edit of those files and with the grep pattern, so re-grep before relying on it). `/devforge:research` loads ≈ 50 k tokens of prose at invocation (bytes/4).

Three structural facts hold in the tree. First, state is written one field per call: `src/devforge/lib/_research/_cli.py` registers 61 `add_parser` verbs and `src/devforge/lib/_specify/_cli.py` 58, every setter takes its fields as per-field flags, and no verb accepts a phase's fields as one JSON or file payload (the path-shaped flags that exist, such as `--file-line` and `--handoff-path`, each carry a single value). Second, the enforcement knob the user answers gates nothing: `/devforge:configure` Q9 writes `workflow_enforcement` (`Strict` / `Moderate` / `Light`) through `configure_helper set-workflow-enforcement`, with options that describe gating ("approval gates at major milestones; smaller decisions auto-proceed"), yet no Python module outside `src/devforge/lib/_configure/` names the field — its only reader is `/devforge:constitute`'s prose composition of project-specific workflow sub-sections (`src/commands/constitute/main.md`; `src/commands/constitute/references/section-shapes.md`, "**Composition source**: extract project-specific workflow rules from `CONFIGURE_JSON.workflow_enforcement` value") — so neither `plan_helper verify-spec-check` nor `breakdown_helper verify-grill-ran` reads it. Third, the profiler cannot segment the transcripts this plan needs measured: `src/devforge/lib/_profile/_segment.py` compiles `_COMMAND_MARKER_RE` anchored with `^` and applies it with `.match()`, while real user messages of both generations begin with `<command-message>…` and carry `<command-name>` on the second line, so the primary segmentation signal never fires — every segment comes from the `*_helper` Bash fallback, v1 transcripts profile as one `(preamble)` per session, and model-invoked v2 commands are seen only through their helper calls (research file F9).

What the measured cost buys is unproven on outcome (research file F8 and Part 1 §3). On the frozen brownfield benchmark, v2's one run named the hidden second surface and wrote the correct AC requiring both surfaces to change, then failed the probe; the best v1 run passed per the benchmark report's narrative (its table records 0), the v2 run used a different model from all six v1 runs, and the plan-81 acceptance re-run has not happened. The report's own sentence on mass: "artifact volume varied 24×, test volume 14×, active time 17×, review depth from none to mutation-tested — none of it correlates with the outcome." The analysis advantage v2 did show sits in a small fraction of its mass — research file Part 2 §2.4 lists it: the emission matrix (research Phase 3, written at Step 4.5b), the Coupling decision point and the `set-scope --evidence` gate, the Phase 0.5 intake gate's echo-back, the Phase 2.4c helper-API surface enumeration (→ `declare-caller-total`), Rule 5 in `src/commands/plan/main.md` (the rejected-as-IMPOSSIBLE value-set rule), the six plan-81 inference rules, spec-check's subject resolution (plan 82) and the typed handoffs between stages — and every lever below is written to leave those intact. Research file §2.3 also finds that none of plans 106–123 touches the four levers that carry most of the measured cost: setter round-trips, CBM volume, the two gates and prose size.

## Candidate levers (from the diagnosis — recorded, not decided)

Each item names the research file's lever label (Part 2 §2.2, or F10 for item 8), the mechanism it would change, the predicted saving (item 8: the measured cost) and the plans it interacts with.

0. **Dependency, not a lever (L6, L4(b)).** Plan 110 (`--auto-approve` for `/devforge:implement`) lets a task whose `review_checkpoint` is `false` auto-approve under the flag, and is the largest stop reducer among the open plans — one measured implement run made 75 stops. Plan 123 targets the unconditional design-intake asks, which the research file prices at −1 stop in each of `/devforge:research`, `/devforge:discover` and `/devforge:specify` on non-UI projects. Both are numbered before this plan, so the directive above builds them first.
1. **One state write per phase (L1).** An `apply --from-json <path>` (or stdin) verb per helper that runs the validators the setters run and names the failing field, so a phase's fields are written once; read, verify and render verbs stay. Predicted: research −20–25 of its 92 tool calls with their narration turns, specify's heavy path −40–50 of its 63 helper calls. The batch validator must carry every per-setter gate — the research file names `set-scope --evidence`, `set-dp-default-applied --delegated-reply` and `record-intake-classification --kind` — because a batch that reports only "invalid" costs more turns than it saves. Interaction: plan 106 D3 (separating the two `--seeded-by-upstream` producers), plan 107 D2 (a typed `--change-kind` on `specify_helper record-affected-area`) and plan 109 D4 (thin verbs on both intake helpers) each add per-call surface documented at per-call sites in a command's `main.md`. Research file §2.5 sequenced the batch verb before them; under the directive above it lands after them and rewrites those sites — prose rework the maintainer accepted on 2026-09-28.
2. **CBM call budget in `/devforge:research` Phases 2.3–2.5b (L2).** A per-sweep call budget with a named fallback when it is hit; Phases 2.4, 2.4b and 2.4e made conditional on the previous phase's result and on `scope` / mode; Phase 2.4c (helper-API surface enumeration → `declare-caller-total`) and `trace_path` kept unconditional; the prescribed `search_code` calls pinned to `mode=compact`, `limit` 10 and `max_output_tokens` (measured: 26 calls and 129 KB per run at `limit` 30–60 on the benchmark install — half its CBM calls and two thirds of its CBM bytes — and 24 calls and 37 KB, 45% and 43%, on the newer-CBM client install, because Phase 2.3 forbids raw `Read` / `Grep` / `Glob` / `grep` / `find` / `cat` over source-file extensions and its CBM chain names `search_code` as the text search), and `get_code_snippet` / `trace_path` given an explicit `max_output_tokens` — which also retires `src/commands/research/main.md` Phase 2.4's sentence "The supported `search_code` argument is `pattern` only", stale against the live tool schema that exposes those parameters and against the recorded runs that already passed `limit` and `mode`; patterns deduplicated across sweeps; Phase 0.2's index-refresh output reused instead of re-queried; and whether that raw-read ban stays decided separately. Predicted: −30–50% of research context bytes. No budget may cut below completeness — the plan-81 inference rules need complete value sets, not sampled ones. Interaction: plans 113, 114 and 115 make CBM return data where it now returns nothing, so research bytes rise before this lever lands; research file §2.2 wanted the budget landed with them, and the directive above lands it after.
3. **Delete the `/devforge:research` Phase 2.1 cost gate (L4(a)).** Phase 2.1 asks `proceed` / `cancel` via `AskUserQuestion` on a CBM call-count estimate (one-package ≈ 15-30 calls up to cross-cutting ≈ 60-120) that the research file finds the user cannot act on, and the cancel arm's value is unmeasured. −1 stop per run; no forcing function touched.
4. **Bundle `/devforge:configure` Phase 4 (L5).** Q9, Q10, Q12 and Q13 in one `AskUserQuestion` call — four questions, the tool's cap ("each `AskUserQuestion` call supports 1-4 questions with 2-4 options each", https://code.claude.com/docs/en/agent-sdk/user-input) — the four Q11 alias probes in one subagent, and Q11 in two calls (think + do, verify + security) instead of four. This reverses Phase 4's "One AskUserQuestion per question, in order" rule; per-question delegation rules stay, and the bundle must account for Q12's conditional Q12.1–Q12.3 follow-ups (`src/commands/configure/references/q12-ac.md`). Predicted: about a third of configure's 14 stops, roughly −10 min answering per project. Interaction: plans 116, 117, 118, 120, 122 and 123 edit `/devforge:configure`; a project-type question, if plan 123 adds one, joins the same bundle.
5. **Policy-driven grill gate (L3).** A policy read in `breakdown_helper verify-grill-ran` — today the verb reads no policy field — taking `workflow_enforcement` from `.devforge/configure.yaml`: `Strict` = required (today's behavior for every value); `Moderate` / `Light` = `/devforge:breakdown` offers `/devforge:grill`, proceeds on decline and records the decline in the breakdown handoff. Q9 recommends `Strict` and saves it on a delegated answer, so a default install keeps today's gate. Predicted: up to ~1 h and ~26 M tokens per feature outside `Strict`. `/devforge:spec-check` stays required: plan 82's origin is an observed incident whose fix (subject resolution) lives inside spec-check, while plan 85's origin is recorded as a maintainer decision with "no incident behind this plan". `src/CLAUDE.md` states the grill gate as required in its workflow text, its `/devforge:grill` Command Details entry and its Hard Gates list; per research file §2.2, none of plans 106–123 touches either gate.
6. **Prose diet (L7).** One shared exit-2 recovery paragraph cited by name from each helper site, replacing the "copy stderr VERBATIM … then end the turn" paragraph repeated at nearly every site; verbatim echo only on exit-2 / BLOCKED paths and user-facing renders, an acknowledging line elsewhere; `research_helper render --out <path>` (no `--out` flag exists today) so the report never transits the model — the research file counts two `render` calls per research run (the Phase 3 preview and the Step 4.4 re-render with the real path) followed by a write of the bytes received. Predicted: prose −30–40% per command, research ≈ 50 k → ≈ 30 k tokens at invocation, one fewer `Write` turn per save. The verbatim convention exists so gate messages are not paraphrased, and it stays exactly there.
7. **Measure before and after.** Fix the `_COMMAND_MARKER_RE` anchor in `src/devforge/lib/_profile/_segment.py` first, so `profile_helper` resolves v1 and model-invoked v2 segments alike; then profile before and after each lever, and run the ablation from research file Part 1 §5 — the same v2 with grill and spec-check off and one state write per phase — beside the plan-81 acceptance re-run with the model pinned. If L1, L2, L5, L7 and plan 110 land, research file §2.5 predicts for research tool calls 92 → ~55, turns ≈ −40% and context bytes ≈ −50%; for implement, stops 75 → the number of tasks marked `**Review checkpoint**: Yes`; for the chain, −1 h under a non-`Strict` policy. Every saving in items 0–7 is predicted from static counts and the Part 1 medians, not measured; item 8's figures are measured on one feature (F10).
8. **Added by F10, 2026-09-28 (L9, L10).** A fresh session per pipeline command (L9): on the real-work install one session ran specify through implement without `/clear` and its cache-read per message grew from 276 k (first specify) to 580 k (plan) and stood at 457 k at implement, so every command after the first paid 4–8× the context a fresh session carries — quality-neutral by construction. A visible, bounded re-entry loop (L10): both grill runs there returned `RE-ENTER-UPSTREAM` targeting `spec`, so specify → spec-check → plan ran three times and grill twice for one feature — the two passes that ended in grill cost 112 and 159 min of main-thread time plus 92 and 168 min of agent time — and nothing told the user that cost before the pick; L10 changes plan 85's loop and needs a decision.

Not carried from the research file: L4(c), asking the research rubric in two rounds (−3 stops), which contradicts the rubric's stated one-dimension-per-turn forcing function and which the research file records as an open conflict with `/devforge:specify`'s bundling rule rather than a recommendation.
