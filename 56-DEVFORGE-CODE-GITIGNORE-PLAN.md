**Status:** **Phases 1–4 SHIPPED (working tree); RATIFIED 2026-07-10** (D1 accept; OQ-2 EXCLUDE `.devforge/template/`; OQ-1 assumed-install-step). Only **Phase 5 (consumer/testForge20 e2e) remains, user-driven.** On `develop-2.0-init`. This is a DECISION RECORD with an authored build path, not an active build: it recommends one mechanism but picks no winner unilaterally — the maintainer ratifies at Phase 0 before any code lands. **What/why:** the forge ships its runtime helper code into every consumer under git-TRACKED `.devforge/lib`/`bin`/`template`/`templates`, and the consumer's codebase-memory-mcp (CBM) knowledge graph indexes it — forge-internal code drowns the product code in every structural query. This plan gitignores AND untracks three of those four install-reproducible code directories — `.devforge/lib`/`bin`/`templates` (the node_modules model); `.devforge/template/` (singular) stays tracked (Phase 0.5 EXCLUDE — it is `update.sh`'s agent-merge baseline) — so CBM stops indexing them, directly extending plan 49's `.devforge/` runtime-state disposition work by adding a fourth, CODE, class.

## Problem — forge helper code pollutes the consumer's CBM graph

A consumer forge install (a real, git-tracked Electron app) has its CBM knowledge graph polluted by forge-internal code. Measured this session on that install's live CBM graph:

- Total graph: **10628 nodes / 738 files**.
- `.devforge/` forge-internal files: **300 files / 3898 nodes = 37% of the graph**.
- The app's real product code: only **78 `src/` files**.

So the forge's own helper code is more than a third of the graph the consumer's developers query for architecture views, caller traces, and structural search — it buries the 78 files of product code the graph exists to illuminate.

**Root cause.** The forge ships its runtime helper code into each consumer under `.devforge/`, and those files are git-TRACKED. CBM's filesystem walker honors `.gitignore` (proven this session: the consumer's gitignored `node_modules`/`out` produce 0 nodes) — but `.devforge/lib` and its siblings are tracked and NOT gitignored, so CBM walks and indexes them.

### The mechanism — empirical proof (verified this session on throwaway repos)

CBM version **`codebase-memory-mcp 0.6.1`**. Its `config` surface exposes ONLY `auto_index` + `auto_index_limit` — there is NO path-exclude / ignore-globs knob. Its `index_repository` tool has NO exclude parameter. Therefore the ONLY way to scope what CBM indexes is via ignore files honored during its filesystem walk.

Controlled test — two throwaway git repos, each with a git-tracked (`git add -f`) `.devforge/lib/_helper/pollutant.py` containing a real function, then CBM-indexed:

| Ignore file present | Content | `.devforge` nodes after index | Conclusion |
|---|---|---|---|
| `.ignore` | `.devforge/` | 6 (pollutant STILL indexed) | CBM 0.6.1 does NOT honor `.ignore` / `.rgignore` |
| `.gitignore` | `.devforge/` | 0 (pollutant NOT indexed) | CBM honors `.gitignore` EVEN for git-tracked files — its walker is pure pattern-match and never consults the git index |

Two consequences to record so no future session re-treads them:

- **"Keep files tracked but hide them from CBM via a CBM-only / `.ignore` mechanism" is IMPOSSIBLE in CBM 0.6.1** — there is no config knob and `.ignore` is not honored. Record as REJECTED-with-evidence and name it **dead-"C2"** so it is not re-proposed.
- **Only `.gitignore` works.** Gitignoring scopes CBM even while a file stays git-tracked — BUT leaving a file tracked-AND-gitignored is a fragile half-state: a NEWLY added helper file after an `update.sh` would be gitignored-and-untracked, so a consumer's normal `git add -A` silently skips it. Plan 49 eliminated exactly this half-state for runtime-state by ALSO untracking (`git rm --cached`). So the recommended mechanism mirrors plan 49: gitignore the code dirs AND untrack them, making `.devforge/` code install-reproducible (the node_modules model — regenerated by `install.sh` / `update.sh` `cp -R` on every run).

## Decisions

- **D1 (core) — mechanism: the node_modules model (gitignore + untrack the install-reproducible code dirs; reproducible on install).** RECOMMENDED, not decided — Phase 0 ratifies. Rationale:
  - Consistency with plan 49 — it kills the fragile tracked-and-gitignored half-state the same way plan 49 did for runtime-state (gitignore + `git rm --cached`).
  - Removes forge-internal noise from every consumer PR diff and shrinks the tracked tree.
  - Kills the CBM pollution DURABLY: `.gitignore` is honored on EVERY re-index, so even the forge's own `/generate-docs` CBM `index_repository` preflight (which walks from the repo root) stays clean going forward, not just on the one-time delete.

  **Rejected alternatives (recorded with evidence so they are not re-proposed):**
  - **dead-"C2" — keep files tracked, hide from CBM via a CBM-only / `.ignore` mechanism.** IMPOSSIBLE in CBM 0.6.1 (no config exclude knob; `.ignore` not honored — proof table above). Do not re-propose.
  - **"gitignore-but-leave-tracked".** Scopes CBM but leaves the fragile half-state: a helper added by a later `update.sh` is gitignored-and-untracked, so a consumer's `git add -A` silently skips it. This is precisely the half-state plan 49 eliminated for runtime-state — do not reintroduce it for code.

## Phase 2 — Extend `scripts/devforge-state-migrate.sh` with a recursive-dir untrack loop

Add a SEPARATE loop to `forge_migrate_devforge_state` (after the existing single-file loop at `scripts/devforge-state-migrate.sh:21-36` and the lock loop at `:39-43`) that recursively untracks the three code dirs (`.devforge/template/` EXCLUDED per Phase 0.5) so the now-present gitignore rules (Phase 1) take effect on existing installs:

```
for _dir in .devforge/lib .devforge/bin .devforge/templates; do
  if [ -n "$(git -C "$target_dir" ls-files "$_dir" 2>/dev/null | head -1)" ]; then
    git -C "$target_dir" rm -r --cached --quiet "$_dir" 2>/dev/null \
      && echo "  ~ untracked (now ignored): $_dir/" || true
  fi
done
```

The `_dir` list is the three dirs per Phase 0.5's EXCLUDE decision (`.devforge/template/` omitted — it stays fully tracked). The loop MUST preserve the script's three existing properties — FAIL-SOFT (the `|| true` + `2>/dev/null`, never aborts the installer), TRACKED-ONLY (the `ls-files … | head -1` non-empty guard skips a dir with nothing tracked), INSTALL-REPO-ONLY (`git -C "$target_dir"`, and `.devforge/` only ever exists in the install/wrapper root, never the source/product repo — plan 25 D5 / plan 49 D8) — and IDEMPOTENCE (a fresh install with nothing tracked is a clean no-op). It NEVER touches the VERSIONED root files: those sit at `.devforge/` root, outside every `_dir`, so `git rm -r --cached .devforge/lib` cannot reach them.

## Context for next session

This plan stops the forge's own runtime helper code from polluting a consumer's CBM knowledge graph. Measured on a real consumer install: `.devforge/` forge-internal files are 300 files / 3898 nodes = 37% of a 10628-node graph, burying the 78 `src/` files of actual product code. Root cause: the forge ships helper code into every consumer under git-TRACKED `.devforge/lib`/`bin`/`template`/`templates`, and CBM's walker (which honors `.gitignore` but has no other exclude knob in version 0.6.1) indexes tracked, un-gitignored files. Proven this session on throwaway repos: CBM 0.6.1 does NOT honor `.ignore` (6 pollutant nodes remained) but DOES honor `.gitignore` even for git-tracked files (0 nodes) — so "hide from CBM while keeping tracked via a CBM-only mechanism" is impossible (dead-"C2"), and the only durable fix is `.gitignore`. Because a tracked-and-gitignored file is a fragile half-state (a later `update.sh` adds a helper that `git add -A` then silently skips), the recommended mechanism mirrors plan 49: gitignore AND untrack the install-reproducible code dirs, making `.devforge/` code install-reproducible (the node_modules model). This is a SCOPE-EXTENSION of plan 49 — it adds a fourth, CODE, class to plan 49's `.devforge/` runtime-state disposition and reuses plan 49's machinery entirely (the `src/files/devforge.gitignore` template merged by `manifest.json` `union_lines`, and the shared `scripts/devforge-state-migrate.sh` `git rm --cached` migration). The ONE substantive code change is extending the migration script with a recursive-dir untrack loop (Phase 2); Phase 1 appends three lines to the ignore template; Phase 3 confirms no wiring change is needed; Phase 4 docs it. The untracked dirs are `.devforge/lib/`, `.devforge/bin/`, `.devforge/templates/` (three; `.devforge/template/` SINGULAR is EXCLUDED per the Phase 0.5 ratified decision — it stays tracked) — NEVER a blanket `.devforge/` (which would risk untracking the VERSIONED root files: `memory.md`, `constitute.json`, `spec-stamps.jsonl`, `init.yaml`, `configure.yaml`, `project-config.json`, `index.json`, `storage-rules.md`, all of which live at `.devforge/` root and must stay tracked). The key open tradeoff (OQ-1) is fresh-clone bootstrap: after untracking, a clone without a forge install/update lacks the helpers, so forge commands fail until install is re-run (the node_modules tradeoff — assumed onboarding step vs an explicit missing-helpers guard).
