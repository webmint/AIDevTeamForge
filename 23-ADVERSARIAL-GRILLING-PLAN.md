# 23 — `/grill` STANDALONE ADVERSARIAL DESIGN-GRILL PLAN (the design-level mirror of `/review`)

**Status:** Phase 0 (design lock) DONE 2026-06-17; on branch `develop-2.0-init`. The Phase-0 resolutions are recorded (OQ1 → dedicated `devils-advocate` agent; D10 removability constraint added; Phase 7 DEFERRED; OQ6 / OQ7 / OQ8 deferred to their build phase). No code/spec/agent is built yet — Phases 1–6 are unstarted (the build proceeds against the recorded resolutions); Phase 7 is the deferred user-driven standing gate.

Forge already separates *build* from *adversarial scrutiny* at the CODE level: `/implement` builds, then `/review` (a separate pipeline stage that attacks the ASSEMBLED artifact) and `/verify` (the stage that owns the verdict) scrutinize it — nobody embeds review inside `/implement`. **`/grill` is the design-level mirror of `/review`:** `/plan` builds the design, and `/grill` — a standalone, opt-in command positioned BETWEEN `/plan` and `/breakdown` — attacks the FINISHED design (`plan.md`, the chosen architecture) before `/breakdown` spends effort decomposing it.

The genuine gap it fills (verified against the live pipeline): `/plan` *compares* 2–3 alternatives and the architect picks a winner, but **nobody ever attacks the winner** — comparison is optimization, not refutation. And by charter the architect is an OPTIMIZER / decision authority, not an adversary: it is chartered to "decide HOW" and "own the final architectural call," and "every decision chain terminates with [it]" (`src/agents/architect.md` charter posture — the `name`/`description` block + the director framing + the Termination rule, verify on read; line numbers drift) — it is built to pick the best design and own that call, NOT to attack the design it just chose. Its consultation-framing rule even steers the specialist sub-questions it asks toward the minimal in-scope solution rather than robustness against excluded edges (`src/agents/architect.md:85` — "Frame the sub-question toward the MINIMAL in-scope solution, not robustness against excluded edges" — verify on read; line numbers drift), reinforcing the optimizer posture. So the chosen design is never adversarially attacked anywhere in the pipeline. `/grill` is the only place it is.

Cost-of-undo: `/grill` runs AFTER `/plan` is paid for but BEFORE `/breakdown → /implement` (where code, the real cost, is written), so killing a bad design here still saves all of implementation. It is structurally opt-in — the user CHOOSES to invoke it (exactly like `/audit`), so there is no auto-gate and no per-`/plan`-run cost.

## Settled decisions

These are user-chosen — settled, not open. (The `D` numbering is this plan's own.)

- **D1 — STANDALONE COMMAND.** `/grill` is a separate, opt-in pipeline stage positioned BETWEEN `/plan` and `/breakdown`, modeled structurally on `/review`. It is NOT a sub-phase embedded inside `/plan`. It attacks the COMPLETED `plan.md` artifact (the chosen design), not a mid-flight `/plan` phase. Rationale: forge already separates build from adversarial scrutiny at the code level (`/implement` builds; `/review`/`/verify` attack the assembled artifact) — `/grill` is the design-level mirror of that separation. A standalone command keeps the engine reuse clean (a third `_shared/` consumer alongside `/audit` + `/review`) and the opt-in structural (the user invokes it, like `/audit`).
- **D2 — OPT-IN BY CONSTRUCTION (no auto-gate).** `/grill` is user-invoked. It is RECOMMENDED for high-stakes plans (new architecture / new dependency / new external integration / new data model / security-relevant) and SKIPPED for mechanical ones — but the HUMAN decides by choosing to invoke it. There is NO deterministic stakes-detector, NO `Stakes:` architect-return signal, and NO forced gate on every `/plan` run. Rationale: a default gate manufactures fake objections on small features (the source article's own failure mode #1), so the value case requires narrowness; making opt-in STRUCTURAL (invoke-or-don't, like `/audit`) is the simplest possible honest narrowness — it cannot be "hardened" into an always-on check because there is no gate to harden.
- **D3 — The PLAN is the attack surface; the SPEC / discovery / research are reached via the RE-ENTER-UPSTREAM backward loop — no separate spec-grill.** The PLAN (the HOW / architecture) is the attack surface `/grill` dispatches its ensemble against. The upstream artifacts (`spec.md`, the discovery/research dossier) are NOT attacked by a separate upfront pass; instead the plan-grill discovers spec/discovery/research defects IMPLICITLY — a grounded plan attack whose defect is inherited from upstream is routed back to the nearest introducing stage via RE-ENTER-UPSTREAM (D9 / Refinement A). Rationale: a spec defect is only DEMONSTRABLE (not speculative) once it is tested against a concrete plan — the plan is the point where an upstream flaw becomes grounded — so a separate upfront spec-grill would attack the WHAT in the abstract, exactly where objections are weakest. The backward loop attacks the spec at the only point it can be grounded, which is why the previously-named `24-SPEC-SCOPE-GRILL-PLAN.md` follow-on is DROPPED as SUBSUMED — there is no separate spec-grill to build. (`spec.md` IS in the read-context — but as TRACE context for attribution, not as a second attack surface.)
- **D4 — KILL and RE-ENTER-UPSTREAM both loop back, human-controlled, with distinct counters.** Two recovery dispositions loop the pipeline backward, and they have DISTINCT bounded counters (do not conflate them):
  - **KILL → re-`/plan` (the kill-reloop counter).** A KILL disposition (D9) means the chosen design is fatally flawed and the recovery is a NEW design: the user re-runs `/plan` with a different approach, then optionally re-runs `/grill` on the new `plan.md`. Because `/grill` is user-invoked (D2), this loop is HUMAN-controlled — there is no AUTO machine ping-pong; the user decides whether to re-`/plan`, re-`/grill`, or escalate. Any bound on this loop is the human's judgment, not a machine cap.
  - **RE-ENTER-UPSTREAM → re-`/research`/`/discover`/`/specify` (the backward-compounding counter — Refinement A).** When the grounded defect is inherited from upstream (the "destroys-the-plan?" test returns YES — see D9), the recovery is re-entering the NEAREST upstream stage carrying a re-entry seed. This backward loop CAN compound (re-spec → re-plan → re-grill → re-spec …), so it has a MACHINE-bounded cap on the number of backward re-entry CYCLES. Each seed carries forward ALL prior findings (monotonic — strictly more informed each pass, never re-deriving a disproven flaw), so the loop is convergent by construction; after the cap, escalate to the human ("this feature may be intractable as framed — decide"). This cap is DISTINCT from D6 (which removes the per-run attack-ROUND ceiling — a single grill pass still has no internal round limit) and DISTINCT from the KILL kill-reloop above (human-driven, not machine-capped). Rationale: KILL recovery is a human cost-to-undo judgment at the `/breakdown` gate (theirs to drive); the backward upstream loop is the one place a machine cap is load-bearing, because without it a circular spec↔plan defect could ping-pong indefinitely.
- **D5 — Reuse the FULL `_shared/` engine like `/review`; the ONLY `/grill`-specific choice is an architect-excluded refuter priority list.** `/grill` runs the same attack → validate → refute (cross-examine) → partition → report flow `/review` runs, using the SAME `_shared/` verbs (`findings_schema`, `_validate`, `route_refutation`, `render_verify_brief`, `consume_verdicts`, `apply_verdicts`). The single divergence is the `route_refutation(findings, present_finders, priority=[code-reviewer, qa-reviewer, security-reviewer])` call — the architect REMOVED from the priority list (unlike `/audit`/`/review`, which include it), because the architect authored the design and must judge neither the attacks on it nor the refutation. `route_refutation`'s `priority` parameter is built for exactly this (`_verify.py:307`, `priority=None` → module constant; an explicit list is used as-is), so this is a PARAMETER choice, NOT an engine fork. Rationale: the engine already encodes the grounding + cross-examination discipline `/grill` needs, and `/audit` + `/review` are the precedent for a third `_shared/` consumer; excluding the architect from the priority list is the mechanism that keeps the proposer out of the judge's chair.
- **D6 — Strip the theater.** No fixed attack-round ceiling, no LLM-judged "equilibrium" stopping condition. The flow is a single attack → validate → refute → report pass (the same single-pass shape `/review` runs), terminated by the report write — not by a model self-assessing "no new valid objection remains." Rationale: an LLM-judged "nothing left to attack" is exactly the self-assessment LLMs are unreliable at; forge's structural safeguards — mechanical grounding (`_validate`) + a non-architect adversary ensemble + a non-author neutral refuter — are stronger guarantees than a named equilibrium, and cost less.
- **D7 — The new capability is the KILL disposition.** Every existing forge command is build-forward — it refines and proceeds. `/grill`'s KILL is the first design-time REJECT: a stage that can conclude "this approach is fatally flawed" and route the user back to re-design rather than improve forward. Rationale: a framework that can only refine an idea, never reject it, cannot catch a fatal design before code is written — which is the gap this plan closes.
- **D8 — Opt-in, never a mandatory gate (standing constraint).** The value case requires narrowness; a default gate on every `/plan` run manufactures fake objections on small features. Stated as a standing constraint so a future session does not "harden" `/grill` into an always-on check between `/plan` and `/breakdown`. With D2's structural opt-in there is no gate to harden — but a future session might be tempted to wire one; this decision forbids it.
- **D9 — Output = findings report + a recommended 4-way disposition (the classification test routes each surviving attack).** `/grill` writes `specs/[feature]/grill.md` containing the surviving grounded attacks (confirmed ∪ high-stakes `[CONTESTED]`, plus a dismissed / worth-a-glance appendix — mirroring `/review`'s report shape) AND a recommended **disposition: PROCEED / REVISE-PLAN / RE-ENTER-UPSTREAM / KILL** (Refinement A widened this from the earlier 3-way PROCEED / REVISE-PLAN / KILL). Unlike `/review` (pure findings-only, because `/verify` owns its verdict downstream), `/grill` carries a light disposition because there is no downstream design-`/verify` to own it; the disposition is a RECOMMENDATION and the human makes the final call at the existing `/breakdown` approval gate.
  - **PROCEED** — no surviving grounded attack threatens the design; run `/breakdown`.
  - **REVISE-PLAN** — a surviving grounded attack is PLAN-LOCAL: fixing it leaves the plan intact (a different HOW satisfies the same WHAT). The user re-runs `/plan` (or hand-patches) and optionally re-`/grill`s.
  - **RE-ENTER-UPSTREAM(→ nearest stage: spec | discovery | research, with a re-entry seed)** — a surviving grounded attack is INHERITED FROM UPSTREAM: no HOW survives the fix because the defect is in the WHAT (a flawed spec / discovery / research conclusion the plan faithfully implements). The recommendation routes back to the NEAREST stage where the defect was introduced (traced via `spec.md` + the dossier now in read-context — nearest-stage-first, NOT a blanket rewind to research), carrying a re-entry seed (the structured backward handoff that makes the re-run converge). See D4's backward-compounding counter for the loop bound.
  - **KILL** — the chosen design is fatally flawed at the HOW level and the recovery is a wholly NEW design: re-run `/plan` with a different approach (D4's kill-reloop).
  - **The classification test** (the operational core of the upgrade) is a TWO-QUESTION decision tree applied to each surviving grounded attack — stated here so the CLASSIFY step is implementable in `main.md` (Phase 3) and the `_report` verb (Phase 2) without reverse-engineering the disposition definitions:
    - **Q1 — "Does a different HOW (a re-plan against the SAME spec) fix the defect?"**
      - YES → **REVISE-PLAN** (plan-local).
      - NO (no HOW survives the fix — this is what "destroys the plan" means) → go to Q2.
    - **Q2 — "Would a corrected WHAT or grounding (re-`/specify` / re-`/discover` / re-`/research`) yield a viable design?"**
      - YES → **RE-ENTER-UPSTREAM** (→ nearest stage that owns the defect, with the re-entry seed).
      - NO (nothing rescues it — the feature is infeasible, unjustified, or should be bought not built) → **KILL**.
    - (PROCEED is the no-surviving-attack / all-accepted-as-risk case — outside this YES/NO tree.)
    KILL is therefore reached only when nothing — no HOW and no WHAT change — rescues the design; a fatal HOW with a viable alternative is REVISE-PLAN (Q1=YES), and a fatal HOW with no viable alternative but an upstream rescue is RE-ENTER-UPSTREAM (Q1=NO, Q2=YES). Rationale: a findings list with no recommended posture leaves the human to re-derive "is this proceedable, plan-local, upstream, or fatal" that the refutation + classification passes already established; the light disposition surfaces that conclusion without claiming a binding verdict. The PROCEED/REVISE/RE-ENTER/KILL labels are themselves a RECOMMENDATION — the human owns the call at the `/breakdown` gate.
- **D10 — REMOVABILITY is a design constraint, not an accident.** `/grill` is an optional command, and the "easy to remove" property is made TRUE by construction — it is a stated constraint a future builder may not erode, not a happy accident. Two parts:
  - **(a) The owned surface is ISOLATED.** The `grill` command (`src/commands/grill/main.md` + `references/`), the `_grill/` helper subpackage + `grill_helper{,.py}` launcher, and the `devils-advocate` agent (`src/agents/devils-advocate.md`) are self-contained. Removal = delete those files + the ONE `_PROMOTED` line in `scripts/emitters/claude.py` (the agent needs no emitter line — it glob-emits). Nothing in `_shared/`, `/audit`, `/review`, `/plan`, or `/breakdown` is forked or mutated by the owned surface, so deleting it leaves those byte-unchanged.
  - **(b) The backward-seed CONSUMER hooks (Phase 5) MUST be ADDITIVE, CONDITIONAL, and INERT.** The re-entry-seed consumers in `/research`, `/discover`, `/specify` MUST be built as a self-contained conditional block — "IF a re-entry seed addressed to this stage exists, incorporate it; ELSE proceed unchanged" — NEVER woven into those commands' core logic. This makes removal three localized deletions (one block per command), AND keeps the block INERT when `/grill` is unused: no seed is ever produced (the producer only runs on a `/grill` RE-ENTER-UPSTREAM disposition), so the consumer block never fires. A future builder threading the consumer logic into the commands' core flow would break BOTH properties (clean removal AND inertness) — so this is a stated constraint, enforced in the Phase 5 description, not a suggestion. Rationale: removability is the concrete mechanism behind D8's "opt-in, never a mandatory gate" promise and the cost-honesty section's hedge — it is what keeps the unproven-bet downside bounded (an unused `/grill` costs nothing and is trivially deleted), so it must be a load-bearing constraint, not left to chance.

## Rejected alternatives & cost honesty

The standalone `/grill` (D1) is the CHOSEN design. This subsection records what was rejected, why, and names the cost plainly (repo discipline: make the cost visible, don't bury it).

- **Chosen — standalone `/grill` (D1)**, modeled on `/review`: its own `src/commands/grill/main.md` + `references/`, its own `_grill/` helper subpackage + `grill_helper{,.py}` launcher, its own emitter promotion, and pipeline wiring placing it between `/plan` and `/breakdown`. It mirrors forge's existing build/scrutinize separation at the design level, reuses the FULL `_shared/` engine (a third consumer alongside `/audit` + `/review`, never a fork), and keeps the opt-in structural. Cost: a new command surface (helper subpackage + spec + references) + a new `devils-advocate` agent (OQ1 RESOLVED — roster 17 → 18) + per-invocation human adjudication at the `/breakdown` gate.
- **Rejected A — embedded `/plan` Phase 1.4 sub-phase.** An OPTIONAL adversarial-review sub-phase inserted INSIDE `src/commands/plan/main.md` between Phase 1.3 (architect) and Phase 2 (write the plan), fired by an auto-gate reading a new `Stakes:` architect-return signal, with the architect RESPONDING to attacks and the user judging. Rejected because: (1) it embeds scrutiny inside the build stage — the exact coupling forge avoids at the code level (review is never inside `/implement`); (2) the auto-gate requires a new `Stakes:` return-contract dependency on `src/agents/architect.md` + `/plan`, added surface for an opt-in the user can express more simply by just invoking a command; and (3) putting the architect (the proposer) in the respond/judge loop on attacks against its OWN design recreates the self-review problem this plan exists to fix. The standalone shape dissolves all three.
- **Rejected B — instruction-only-lite.** An orchestrated adversary Task dispatched inline + a hand-written disposition, with NO new helper subpackage — the orchestrator drives `_shared/_validate` + `route_refutation` + the report by hand. Cheapest; no helper or command-roster growth. Rejected because the scope/brief/report composition wants a tested verb each (orchestrator-composed prose is the exact hallucination surface the helper-owns-shape principle exists to remove), and `/review` already proved the helper-subpackage shape is the right home for this flow — a third one is cheaper to maintain than a bespoke inline orchestration.
- **Cost honesty — `/grill` is now HEAVIER than the clean `/review` mirror (Refinements A/B/C).** The earlier draft cost `/grill` at roughly one more `_shared/` consumer (a `_review` clone with a different scope + a disposition). The three refinements raise that cost materially, and the repo discipline is to name it, not bury it:
  - **It reads scoped CODE (Refinement B — Ring 0 / Ring 1).** The `devils-advocate` agent resolves a three-ring blast radius (via its CBM graph tools — `_scope.py` only hands it the STATIC path manifest) and reads Ring 0 (the files the plan's File Impact table modifies + their tests) and a capped one-hop Ring 1 (direct callers/callees via the CBM graph) into context. That is real token cost the markdown-only mirror did not pay — justified because the expensive design errors (duplicate-by-new-file, search-before-building violations) are invisible in markdown.
  - **It QUERIES the whole repo (Refinement B — Ring 2).** Ring 2 is query-only (CBM `search_graph` / `search_code` / `get_architecture` + targeted `get_code_snippet`), not read-into-context — cheaper than reading the repo, but still added machinery and added latency over a pure-markdown grill.
  - **It reaches the WEB (Refinement C — context7).** A self-gating web-verification sub-step (fires only when the plan names an external dependency) adds network round-trips and a wider tool surface (`context7` + `WebFetch`/`WebSearch`) over the read-only reviewer baseline.

## The `/grill` flow (the runtime)

This is the runtime flow `/grill`'s `main.md` wires (Phase 3). It mirrors `/review`'s attack → validate → refute → report pipeline, EXTENDED with a wider read-context (`spec.md` + the scoped codebase), a self-gating web-verification sub-step, a CLASSIFY stage, and a 4-way disposition at the end. (These steps are the command's internal runtime flow, distinct from the build-phase numbering in `## Phases`.)

1. **GATE — by invocation.** There is no auto-gate. `/grill` runs because the USER invoked it (D2 / D8). `_preflight` confirms the setup chain completed and the target `plan.md` exists; on a missing `plan.md` it tells the user to run `/plan` first and ends the turn.
2. **SCOPE — resolve the target + assemble the STATIC path manifest.** `_scope` resolves the target `plan.md` (the lowest-numbered in-progress feature's `plan.md`, or an explicit path arg) and assembles the STATIC path manifest the adversary attacks against — it does NOT compute the three-ring blast radius. `_scope` hands the adversary:
   - the target `plan.md` path (the design under attack);
   - the upstream `spec.md` path (the WHAT — TRACE context so a grounded attack can be attributed to the upstream stage that introduced it; Refinement A);
   - the recon dossier path (research/discover handoff, already on disk from `/plan` Phase 0a.5) + the `constitution.md` path;
   - the feature identity (so the report writes to `specs/[feature]/grill.md`).
   - **Why a STATIC manifest, not the blast radius:** `_scope.py` is a Python helper, and a Python helper CANNOT call the codebase-memory-mcp graph — the same constraint that makes `/audit`'s ORCHESTRATOR drive the MCP while its helpers only consume the scratch chain. The three-ring blast-radius traversal therefore belongs to the ATTACK step, performed by the `devils-advocate` agent (which holds the CBM graph tools), NOT to `_scope.py`.
3. **ATTACK — the adversary resolves the three-ring blast radius, then attacks (+ the self-gating web-verification sub-step).** Dispatch the `devils-advocate` adversary (OQ1 RESOLVED — the dedicated adversary, architect excluded). The architect is NOT in the ensemble (it authored the design, and by charter it is an OPTIMIZER / decision authority — it "decides HOW" and owns the final call — not an adversary chartered to attack the design it chose; `src/agents/architect.md` charter posture, verify on read). The adversary reads the artifacts the manifest names (`plan.md` + `spec.md` + dossier + `constitution.md`) AND resolves the **three-ring codebase blast radius itself** via its CBM graph tools (Refinement B):
   - **Ring 0 (read in full):** the existing files the plan's File Impact table declares it will MODIFY, plus their existing tests (the contract). NEW files in the table = nothing to read (design-only attack).
   - **Ring 1 (read in full, ONE hop, CAPPED):** the direct callers + callees of Ring-0 files via the CBM graph (`trace_path(mode=calls)`), capped at a tunable default (~15–20 files / a token budget — OQ7). If a Ring-0 file is a HUB EXCEEDING the cap, read the highest-centrality slice and EMIT the large fan-out as a finding ("plan touches an N-caller hub, high blast radius, addresses M of them") — never silently drop (the `/audit` no-silent-caps discipline). Use `/audit`'s centrality signal (churn × CBM-callers × size) to pick which Ring-1 neighbors to read first under the cap — no new ranking machinery.
   - **Ring 2 (QUERY only, NOT read into context):** the whole repo via CBM probes (`search_graph` / `search_code` / `get_architecture`), pulling only the specific `get_code_snippet` a hit points to. This is how duplicate-by-new-file (find the existing thing the plan reinvents, wherever it lives — plan-05's §7 Structural Integration check) and layer/boundary violations get grounded WITHOUT reading the repo.
   - **Boundary:** read NARROW (Ring 0 + one hop), query WIDE (Ring 2). Reading the whole codebase into context is `/audit`, explicitly OUT; two-plus-hop defects are caught by the Ring-2 query layer, not by deeper reading. The scope scales automatically: brownfield (`/research` → existing code) ⇒ Ring 0/1 rich; greenfield (`/discover` → mostly new files) ⇒ Ring 0 nearly empty, grounding leans on dossier + constitution + Ring-2 duplication queries.
   - With the blast radius resolved, the adversary produces grounded, structured ATTACKS-as-findings (architectural failure modes, plan-vs-reality mismatches — duplicate-by-new-file, search-before-building violations, wrong assumptions about existing code — security attack-surface, scalability ceilings, constitution violations, and the holistic "should this approach exist at all").
   - **Self-gating web-verification sub-step (Refinement C):** this sub-step fires ONLY when the plan names an external dependency (library / version / API / pattern). A pure-internal-logic plan SKIPS it automatically — no flag, no mode. The tool is primarily **context7** (current docs for a named library/SDK/API — "use even when you think you know; training data may be stale"), with `WebFetch`/`WebSearch` only for CVEs/advisories context7 does not cover. **Hard boundary — VERIFY, do not RE-DISCOVER:** the sub-step verifies CLAIMS THE PLAN MAKES (e.g. "plan calls Stripe `charges.create` → context7 marks it deprecated for PaymentIntents → attack"); it does NOT hunt alternatives the plan did not consider. A web hit surfacing "a better option (library Y) now obsoletes this approach" does NOT adopt Y and revise the plan — it routes RE-ENTER-UPSTREAM → discovery via the re-entry seed (Refinement A / CLASSIFY). Web-VERIFICATION failures attack the plan directly; web-DISCOVERY findings feed the backward loop.
4. **VALIDATE — the grounding gate (DUAL standard).** `_shared/_validate` drops ungrounded attacks before refutation. There are TWO grounding standards depending on the attack's evidence target:
   - **Internal attacks (code / `plan.md` / `spec.md` / constitution):** the `_validate` mechanical VERBATIM-substring check against a file resolvable under `source_root`. Because `plan.md`, `spec.md`, and the Ring-0/1 source files are ALL under `source_root`, the SAME `_validate` validates them all regardless of which artifact `Finding.file` cites (OQ3 RESOLVED — polymorphic `Finding`, no schema change).
   - **Web attacks (no `source_root` file):** these CANNOT pass the mechanical substring check, so they use the research/discover **web-citation standard** — a cited `library@version` (via context7) or URL + the quoted passage, RE-FETCHABLE by the refutation pass (the refuter re-checks the citation; whether the v1 refuter performs a live re-fetch vs refutes on the captured passage is OQ8). Both standards are stated explicitly so a web attack is never silently dropped for failing the code-only check.
5. **REFUTE — non-author neutral cross-examination.** `route_refutation(findings, present_finders, priority=[code-reviewer, qa-reviewer, security-reviewer])` assigns each attack a NON-AUTHOR refuter (architect excluded from the priority list — D5). Each refuter cross-examines its routed subset under `references/refutation-preamble.md` (default-dismiss unless the defect is re-demonstrated from quoted evidence — for web attacks, from the re-fetchable citation per the dual standard); `consume-verdicts` + `apply-verdicts` partition into confirmed / dismissed / uncertain / contested (high-stakes `[CONTESTED]` surfaced, never buried). The architect is NEVER a refuter.
6. **CLASSIFY — route each surviving attack to a disposition (the "destroys-the-plan?" test).** For each surviving grounded attack, apply the classification test (the SAME two-question decision tree D9 defines):
   - **Q1 — "Does a different HOW (a re-plan against the SAME spec) fix the defect?"**
     - YES → **REVISE-PLAN** (plan-local).
     - NO (no HOW survives the fix — this is what "destroys the plan" means) → go to Q2.
   - **Q2 — "Would a corrected WHAT or grounding (re-`/specify` / re-`/discover` / re-`/research`) yield a viable design?"**
     - YES → **RE-ENTER-UPSTREAM** (→ nearest stage that owns the defect, with the re-entry seed) — attributed to the NEAREST introducing stage (traced via `spec.md` + the dossier in context — is the bad requirement already in the research handoff? → research; introduced at `/specify`? → spec only — nearest-stage-first, NOT a blanket rewind).
     - NO (nothing rescues it — the feature is infeasible, unjustified, or should be bought not built) → **KILL**.
   - (PROCEED is the no-surviving-attack / all-accepted-as-risk case — outside this YES/NO tree.)
   KILL is reached only when nothing — no HOW and no WHAT change — rescues the design (a fatal HOW with a viable alternative is REVISE-PLAN at Q1=YES; a fatal HOW with no viable alternative but an upstream rescue is RE-ENTER-UPSTREAM at Q1=NO, Q2=YES). This stage produces the recommended disposition AND, for a RE-ENTER-UPSTREAM, the re-entry-seed payload (`[what the upstream stage concluded] + [the grounded grill finding that invalidates it] + [what the re-run must now additionally satisfy]`).
7. **REPORT — findings + disposition + any re-entry seed.** `_report` writes `specs/[feature]/grill.md`: the surviving grounded attacks (confirmed ∪ high-stakes `[CONTESTED]`) + a dismissed / worth-a-glance appendix (mirroring `/review`'s report shape) + the recommended **4-way disposition: PROCEED / REVISE-PLAN / RE-ENTER-UPSTREAM / KILL** (D9). On a RE-ENTER-UPSTREAM disposition, the re-entry-seed producer (Phase 2) ALSO emits the structured backward seed for the nearest upstream stage to consume on re-entry (Phase 5 wires the `/research`/`/discover`/`/specify` consumers).
8. **HUMAN GATE.** The disposition is a RECOMMENDATION. The human makes the final call at the existing `/breakdown` approval gate: PROCEED → run `/breakdown`; REVISE-PLAN → re-run `/plan` with a different HOW, then optionally re-`/grill`; RE-ENTER-UPSTREAM → re-run the named upstream stage (`/research`/`/discover`/`/specify`) with the re-entry seed, then re-`/plan` → re-`/grill` (the backward loop, bounded by D4's compounding counter — each seed monotonic, escalate to the human after the cap); KILL → re-run `/plan` with a wholly different approach (D4 — human-controlled loop throughout).
