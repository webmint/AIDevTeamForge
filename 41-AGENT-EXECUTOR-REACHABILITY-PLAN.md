## Why this plan exists

A 2026-06-24 survey traced every **declaration** of responsibility in `src/` (an agent named as responsible, a phase that claims "X is verified/reconciled at stage Y", a finder that produces findings) down to its **executor** (the command/helper/verdict that actually RUNS or CONSUMES that responsibility). The survey's method header was *declarations → executors*: for each declared responsibility, find the code path that honors it; where none exists, the declaration is an **orphan**. Three orphan types surfaced:

1. **ORPHANED AGENT (type-1).** An agent is named as responsible for some concern, but no command dispatches it — it can never run.
2. **ORPHANED STEP / PHASE (type-2).** A spec/table says "X is verified/reconciled at stage Y", but stage Y performs no such step — the promised step does not exist.
3. **ORPHANED FINDING (type-3).** An agent runs in an ensemble and produces a finding, but the finding gates nothing downstream — it is rendered for a human, never blocks a verdict, and so is inert. It looks wired; it is not.

The survey produced four concrete findings:

- **`design-auditor` (type-1 / type-2).** The canonical orphan — dispatched by no command, with a charter step and boundary output nothing honors. **OWNED BY PLAN 40 — OUT OF SCOPE here.** Plan 40 (`40-DESIGN-FIDELITY-FORCING-FUNCTION-PLAN.md`, Phase 0 RATIFIED 2026-06-24) wires it into `/review`. Plan 41 does not touch it.
- **`qa-engineer` (type-1).** A real test-writer charter with no assignment path that routes work to it (Work Item 1, in scope).
- **Confirmed Medium/Info `/review` findings (type-3).** Produced, parsed, folded into `/verify`, and rendered — but they cannot move the verdict off APPROVED, so a finder that emits only Medium/Info output gates nothing (Work Item 2, in scope).
- **`/breakdown` roster gap (a separate class).** A `/breakdown` assignment can name an agent absent from the target project's installed `.claude/agents/` roster. **OWNED BY PLAN 38** (`38-BREAKDOWN-AGENT-ROSTER-VALIDATION-PLAN.md`) — a CONSUMER-side runtime check. Plan 41's permanent gate (Work Item 3) is the MAINTAINER-side complement, not a fold-in (see D7).

A one-time survey cleans today's orphans; it does not stop tomorrow's. The root cause of all three types is **a declaration with no enforced executor**. Work Item 3 is the centerpiece: a permanent maintainer-side gate that fails when a new orphan is authored.

## Decisions

- **D1 — WIRE `qa-engineer` an executor; do NOT retire it (maintainer decision).** `qa-engineer` (`src/agents/qa-engineer.md:3`) has a real charter — write and fix tests from a spec's acceptance criteria, fill coverage gaps; *"Writes tests; does not render an adequacy verdict."* Plan 15 deliberately split it from `qa-reviewer` as a pure test-writer (`model_tier: do`). The orphan is purely missing routing: the `/breakdown` Agent Assignment table (`src/commands/breakdown/main.md:240-251`) has NO test-authoring row (grep confirmed zero "write tests → agent" rows), so no task ever routes to it. It is reachable ONLY via the conditional architect-consult relay availability list (`breakdown/main.md:189`, `plan/main.md:326`), which cannot honor its charter (a relay is not a dispatched implementer task). Retiring a charter-complete builder to satisfy a survey is the wrong correction; the survey says "no executor", so the fix is to add one. **Alternative rejected:** retire `qa-engineer` and let stack engineers own all tests — rejected because the agent is a deliberate plan-15 split with a distinct `model_tier: do` builder role; the gap is routing, not redundancy.

- **D2 — `qa-engineer` testing-model: inline-default + dedicated-task-on-flag (RECOMMENDED; maintainer ratifies at Phase 0).** Two candidate models:
  - **(a) inline tests stay the default; a dedicated `qa-engineer` task is created only on a flagged coverage-gap.** Each feature task's implementing stack engineer writes that task's tests inline as the established per-engineer practice — note that the task "Done When" line (`breakdown/main.md:275`) carries the standing static-analysis conditions (tsc / lint / no-secrets / no-debug), NOT a mandated inline-test-writing item, so inline test authoring is engineer practice rather than a Done-When mandate. `/breakdown` ADDS an explicit rule + assignment row that routes a DEDICATED test-authoring task to `qa-engineer` when (and only when) decomposition / the architect consult flags a coverage gap or a test-heavy AC. This gives `qa-engineer` a real executor without double-covering every task.
  - **(b) a standing "Dedicated test authoring / coverage-gap tests → `qa-engineer`" row** that decomposition uses whenever a spec calls for it.
  - **RECOMMENDED: (a).** It preserves the existing inline-test contract (no behavioral churn on the common case), gives `qa-engineer` a real, scoped executor, and avoids double-coverage (every task already carries inline tests; a standing always-route row would manufacture redundant qa-engineer tasks). Model (b) is the superset — adopt it only if Phase-0 review wants test authoring routed away from engineers by default, which contradicts the existing inline contract. **Cross-ref:** `/implement` PHASE 5 (plan 17) RUNS tests as a gate (`17-IMPLEMENT-PER-TASK-PANEL-PLAN.md`); it does not WRITE them. `qa-engineer` fills the write side; the two are complementary, not overlapping. **Architect-guard note:** the new assignment row must not collide with the `/implement` architect-guard (plan 14, `src/commands/implement/main.md` + `references/agent-brief.md`) — `qa-engineer` is `model_tier: do`, a builder, so it is a VALID per-task implementer (unlike `architect`, which the guard forbids as a coder). The row routes a real implementer task; the guard does not fire.

- **D3 — Confirmed Medium `/review` findings gate the `/verify` verdict (maintainer decision); threshold = any-confirmed-Medium → NEEDS WORK (RECOMMENDED).** Today the verdict math only turns a review finding into a blocker if it is Critical/High severity OR carries `[CONSTITUTION-VIOLATION]`. The severity predicate is `_is_critical_high` (`src/devforge/lib/_verify/_verdict.py:139-143`); the fact-gathering list comprehensions (`constitution_confirmed` / `constitution_contested` at `_verdict.py:204-205`, `critical_high_headline` at `_verdict.py:207-210`) FEED the blockers but are not themselves the blocker list; the actual `blockers.append(...)` happens in separate downstream `if` blocks — `if constitution_confirmed:` at `_verdict.py:226-235`, `if constitution_contested:` at `_verdict.py:244-256`, AC failures at `_verdict.py:259-282`, and `if critical_high_headline:` at `_verdict.py:297-315`. A confirmed Medium- or Info-severity, non-constitution review finding is rendered into `verification.md` (the human sees it — `src/devforge/lib/_verify/_report.py`) but no `if`-block appends it to `blockers`, so it cannot move the verdict off APPROVED. A finder producing only Medium/Info output runs, is parsed, folded, counted — and gates nothing. **This is a `/verify` verdict BEHAVIOR change.** Threshold options:
  - **RECOMMENDED: any confirmed Medium → NEEDS WORK (not REJECTED); Info stays advisory / non-gating.** The simplest defensible rule, no tunable knob.
  - **Rejected for now: N≥threshold Mediums → NEEDS WORK.** A count threshold is a tunable knob that drifts and is escape-hatch-shaped (per the zero-escape-hatch discipline — "≥N" is exactly the kind of judgment dial a future session widens until it never fires).
  - Confirmed Medium maps to NEEDS WORK, never REJECTED — REJECTED stays reserved for the existing hard blockers (Critical/High + constitution violations). Info remains advisory.

- **D4 — Hygiene stays advisory and untouched; the Medium gate is CODE findings ONLY.** Plan 34 (`34-VERIFY-HYGIENE-FALSE-POSITIVE-PLAN.md`) made hygiene (scope-creep + leftover-artifacts — `_verdict.py:53-57,317-329`) ADVISORY precisely to kill a false-positive NEEDS WORK on clean features. Work Item 2 must NOT reintroduce that false positive. The Medium gate applies ONLY to real, CONFIRMED, post-refutation CODE findings of Medium severity from the `/review` finder ensemble — NOT to hygiene flags, which remain advisory and out of the blocker set. This boundary is load-bearing: a future session must not "tidy" the Medium gate into re-blocking on hygiene.

- **D5 — The permanent gate checks a mechanizable slice only; it does NOT claim type-2/type-3 coverage (zero-escape-hatch honesty).** The gate (Work Item 3) closes the type-1 orphan class (an authored agent with no executor) and the assignment-names-an-unknown-agent class, both of which are presence-checks over parseable source. It does NOT cover type-2 forward-prose ("verified at X") or general type-3 finding-inertness — those require natural-language and verdict-semantics understanding the gate cannot mechanize. **State this in the gate's own output and docs** so a future session does not believe the gate covers them and skip the human review convention that does (D8).

- **D6 — Gate check-set (the four mechanical rules).** The gate:
  1. Parses every `src/agents/*.md` → the roster set (file stems).
  2. Collects every real dispatch path in `src/`: literal `subagent_type: <agent>` occurrences in `src/commands/**`; data-driven `/implement` agent-field dispatch via a `/breakdown` Agent Assignment table row (`breakdown/main.md:240-251`); and helper ensemble / finder / refuter lists, each with its own collection shape — `src/devforge/lib/_audit/_preflight.py` `_AUDIT_AGENTS` (flat list), `src/devforge/lib/_review/_brief.py` `_FOCUS_BLOCKS` (dict — parse the KEYS as agent names), `src/devforge/lib/_implement/_cmds_review_panel.py` `_REVIEWER_VOCAB` (dict — parse the KEYS), `src/devforge/lib/_shared/_verify.py` `_REFUTER_PRIORITY` (flat list), `src/devforge/lib/_grill/_cli.py` (the `devils-advocate` adversary dispatch + refuter priority). The gate parser must handle BOTH list literals and dict keys — a flat-list-only parser silently misses the dict-keyed lists and false-fails the agents they dispatch.
  3. FAILS if any roster agent has ZERO dispatch path.
  4. FAILS if any agent NAMED in an assignment row is absent from the roster, OR is named ONLY in a consult-relay availability list (`breakdown/main.md:189` / `plan/main.md:326`) with no other executor.
  - **Data-driven nuance (must be encoded):** the engineer agents (`backend-engineer`, `frontend-engineer`, `db-engineer`, `devops-engineer`, `migration-engineer`, `mobile-engineer`, `api-designer`, `runtime-debugger`) are NOT literal `subagent_type` anywhere — they are dispatched via the `/breakdown` table → `/implement` agent-field. The gate MUST treat an Agent Assignment table row as a valid executor for those, or it will false-fail every engineer agent.

- **D7 — Plan 41's gate is MAINTAINER-side; plan 38's gate is CONSUMER-side. Complementary, not overlapping.** Plan 38 = "is the assigned agent present in the target project's installed per-project roster (`.claude/agents/*.md`)?" — checked at `/breakdown` RUNTIME in a consumer install (its trigger was the mintEnvoy missing-`backend-engineer` halt). Plan 41 = "does every agent authored in `src/agents/` have an executor somewhere in `src/`?" — checked at MAINTAINER commit time against the framework source. Different roster (per-project install vs framework source), different time (runtime vs commit), different question (presence-in-install vs has-an-executor). Plan 41 cross-references plan 38; it does NOT fold it.

- **D8 — Type-2 and type-3 stay human review conventions, by construction.** Per D5, the gate covers only the mechanizable slice. Type-2 ("X verified at Y" prose) and type-3 (a finding that gates nothing) are recorded as a maintainer review-checklist convention — NOT a hard gate, NOT a TODO-to-mechanize. Naming them as out-of-mechanical-scope is the honest stance; pretending the gate covers them would be the escape hatch.
