#### What bounds a command today — timeouts

**F1 — The project-toolchain timeout.** `_CMD_TIMEOUT = 120` at `src/devforge/lib/_implement/_cmds_verify.py:157`, applied at `:396`. It bounds EVERY collected type-check, lint, build and test command. The run is `shell=True`, `cwd=source_root`.

**F2 — A timeout is scored as an ordinary failure.** On expiry the function returns `(1, "Command timed out after 120s: <cmd>")` (`:401`). `_is_tooling_unavailable` (`:427-451`) matches ONLY `returncode == 127` or two anchored shell strings — *"command not found"* and *"not recognized as an internal or external command"* — so a timeout matches nothing and **enters the self-repair loop as though the code were broken.**

**F3 — The self-repair cap is helper-owned, and the worst case is bounded by the FIRST failure.** `SELF_REPAIR_CAP = 3` (`:153-154`); the orchestrator cannot extend it. The loop restarts the command list from index 0 on each iteration (`:597`) but **breaks at the first failure** — the `break  # Stop at first failure` line in the same module — so a command that times out is paid for up to **four sequences of the commands that precede it plus itself**, never four times the whole list, before the helper returns `{"status": "failed"}`. ⚠ **At a 1200-second ceiling with one slow command that is roughly 80 minutes**; it approaches several hours only when a second slow command succeeds ahead of the failing one.

**F4 — The repairing agent is told almost nothing.** On a timeout the subprocess output is discarded; the agent receives only the one-line timeout string as `output`. It has no compiler error to repair, and no way to tell "slow" from "broken" from that string.

**F5 — A SECOND, independent timeout.** `_CMD_TIMEOUT = 120` at `src/devforge/lib/_implement/_cmds_gate.py:66`, applied at `:193`. It bounds the framework's OWN `constitute_helper` calls — an argv list, no `shell=True`. A timeout there is converted into a rule **FAILURE with an empty report string** (`:194-196`).

**F6 — The regression gate's timeouts.** `src/devforge/lib/_verify/_regression.py` carries `_WORKTREE_TIMEOUT = 120` (`:104`) and `_TEST_TIMEOUT = 600` (`:107`). The suite it runs is `TEST_COMMANDS[0]` ONLY (`_get_test_command` `:154-171`), executed twice — once at the merge base, once at HEAD.

**F7 — The baseline worktree is never built.** The baseline is a detached `git worktree` in a temp dir. `_symlink_deps` (`:267-287`) symlinks ONLY `node_modules`, `.venv`, `venv` and `vendor` (`_DEP_DIRS` `:113`) and **builds nothing.** A project whose suite needs compiled artifacts therefore fails at the merge base, which lands on `baseline-failing` (`:450-462`) and sets `regression: False` — **the gate reports and never gates.**

**F8 — The e2e lane.** `src/devforge/lib/_verify/_e2e.py` carries `_E2E_TIMEOUT = 1800` (`:146`); the suite runs once at HEAD in `source_root`, never in a worktree. Statuses are `off` / `inconclusive` / `e2e-clean` / `e2e-failing`, and the lane is ADVISORY — no status changes the verdict.

**F9 — No timeout anywhere is config-driven.** A grep over `src/devforge/lib/_configure/` returns zero `TIMEOUT` hits, and a grep over `src/` for a `TIMEOUT` key in any json, md or yaml file returns zero. **Every timeout in the framework is a module-level constant or an inline literal.**

#### The config surface a new key crosses

**F10 — The counts, obtained by EXECUTING the modules on 2026-09-20.** `FIELD_SCHEMA` = 37, `ENUM_FIELDS` = 9, `FIELD_DEFAULTS` = 7, `_PROJECT_CONFIG_KEY_ORDER` = 45. It is a render artifact"*: `if [ -f "$PROJECT_CONFIG" ]; then HAS_CONFIG=true; elif [ -f "$TARGET_DIR/.devforge/configure.yaml" ]; then … render-config`). **So the entry prevents the null-scalar violation, and every install whose `project-config.json` was rendered before the change still gets exactly one new violation, `project-config.json missing key COMMAND_TIMEOUT`.** `update.sh` calls `forge_check_config_completeness` (`scripts/post-update-checks.sh`), which surfaces it as a WARN — *"⚠  Project configuration does not match this framework version (configure_helper verify):"* … *"Fix: re-run /devforge:configure, which writes .devforge/configure.yaml and renders .devforge/project-config.json."* — until `/devforge:configure` re-renders. It is the WARN every key added since 2.0.9 produced: `tests/scripts/test_post_update_checks.py::test_legacy_config_warns_with_each_violation_tier_line_and_fix` pins it for `E2E_COMMAND`, `REQUIRE_TICKET` and the four `CLAUDE_EFFORT_*` keys — every one of which HAS a `FIELD_DEFAULTS` entry — plus `CLAUDE_TIER_SECURITY`. **F12 — The render is a case transposition.** `render-config` maps `configure.yaml` → `project-config.json` by `key.lower()` (`_configure/_render.py:174-190`). The two names must be exact case-transposes, or the field renders `None` and the round-trip check at `_cmds_verify.py:118-133` fails.

**F13 — There is NO shared `project-config.json` reader, deliberately.** 33 files under `src/devforge/lib/` each own a private one. ### D1 — ONE new config key, `command_timeout` / `COMMAND_TIMEOUT`

A string scalar (F10), with a `FIELD_DEFAULTS` entry of `"120"` (F11 — **mandatory**, or every existing install fails `configure_helper verify` on the null-scalar check; the entry does NOT make the upgrade silent), appended LAST to both `FIELD_SCHEMA` and `_PROJECT_CONFIG_KEY_ORDER` per the in-tree byte-stability rule. The two names are exact case-transposes, as F12 requires.

- **Exactly ONE consumer reads it:** `src/devforge/lib/_implement/_cmds_verify.py`. `_CMD_TIMEOUT` has **TWO uses** in that module's `_run_command` (verified 2026-09-23), and **both take the resolved value**: the `timeout=_CMD_TIMEOUT,` argument to `subprocess.run` AND the message `return 1, "Command timed out after {0}s: {1}".format(_CMD_TIMEOUT, cmd)`. ⚠ **The message is not cosmetic** — per F4 it is the ONLY thing the repairing agent receives on a timeout, so replacing only the `timeout=` use would tell the agent "120s" while the real bound is the configured value. `_run_command(cmd, cwd, extra_paths=None)` has **no timeout parameter today**, and `cmd_verify_touched` calls it as `_run_command(cmd, source_root_str, extra_paths=_bin_dirs_ordered)`, so getting the resolved value into it takes a signature change or an equivalent; this decision does not prescribe which. The module constant is KEPT as the fallback when the key is absent or unparseable, so a helper invoked outside a configured install behaves exactly as today.
- **Validation lives INSIDE the setter** — a positive-integer check. **Do NOT add a sixth shared validator** to `_validators.py`, which already defines five — `_validate_scalar`, `_validate_enum`, `_validate_string_array`, `_validate_path_value`, `_validate_verbatim` (verified 2026-09-23): one key with one setter does not earn a shared validator, and F13's no-shared-reader rationale applies the same way to writes.
- **The counts move and nothing else does:** `FIELD_SCHEMA` 37 → 38, `FIELD_DEFAULTS` 7 → 8, `_PROJECT_CONFIG_KEY_ORDER` 45 → 46. `ENUM_FIELDS` stays **9** — a string scalar is not an enum. Say so explicitly, so a future session can prove it rather than re-derive it.

**Why.** The ceiling is a property of the project's toolchain, not of a command class. One key, one read site, and **the consumer's behaviour on every existing install is unchanged**: a `project-config.json` rendered before the change lacks the key, so the consumer falls back to the module constant, and a re-render writes the `"120"` default — 120 seconds either way. ⚠ **The one visible change on an existing install is the post-update WARN** (`project-config.json missing key COMMAND_TIMEOUT`) until `/devforge:configure` re-renders (F11).

**Rejected alternative:** per-class keys (`BUILD_TIMEOUT` / `TEST_TIMEOUT` / …) — three to four times the blast radius, for a distinction no project has asked for.

**Rejected alternative:** a per-package field inside `PACKAGE_STACKS` — the heaviest surface of all (record shape, render, detection prose, every consumer), for a precision no consumer needs yet.

**Rejected alternative:** raise the constant globally with no key — it takes the fast-fail property away from every project to serve one.

**Rejected alternative:** do nothing, and proxy the slow commands. This works for type-check (`dotnet build` on the generated `.csproj` is seconds) and can be made to work for build, but **cannot be made to work for the test command**, which needs the editor in batchmode. ⚠ **It also depends on that `.csproj` being on disk, which is not guaranteed** — F25's review nuance: the file is generated by the IDE packages, excluded by the standard engine `.gitignore`, absent from a fresh clone and never present in a git worktree. **The decision does not change** — the alternative was already rejected on the test command alone — but a future session must not revive it on the assumption that the manifest is always there.

**RECOMMEND D1 as stated.**

**Counter-argument, recorded:** one key means a hung linter in that same project also gets the long ceiling — the fast-fail that 120 seconds buys is spent on every command, not only the slow ones. The setter's own check is the only guard, and a value hand-edited into `configure.yaml` bypasses it entirely — at which point the consumer's unparseable-value fallback is what stands between the run and a crash.

### D9 — `update.sh`'s new-agent delivery honours `applies_to`

When `update.sh` computes `NEW_AGENTS` (F21) for a target whose `.devforge/configure.yaml` sets `project_natures`, it applies the same keep/drop rule `prune-agents` applies to each candidate — `_parse_agent_frontmatter` (`_configure/_md_parsers.py`) on the candidate's SOURCE file, then `_decide_agent` (`_configure/_render.py`) against `configure.yaml`'s `project_natures` — exposed as **ONE `configure_helper` verb**, so the decision is Python and tested, and `update.sh` only branches on its answer. The verb calls both functions rather than copying them, so the rule itself keeps one owner. ⚠ **It is called ONCE, where `NEW_AGENTS` is computed** — the block *"# NEW agents: in the current roster (src/agents/*.md) but NOT in the snapshot."*, which iterates `$TEMPLATE_DIR/src/agents/*.md` — and a candidate the verb DROPs never enters `NEW_AGENTS`.

- **A DROP is neither installed nor seeded into the snapshot — by construction.** The execute loop that installs an agent and seeds the snapshot with it iterates `NEW_AGENTS`, which a DROP never enters. The agent then stays absent from `.devforge/template/.claude/agents`, so every later update meets it as a candidate again and re-asks the verb — and a target whose natures later gain `game` still receives it. ⚠ **Seeding the snapshot on a DROP would lose the agent for good:** update's three-way merge touches only agents present in the snapshot AND live in the target, so an agent in the snapshot but absent from the target is treated as one the user pruned (F21).
- **Every reader of `NEW_AGENTS` sees the filtered set, so none needs its own call** (verified 2026-09-23): the preview loop under *"# New framework agents to install (FIX C)"*, the regeneration trigger `if [ -n "$NEW_AGENTS" ]; then AGENT_WORK=true; fi`, and the execute loop under *"# ── Execute: install NEW framework agents (FIX C)"*. So the preview prints *"ADD (new agent)"* only for an agent the execute loop installs, and candidates the verb drops, every one of them, no longer set `AGENT_WORK` through that trigger (the three-way-merge line above it still can). ⚠ **The verb reads the SOURCE form:** the computation runs before `update.sh` regenerates agents — `REGEN_AGENTS_DIR` is assigned later — so each candidate is a `src/agents/<name>.md` in its fenced ```yaml form (F19), never the regenerated `---` form. `_parse_agent_frontmatter`'s docstring reads *"Two frontmatter forms are tolerated (parser tries both)"*, the first of them the SOURCE form.
- **A target with no natures keeps today's behaviour:** no `configure.yaml`, or `project_natures` unset → the candidate stays in `NEW_AGENTS` and is installed, and `/devforge:configure`'s Phase 5.2 prunes later.
- **The filter FAILS OPEN: a verb that exits non-zero leaves the candidate in `NEW_AGENTS`** — today's behaviour, the same answer the no-natures case gives. **(1)** The execute loop's first-write rule, *"a new framework agent that a new command depends on (e.g. devils-advocate → /grill) MUST always land"*, must not be defeated by a filter error. **(2)** Failing open costs at most today's delivery, which `/devforge:configure` prunes later (F21); failing closed would withhold an agent on any verb bug, and a withheld agent announces nothing — the preview does not list it and the execute loop does not install it. ⚠ **An absent Python never reaches the call site** (verified 2026-09-23): `update.sh`'s *"# ── Detect Python 3 (required for placeholder substitution + agent regen) ──"* block exits 1 with *"Python 3 is required (placeholder substitution + agent regeneration) but was not found."* when `PYTHON3_CMD` is empty, before `NEW_AGENTS` is computed — so fail-open governs the verb's own errors only.
- **An `["all"]` agent always lands**, by `_decide_agent`'s rule 2 — so the execute loop's own first-write rule, *"a new framework agent that a new command depends on (e.g. devils-advocate → /grill) MUST always land"*, stays true: `devils-advocate` is `applies_to: ["all"]` (verified 2026-09-23).

**Why.** This is not a prediction about an engine project. It is a **certain side effect of this plan's own Phase 2 on every existing install of every nature** (F21): the delivery applies no nature check, and `game-engineer` is the first nature-scoped agent to arrive through it. That is the class Phase 4 already treats as this plan's to fix — sites this plan's own phases falsify, which *"are this plan's to fix"* in Phase 4's own words — and not the class the fix/record line governs, which is gaps the plan predicts.

**Rejected alternative:** RECORD only — residual 14 plus an honest bound. Every existing install then receives `game-engineer.md` on its next update, until `/devforge:configure` prunes it.

**Rejected alternative:** run `prune-agents --apply` from `update.sh`. It re-prunes the WHOLE `.claude/agents/` directory against `project_natures`, deleting agents a user deliberately kept at `/devforge:configure`'s Phase 5.2 bulk confirmation — a `keep <name>` override is honoured once, by the orchestrator, and `--apply` *"deletes exactly the helper's decisions, not the override-adjusted set"* (`src/commands/configure/main.md`, Phase 5.2).

**Rejected alternative:** call the verb in both loops, the preview and the execute loop — this decision's first 2026-09-23 wording. **Two call sites can disagree:** each would be a separate shell edit over a different file form — the preview over the source form, the execute loop over the regenerated one — and keeping them in step would be a review duty with no test behind it, while the regeneration trigger would still fire for candidates both loops then skip.
