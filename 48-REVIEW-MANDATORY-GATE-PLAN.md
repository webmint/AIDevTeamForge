# 48 — Review Mandatory Gate Plan

**Status:** **SHELVED 2026-06-30 — keep the warning, do NOT build until observed.** No code, no docs. Nothing in this plan is built. Maintainer decision: the gap is structural-but-theoretical (NOT a reproduced incident, unlike the plan-38/42 precedent it anchors to), `/verify` already WARNS loudly on a missing review, and OQ-1 means even a full build guarantees review *presence* not *freshness* — so the cost is disproportionate to a gap nobody has hit. **Revival trigger:** revive this plan if a `/review` skip is OBSERVED in practice — especially a UI feature reaching an APPROVED `/verify` verdict while `design-auditor` (which runs ONLY at `/review` PHASE 2.5) never fired, leaving runtime design-fidelity unchecked. **Branch:** `develop-2.0-init`.

## Problem

`/review` is documented as a **mandatory** linear pipeline step — it appears UNBRACKETED in the workflow chain at `src/CLAUDE.md:40` (`… /breakdown → /implement → /review → /verify → /summarize → /finalize`), unlike the bracketed `[/grill]` on the same line that marks an opt-in step — but it is enforced by NOTHING. Two facts establish the gap. (1) `src/commands/verify/main.md:153` (the "Missing-review warning (proceed weakened)" block): when `read-review-findings` returns `"missing": true`, `/verify` only WARNS the user (*"no review report was found — run `/review` first … proceeding with AC + mechanical checks only"*) and then proceeds to render a verdict anyway — that same line states `compute-verdict` treats a missing review as a non-blocking note. (2) Every forge command sets `disable-model-invocation: true`, so the model CANNOT auto-run `/review`; the user must type it, which means the only enforceable lever is a downstream HARD GATE that refuses to produce a verdict until `/review` has run. Consequence: a feature can go `/implement → /verify` and skip `/review` entirely — the runtime design-fidelity check (`design-auditor`, which runs ONLY at `/review` PHASE 2.5) and the 5-finder emergent cross-task review never fire, yet the feature still earns an APPROVED verdict. This is the same disease plan 38 (agent-roster) and plan 42 (design-manifest trigger) closed: a load-bearing step guarded by SKIPPABLE PROSE instead of a MECHANICAL gate.

## Anchor to the established gate-shape precedent

This plan does not invent a mechanism. It reuses the exact forcing-function shape plans 38 and 42 established for `/breakdown`: a mechanical helper verb that walks the filesystem, exits non-zero on a violation, and a `main.md` step that copies the verb's stderr VERBATIM and HARD-halts. Plan 38's `breakdown_helper verify-agent-roster` and plan 42's `breakdown_helper verify-manifest-present` both sit in the `## PHASE 3.5: Integrity gates` section (`src/commands/breakdown/main.md:407`, running through ~454), exit 2 with a stdout findings block, and offer no Risk-Assessment bypass. Read `38-BREAKDOWN-AGENT-ROSTER-VALIDATION-PLAN.md` and `42-DESIGN-MANIFEST-TRIGGER-FORCING-FUNCTION-PLAN.md` in full before authoring any build phase here — they are the canonical pattern this plan applies to a new command (`/verify`) and a new precondition (`/review` ran).

The closest *forward-precondition* analogue is `/specify`'s gate: `/specify` blocks until a research or discover handoff exists (`src/CLAUDE.md:45` — *"`/specify` blocks until a research or discover handoff exists"*; enforced in `/specify` Phase 0.4). That is the same shape this plan gives `/verify`: refuse to do the expensive work until an upstream artifact is present.

## The settled thesis

`/review` becomes mechanically mandatory before `/verify` can render a verdict. The enforcement is a HARD GATE in `/verify` that halts BEFORE any AC verification or agent dispatch when `specs/[feature]/review.md` is absent.

## Decisions (proposed — ratify in Phase 0)

- **D1 — Mechanism = a preflight precondition verb, fail-fast (RECOMMENDED).** Add a new `verify_helper` precondition verb (working name `require-review --feature <dir>`) that exits NON-ZERO when `specs/[feature]/review.md` is absent and zero when present, wired into `/verify`'s PHASE 0 as a new sub-step AFTER feature resolution (PHASE 0.2, `src/commands/verify/main.md:67-74`, which is where `<feature>` first becomes defined) and BEFORE the scratch-dir setup (PHASE 0.3, `src/commands/verify/main.md:76`). It cannot sit alongside the setup-chain `preflight` gate at PHASE 0.1 (`src/commands/verify/main.md:59-65`), because PHASE 0.1 runs before feature resolution and the verb needs `<feature>` as its argument. Placed here, `/verify` halts during PHASE 0 preflight — before PHASE 1 scope resolution, PHASE 3 AC parsing, and the `ac-verifier` dispatch. The halt is exit-driven (on non-zero, copy the helper's stderr VERBATIM as a fenced code block and end the turn — the same contract every other `verify_helper` verb already uses per `src/commands/verify/main.md:53`), NOT a JSON-field read the orchestrator can soften. **`read-review-findings` already detects absence** — it emits `"missing": true` (`src/commands/verify/main.md:151`) — so the detection logic is reusable, but `read-review-findings` must KEEP folding findings for the verdict in PHASE 2; the precondition therefore belongs in a SEPARATE dedicated verb, not by making `read-review-findings` itself fail.
  - **Rejected alternative (a) — prose-halt at the existing fold-in step (`src/commands/verify/main.md:153`).** Flip the "proceed weakened" warning into a halt. Rejected as the PRIMARY mechanism because it fires LATE (after the PHASE 0 preflight, PHASE 1 scope resolution, and — if reached — costs the operator a longer run before the stop) and because it is a JSON-field read (`"missing": true`), the softer pattern an orchestrator can rationalize past. Retained ONLY as an optional defense-in-depth SECONDARY if the maintainer wants belt-and-suspenders (see D1-secondary below).
  - **Rejected alternative (b) — make `compute-verdict` refuse on a missing review.** `compute-verdict` is deterministic verdict math (its verb description is at `src/commands/verify/main.md:247`, inside PHASE 5 which opens at `:232`). Overloading it with a precondition couples two concerns and STILL runs only after the expensive AC + mechanical work in PHASE 3–4. Rejected.
- **D1-secondary — fold-in step reconciled, not left contradictory.** Independent of which mechanism is primary, the PHASE 2 "Missing-review warning (proceed weakened)" block at `src/commands/verify/main.md:153` MUST be reconciled with the new hard gate, or the file ships an internal contradiction (preflight halts on missing review, yet PHASE 2 still describes proceeding without it). Two coherent options, decided at Phase 0: **(i)** DELETE the proceed-weakened branch entirely (the preflight gate guarantees `review.md` exists by the time PHASE 2 runs, so the missing-case is unreachable); **(ii)** DOWNGRADE it to a defense-in-depth restatement that also halts (belt-and-suspenders). Recommendation: **(i)** — the preflight gate makes the PHASE 2 missing-case dead code, and a dead branch is itself a future-hallucination seed.
- **D2 — Zero exemptions (no escape hatch).** Per the zero-escape-hatch policy: NO carve-out. Even a trivial single-task feature must run `/review`, and there is NO `--force` / `--skip-review` flag. **Counter-argument recorded honestly:** `/review`'s headline value is *cross-task emergent* issues (cross-task security holes, assembled-data-flow perf, cross-task duplication, architectural drift), and a single-task feature has no cross-task surface — so mandatory `/review` there is heavier-but-lower-value. **Why the gate stands anyway:** (a) `design-auditor`'s runtime design-fidelity check, assembled-data-flow perf, and architectural-drift checks still apply to a single task's *assembled* diff; (b) an exemption is a slip-path — "single-task" is a judgment call the orchestrator gets wrong, exactly the class of carve-out the zero-escape-hatch policy forbids. Recommendation: no exemption.

## Open Questions (resolve in Phase 0 or a named follow-on)

- **OQ-1 — `/fix` re-review staleness (DEFER from v1).** The NEEDS-WORK loop is `/verify` NEEDS WORK → `/fix` changes code → re-`/verify`. On the re-run `review.md` already exists (from the first `/review` pass), so the new gate is SATISFIED by a now-STALE report that never saw the `/fix` changes. Should re-verify after a `/fix` require a FRESH `/review`? Closing this needs a staleness signal — e.g. compare `review.md`'s mtime or committed SHA against the latest feature WIP commit, and treat "review older than the newest code change" as a soft gate. This is genuinely harder than the presence check (it needs a freshness oracle, not a `test -f`) and is explicitly OUT OF SCOPE for this plan. **Next-session hallucination seed if left unaddressed:** a future session reading "this plan made `/review` mandatory" may FALSELY believe the gate guarantees the verdict reflects a review of the CURRENT code — it only guarantees a review report EXISTS, not that it is fresh. Record this limitation in the verdict-stage docs and track the staleness gate as a separate follow-on plan; do NOT solve it here.
- **OQ-2 — Precondition verb name.** `require-review` is the working name. Confirm at Phase 0 (alternatives: `check-review-present`, `gate-review`). Cosmetic — the contract (exit non-zero on absent `review.md`) is what matters.
