# Checklist: task-review

**Gate**: on — set to `off` to skip this gate (the file is project-owned; deleting it does not work, `update.sh` restores missing checklists).
**Runs**: in `/execute-task`, the per-task code review of every task, together with `test-lens.md` · **Reviewer**: `code-reviewer`; a fresh context; a different model from the implementer where possible.
**Inputs**: the task file `specs/NNN-*/tasks/NNN-*.md` and its diff; the spec sections, plan decisions and `contracts.md` entries it cites; `CLAUDE.md`; `constitution.md` if present; the design source when the task has UI.

**How to use**:
- Check every item that applies to the diff against the artifact and its sources, on top of the reviewer's standard pass; report each failed item by id with evidence quoted from both sides.
- Severity follows the review scale (Critical / Warning / Suggestion / Info). An item that names its Critical or Warning case uses it; otherwise the severity follows the effect of the defect.
- Defects outside the list are reported too, as `new`.

**Origin**: `seed` = shipped with Forge; `field` = generalized from defects that escaped earlier gates in field use; `escape NNN/E<n>` = added by this project's /finalize learning step; `audit <date>/<theme>` = added by /audit. New items take the next free id; ids are never reused. An escape that an existing item already covers adds its origin to that item instead of a new item.

## Items

- **TR-01** Every changed file complies with `CLAUDE.md` and `constitution.md` (the reviewer's standard pass). — seed
- **TR-02** Both paths of every fallible operation are handled: no error is swallowed, no catch block is empty, a secondary read after a write surfaces its own failure, and every caller consumes the result it returns. A success signal (message, close, navigation, event) fires only after the state it reports has settled. — seed
- **TR-03** Every user-visible text, message payload and ordered list matches the spec place by place: the exact text, every part of a message (title, detail, action), the form of an entity the spec names for each place (full name, short name, code), and an explicit sort by the rule the spec states rather than the order an API returned. — seed
- **TR-04** Docs and comments state the code's actual values (defaults, limits, names, return values, the empty and zero case); every path, key or guarantee that prose names exists and holds, superseded names are searched for rather than only the new text read, and a comment copied from a sibling is corrected to what the code now does. A docs-only task gets the same review. — seed
- **TR-05** Every changed file is inside the task's scope and none appears in the spec's Out of Scope or "stays unchanged" lists (check the diff stat against them); the diff holds no process text (task numbers, "wired in a later task") and no tool leftovers, and every key or export it adds has a consumer in the same diff or a named later consumer. A defect noticed outside the scope is filed as a bug or task note, not fixed or mentioned in passing. — seed
- **TR-06** For every plan decision or contract entry the task touches, the diff is compared with the chosen option and its rejected alternatives; a call, route or operation that replaces the one the plan names is raised even when the code is clean, and is reverted or recorded as a deviation with the user's decision. — field
- **TR-07** Every style value in a changed component (size, padding, weight, colour token, radius) matches the spec and the design value by value, and a size the spec fixes comes from explicit declarations, not from a font line box. A metric the reviewer cannot verify from the diff is a Warning that names the later check that measures it, never an Info. — field
- **TR-08** Every interactive control has an accessible name and a visible keyboard focus state in every theme; no element that carries a value the user reads is hidden from the accessibility tree; a focus placement the spec states is set explicitly and asserted through the active element. Fix and repair commits get the same check. — field
- **TR-09** Markup structure matches the spec and the design: content placed inside a container is a descendant of it, element order and grid cells match, a named state component (skeleton, empty, error) is rendered rather than a substitute, a library override that replaces defaults is compared with the design, and anchors ship exactly as named on the element the spec names. A shared component is checked against every consumer's design, not only the first. — seed
- **TR-10** Every enabled, visible or valid state that the spec derives from several conditions is computed from every named condition (async messages still showing included), and each spec sentence that makes a control, label or guard depend on a state is implemented and unit-tested in every state the view can be in. — field
- **TR-11** Shared state written by async flows ignores late results from a superseded user, request or key; state is written inside the guarded or latest-request flow, never before it; a dependent read whose key changed is cleared; a handler on blur, change or visibility that starts a request is guarded against its own teardown. — seed
- **TR-12** A value the user types or picks and the spec says is stored or sent is traced from the control to the request payload: no constant or default stands in for it, and a unit test per layer asserts the typed value arrives. — field
- **TR-13** A mapper over an external or stored row accepts every nullability the contract states and has a unit case with a null in each nullable field; a consumer downstream of it handles the null case. — field
- **TR-14** Numeric and date handling cannot overflow or accept special values: a cast or aggregate into a bounded type is checked at the extreme case, client text cast to a date or number rejects non-finite and special values with a clear error, and an equality over numeric text compares canonical values (equal numbers in different scales are equal). — field
- **TR-15** A guard or scope check inside a function that returns a set raises on mismatch instead of returning an empty set, because the caller may read empty as "nothing blocking" (fail closed). — field
- **TR-16** A command that writes, moves or deletes files confines its targets to an allowed root by canonical path (resolved, case-folded), refuses protected locations (VCS metadata, dependency folders) at any depth including the root argument, and a test pins each refusal. — field
- **TR-17** Every entry point (CLI, handler, job) wraps synchronous and asynchronous failures in one top-level handler that prints a fixed message without stack or paths and exits with the contract's code; every subprocess, network or CLI call has a timeout and a defined failure result that does not echo captured output. — field
- **TR-18** A guard or filter over a tool's command line is checked against how the real tool parses input (option prefixes, clustered short flags, shell wrappers, non-literal command words, alternate commands that do the same job), not only exact names. — field
- **TR-19** A task that changes a view or a file that earlier tests cover, read as data or compare with a copy elsewhere (a template and its copies in probes, a documented list and its fixture) finds those tests by search and runs them in the task, docs-only tasks included, repairing or re-recording their baselines in the same wave; such a test left unrun is a Warning, Critical when it fails. — field
- **TR-20** A check the task relies on runs the way CI runs it: without build caches, over every config the repository checks, under the runner's limits; a new repository-wide scanner runs over the whole tracked tree with every hit triaged. — field
- **TR-21** Every new exported symbol is checked by the reviewer's own search by name, signature and meaning, not by the implementer's notes; a semantic duplicate of existing code is Critical, a new shared export without a reason is a Warning. When `.claude/quality-profile.json` sets `newExports`, the reviewer checks every export that list reports; when it sets `canonicalSources`, another derivation of a listed concept is Critical. — seed
- **TR-22** When `.claude/quality-profile.json` sets `ratchets`, the reviewer runs the copies and similar-functions ratchets on the task diff: logic with three or more copies that the task added or changed is Critical unless the plan decides it, and a ratchet increase is never blamed on the environment without measuring the base tree the same way. Without `ratchets`, call sites turned into near-identical wrappers are a Warning. — seed
- **TR-23** A changed module keeps one axis of change and sits in the layer its content belongs to, with a name matching its main export and its siblings; its imports respect the declared layer directions, also through a public entry or alias, and business code imports no infrastructure SDK outside the allowed layers. A breach of a layer rule the project states is Critical, any other miss a Warning. — seed
- **TR-24** An implementation of a seam honours the seam's contract: no strengthened precondition, no weakened postcondition, no branch on the implementation's kind, no "not supported" stub (each Critical). Code that needs a set of kinds for which a registry exists derives it from that registry; a hand-written copy is a Warning. — seed
- **TR-25** The task's evidence is real: only the reviewed task changed its status to Complete, it has its own commit and non-empty Completion Notes, it ran through its assigned agent, and each Done when clause is ticked against output that matches the clause (the zero case included). A row marked Complete without them is Critical. — field
