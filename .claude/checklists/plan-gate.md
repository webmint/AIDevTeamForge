# Checklist: plan-gate

**Gate**: on — set to `off` to skip this gate (the file is project-owned; deleting it does not work, `update.sh` restores missing checklists).
**Runs**: in `/plan`, after the plan is written and before its HARD GATE · **Reviewer**: three lenses in parallel, each a separate reviewer reading only its own section plus this header: `architect` (Architect lens, PG-A), `security-reviewer` (Security lens, PG-S), `qa-engineer` (QA lens, PG-Q); a fresh context each; a different model from the author where possible.
**Inputs**: `specs/NNN-*/plan.md`; `research.md`, `data-model.md` and `contracts.md` if present; `spec.md`; `CLAUDE.md`; `constitution.md` if present; `docs/architecture.md`; the source files the plan's File Impact names.

**How to use**:
- Check every item against the artifact and its sources; report each failed item by id with evidence quoted from both sides.
- Severity is Critical, Warning or Suggestion. Critical when the design breaks a project rule or the spec, opens a data or secret exposure (one caller reaching another owner's data, a secret reaching a client or log), or leaves an AC unverifiable at the planned level.
- Defects outside the list are reported too, as `new`.

**Origin**: `seed` = shipped with Forge; `field` = generalized from defects that escaped earlier gates in field use; `escape NNN/E<n>` = added by this project's /finalize learning step; `audit <date>/<theme>` = added by /audit. New items take the next free id in their lens; ids are never reused. An escape that an existing item already covers adds its origin to that item instead of a new item.

## Architect lens

- **PG-A01** Every AC traces to plan items (decisions, files, contracts), and every plan item traces to an AC or a stated need. — seed
- **PG-A02** Module boundaries hold as `CLAUDE.md` and `docs/architecture.md` declare them: modules reach each other only through their public entry, data is reached only through the declared data layer, and business code imports no infrastructure SDK, ORM or transport client outside the layers allowed to hold it. No new dependency without a justification in the plan. — seed
- **PG-A03** Responsibilities are named: each use case has its controller, and each derived value or operation its owner (the module holding the data it needs); a rule the project assigns to a layer (for example "in the database, in one transaction") lives there. Presentation code that orchestrates a use case or calls the data layer against the declared layer directions is Critical. — seed
- **PG-A04** Signatures, payloads and error codes in `contracts.md` match the spec's ACs and `data-model.md`, and the data-model constraints express the spec's rules. Every error the user sees has a code and a message, and every fallible call has both its success and its failure path designed, normalized at one boundary per the project's error convention. — seed
- **PG-A05** Every claim about a library's or platform's behaviour that the design relies on is verified on each branch the design depends on (success, error, early return, offline), with the source or a probe cited. — field
- **PG-A06** Each contract property (signature, security mode, side effects, volatility) is stated once or kept identical wherever it is repeated, and matches the source it describes. — field
- **PG-A07** A change to a shared module or component is checked against every consumer and every AC that drives its states (disabled, hint, read-only, placeholder); the plan names one input per state or records the fallback. — field
- **PG-A08** Every new operation, helper, derived value and closed-set member has a search for an existing equivalent (by name, signature and meaning; scope; hits as file:line) and a decision: reuse, extend or new, with the reason. The reviewer repeats one search per `new` decision. A hit the plan missed is Critical when it changes behaviour (the new code would behave differently from the existing equivalent) or when `.claude/quality-profile.json` sets `canonicalSources` and the new definition duplicates a concept listed there; otherwise it is a Warning. A claim without search evidence is a Warning. — seed
- **PG-A09** Every variation point the spec consumes (variants by kind or status, a second implementation, a growing branch) goes through one seam with a written contract (preconditions, postconditions, invariants) and one shared contract suite in the planned tests. A closed set used by two or more modules has one typed registry with an exhaustiveness check; a branch on its members outside it is a Warning, Critical when the spec adds a member. — seed
- **PG-A10** No speculative abstraction: configuration for constants, a plugin point, a strategy hierarchy for a fixed rule, or an interface with one implementation inside a stable flow needs a confirmed axis of change or a justified decision, otherwise it is a Warning. Interfaces at system boundaries (storage, external services, files, mail) are exempt. — seed
- **PG-A11** A plan that adds a module, screen or kind lists every shared registration point it must append to (route lists, navigation, composition roots, message catalogs, fixture registries, per-kind maps) and names, for each, the check that fails when the entry is missing; an entry that fails silently when forgotten is a Warning. When `.claude/quality-profile.json` sets `hubFiles`, a plan that registers its feature by editing a listed hub file without a registration seam or a recorded reason is a Warning. — seed
- **PG-A12** When `.claude/quality-profile.json` sets `ratchets`, the lens runs the clone ratchet's copies command over every file the plan and its tasks will edit (tests and fixtures included). A plan that extends or copies logic that already has two or more copies without a seam task ordered first is Critical; a "not a copy" or "differs per case" reason is checked by diffing the copies, and a removal that would join two stretches of an existing clone names the extraction. — seed
- **PG-A13** A plan that adds a shared helper, config block or dependency lists every existing file that must change with it, found by reading the guards, lint rules and manifests that cover the new file's location: the allow or option lists the new file would trip, the manifest that holds its sibling dependencies, and config constraints that an intermediate state breaks (an empty file list, for example). A helper that the callers moved onto the shared module will need and that it does not offer yet is planned in the same change (reuse decided per PG-A08). A missing entry is a Warning. — field

## Security lens

- **PG-S01** Every new resource (table, endpoint, function, job) enforces access control on the server for both reads and writes, for every caller role. A new action reachable by a client or role the spec does not grant it is Critical, and so is an operation family with mixed security modes or permissions. — seed
- **PG-S02** Code that runs with elevated privileges pins its resolution context (search path, module resolution, working directory), uses fully qualified names, and is callable only by roles granted it explicitly. — seed
- **PG-S03** Permissions are minimal per role, field-level where a client may set only some fields, and cover objects created by every role (including defaults the platform applies); a privilege the row- or record-level checks do not filter is denied to client roles. — seed
- **PG-S04** No secret reaches a client bundle, a log or the repository. A value that must never ship to a client is rejected at build time, not only by a runtime check, and a constraint stated as "local only" or "dev only" (hosts, keys, credentials) is enforced by code that fails closed, with its unit test named. — seed
- **PG-S05** The design states its behaviour on session expiry, refresh failure, sign-out under network failure, and multi-device or multi-tab use. A long-lived credential stored on the client is paired with the matching script-injection and framing controls, or the accepted risk is recorded. — seed
- **PG-S06** Third-party code that runs in a job or process holding a secret is pinned immutably (commit SHA or exact version), and the secret is scoped to the steps that need it. — field
- **PG-S07** Code that takes a client-supplied id confirms the caller's ownership or scope before it reads, locks or reveals the record, including helpers whose execution is restricted and code that runs before the main access check; the contract states the rule so later privileged code cannot reuse the helper to leak. — field
- **PG-S08** Every rule the plan places in one write path (an operation, a trigger, an append-only journal) is enforced on every write path the roles' permissions leave open (direct writes, other operations, operator and service roles), or the plan closes that path; the plan lists the write paths per role for each store it touches, and any exception is recorded. — field
- **PG-S09** The contract bounds the magnitude of every numeric input and rejects non-finite values at validation with a named error, so an oversize value cannot surface as a raw overflow at write time. — field
- **PG-S10** A command that writes or deletes in place states its write boundary in the contract (allowed root, protected paths, root-argument and path-case behaviour, dry-run default), and the contract wording agrees with that boundary. — field
- **PG-S11** A committed artifact derived from sensitive input (hash list, mask, digest) is assessed for reversibility (salt scope, input space, length); when it is reversible, the plan treats it as clear text. — field
- **PG-S12** A per-request cap on a shared resource (locks, connections, memory) is checked against the system-wide limit (pool size times cap across all callers), and the deployment setting is recorded. — field

## QA lens

- **PG-Q01** Every AC has a planned verification level (unit, integration, end-to-end, command or manual) that can observe it: a simulated DOM cannot see CSS or layout, and a database test cannot see the UI. — seed
- **PG-Q02** Every UI AC has planned end-to-end coverage with the AC id in the test title, bound only through the anchors the spec names. — seed
- **PG-Q03** Concurrency, race and multi-instance ACs have a deterministic test strategy (barriers, locks, controlled ordering), not timing luck. — seed
- **PG-Q04** Test data comes from the project's seed data or fixtures derived from the spec. Tests that share accounts or state isolate them, and a design that persists data from tests or tools lists every existing test that asserts a closed set over the same stores and states how each stays order-independent. — seed
- **PG-Q05** Every visual metric the spec fixes (sizes, paddings, weights, colour tokens) has a planned runtime check in a real browser. A visual-baseline tolerance is justified by the measured noise of the host and is smaller than the smallest style change the spec fixes, converted to pixels when it is a ratio. — seed
- **PG-Q06** The plan's AC traceability lists every lettered sub-item of each AC, and the planned order creates each object before any test or task that calls it. — field
- **PG-Q07** An AC verified by a one-off command (a search, a diff, a manual count) that a later edit can regress has a permanent automated guard (lint rule or test), or a recorded exception that every later change touching the area re-runs. — field
- **PG-Q08** Every count or search command the plan quotes, and every count it states about existing code (branches, call sites, files), is re-run by the lens at the base: its output matches the figure the plan and the spec state, and scratch or fixture files are outside its scope. A differing count is a Warning, because task text and tests copy it. — field
- **PG-Q09** A plan that changes a behaviour, a shared module's contract or a message catalog lists, in its test impact, every existing test file and case that must change, found by searching the changed symbol, key or text across the tests, not only the files in File Impact. — field
- **PG-Q10** A plan whose AC proves two states equivalent (a baseline against a migrated schema, a copy against its source) names the attributes the proving check can observe and those it cannot, and adds a check or a normalizing step for each blind attribute or records it as an accepted blind spot. — field
- **PG-Q11** A plan that adds a generator whose output is committed names how the committed file is re-checked after later changes to its inputs land; a check that fails on the committed result is a Warning. — field
- **PG-Q12** A plan that places the probe or self-check of an AC in a test suite names the command or script that runs that suite and confirms that the command the AC names executes it; a probe in a suite that command never collects is a Warning. — field
