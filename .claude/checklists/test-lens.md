# Checklist: test-lens

**Gate**: on — set to `off` to skip this gate (the file is project-owned; deleting it does not work, `update.sh` restores missing checklists).
**Runs**: on every new or changed test, in `/execute-task`'s per-task code review (with `task-review.md`) and in `/review`'s qa assessment · **Reviewer**: `code-reviewer` in `/execute-task`, `qa-engineer` in `/review`; a fresh context; a different model from the author where possible.
**Inputs**: the new and changed tests and the code they cover; the task file or the feature's `specs/NNN-*/spec.md` ACs they claim; `contracts.md` if present; `CLAUDE.md`; `constitution.md` if present.

**The question for every test**: *would this test fail if the feature were broken?* Then check assertion specificity: scoped to the element or row, not page-wide; exact values, not mere presence.

**How to use**:
- Check every item that applies to the new or changed tests against the artifact and its sources; report each failed item by id with evidence quoted from both sides.
- Severity follows the review scale (Critical / Warning / Suggestion / Info). A test that cannot fail for a plausible break is a Warning; it is Critical when it is the only coverage of an AC.
- Defects outside the list are reported too, as `new`.

**Origin**: `seed` = shipped with Forge; `field` = generalized from defects that escaped earlier gates in field use; `escape NNN/E<n>` = added by this project's /finalize learning step; `audit <date>/<theme>` = added by /audit. New items take the next free id; ids are never reused. An escape that an existing item already covers adds its origin to that item instead of a new item.

## Items

- **TL-01** The test fails if the feature is broken: name the mutation it kills (a removed check, a wrong value, a swapped branch, a dropped sort). For a unit that is an AC's only proof, the reviewer names one mutant and checks, by reading or by one run against the mutated line, that a test kills it; a fix for a race or ordering defect has a test that fails when the fix is removed. — seed
- **TL-02** A guard or check meant to fail on a regression is shown to fire (the targeted fault injected, the failing run recorded), and its trigger does not depend on state left by earlier tests. No assertion sits on an unmounted wrapper, a mock replaced after the flow started, a value the setup already makes empty, or after a rollback; a structural test of a workflow asserts the order and presence of each security-relevant step and a reorder is shown to fail it. — field
- **TL-03** Assertions are scoped to the element, row or region the AC talks about, never page-wide, and a test locator is at least as strict as the anchor the spec names. — seed
- **TL-04** Assertions check exact values (text, count, number, state, every field of a returned record), not mere presence or visibility: the rendered text the user sees rather than a bound model value, the full error or object with strict equality on the AC's own input, a formatted string with its exact space characters, and the persisted effect re-read after a write or a rejected write. — seed
- **TL-05** Every test that covers an AC has the AC id in its title. — seed
- **TL-06** Every error, exit and failure path of the changed code has a test that asserts its code or message, not only the happy path; a top-level failure handler is tested with a synchronous throw. A fail-closed branch is never untested by default; an unreachable one is recorded with the reason. — field
- **TL-07** Every boundary and edge input has a test row: case, whitespace, sign, zero, scale or length limits, empty, non-ASCII letters and their case forms, multi-part entries, sibling paths sharing a name prefix, and time-zone or calendar edges the AC names. A sanitizer or text guard is exercised with each variant (leading whitespace, tab, line feed, carriage return, a lookalike prefix), and every input a contract names as accepted or rejected is pinned. — field
- **TL-08** Component tests assert after re-renders settle, and cover the composed component with its optional inputs, not only each part right after mount. — field
- **TL-09** A check that depends on the environment (screen size, timing, locale, clock) reads it at assertion time instead of assuming a constant; a time assertion does not compare with a clock value that is frozen in its scope (for example a transaction timestamp). A pin or snapshot of rendered output passes on a later day and in another locale and time zone, or its test fixes the clock; a default derived from the current date, time or a random value that reaches the pinned output is fixed in the test itself. — field
- **TL-10** A guard with several alternative failure conditions is exercised once per condition in isolation; when the spec defines a precedence among failures, tests combine two or more failing conditions, and a guard that counts or blocks dependents has a row for each kind it must count and each it must not. — field
- **TL-11** Observers, listeners and request stubs are installed before the action they observe (before the first load for startup checks), and a test that stubs, routes or aborts a request asserts that the stub was hit. — field
- **TL-12** Test timeouts exceed the longest wait inside the test plus the retry horizon of the dependencies it exercises, measured under parallel load; locks, leases and stale thresholds in fixtures exceed the longest test timeout or are refreshed while held. — field
- **TL-13** Async state, geometry and layout reads are polled or awaited, never a fixed sleep or a single read; an absence assertion (no message, no request) observes a settle window or a listener, not one instant, and a fixture lookup throws on a missing row instead of defaulting. A derived value (a total, a count, a status text) read right after an action waits for its settled value, and a case seen failing once for this reason is fixed in the test, never rerun until it passes. — seed
- **TL-14** An ordering assertion uses input that is not already in the expected order, so removing the sort changes the result; when ordering uses a composite key, a test uses rows equal on every leading key, so dropping any key fails a test. — field
- **TL-15** A value, label or enabled state derived from several inputs has a case for each combination the UI can show, a region whose parts follow different state rules has a test per part in each state, and a directional output (sign, side, slot) is exercised through a successful operation in each direction with the exact stored value. — field
- **TL-16** Every way the spec offers to reach a state (typed, picked, pasted, a link and a direct address, each keyboard command) is tested to the same result; a keyboard command is tested with focus on each kind of child; an input that reformats while typing is tested key by key, including clearing and retyping after a refusal. — field
- **TL-17** A workaround that bypasses the user path under test (fixed clock, seeded value, direct model write, forced click) is filed as a bug when it is adopted, and the AC it weakens is listed as not covered until the real path is tested. — field
- **TL-18** A visual baseline is not recorded over a deviation the author has already seen (truncated text, an empty control); every style the spec states explicitly has a computed-style assertion, and value-bearing controls assert that their text is not clipped. — field
- **TL-19** Each default value, message text, focus destination and "nothing happens" rule the spec states is pinned by a unit test in the task that implements it, not only in a later end-to-end test. — field
- **TL-20** When an AC enumerates cases, sites or steps, each one maps to its own committed test with the full expected result; a neighbouring weaker test or an uncommitted probe run does not cover a listed case, and an AC with per-step effects asserts each step in turn. — field
- **TL-21** A test of a client for an external API asserts the request against the API's documented limits and required headers, and its stub responses have the real endpoint's shape (fields the endpoint omits or leaves null are absent or null); a mock that accepts any value is not evidence. — field
- **TL-22** An expected value comes from the spec sentence or the design, cited in the test, never from running the code; a test written after the code that only repeats what the code produces is a Warning. — field
- **TL-23** A seam has one shared contract suite that every implementation runs unchanged, proven to fail on a mutant implementation before it is relied on; when one shared core replaces several per-feature copies, each binding has a test pinning the output only that binding produces. — seed
- **TL-24** A test is not a change detector (a literal copy of a module, catalog or table), does not test the framework or a library instead of the unit, and does not make the mock's received arguments, as set up by the test itself, its only assertion; a registry completeness test compares with the independent source of truth, not with its own list. When `.claude/quality-profile.json` sets `ratchets`, a test setup, fake or fixture copied from another feature's tests is a Warning, Critical at the third copy. — seed
- **TL-25** A new test is shown to be collected: the suite's reported test count rises by the number added; a test placed where the runner does not collect it is a Warning. — field
