## Why this plan exists

Plan 40 made visual drift from a `design/reference.html` gate-blocking through a three-part apparatus: the disposition manifest (`specs/[feature]/design-manifest.json`, produced at `/breakdown` PHASE 2.5), the static provenance gate (`verify-design-tokens` at `/implement`'s forcing-functions gate), and the runtime conformance gate (`design-auditor` at `/review` PHASE 2.5). The contract is persisted as constitution §3.8.

The apparatus has a **single load-bearing trigger** — the manifest must EXIST for two of the three gates to do their job — and that trigger is currently **skippable prose** with a **silent-failure cascade** when it is skipped. Both halves verified in code:

- **Trigger is prose, not mechanical.** `/breakdown` PHASE 2.5's detect step (`src/commands/breakdown/main.md:272`) is an LLM instruction — *"Check whether `design/reference.html` exists at the workspace root … If it exists, continue."* Nothing downstream of PHASE 2.5 asserts that, given a `reference.html`, the manifest was actually produced. The PHASE 3.5 integrity gates (`main.md:395-430`) run `verify-contract-chain`, `verify-ac-coverage`, and `verify-agent-roster` — **none checks the manifest exists.** A skipped or mis-skipped PHASE 2.5 (the LLM mis-judged the reference absent, or short-circuited the phase) writes task files and a `breakdown-handoff.json` with no manifest, and the breakdown completes green. This is the exact failure mode plan 38 closed for the agent roster (`feedback_helper_owns_contract_filesystem_forcing`: *spec prose can't enforce a check; only a mandatory gate that walks the filesystem is a reliable forcing function*) — the manifest trigger is the same shape of prose-only obligation, unguarded.

- **Missing-manifest cascade is silent — and for the static gate, worse than a no-op.** When the CURRENT feature's manifest is absent but a `reference.html` is present, BOTH downstream fidelity gates fail the current feature silently, in two different ways:
  - `verify-design-tokens` Check 5 (MATCH-element token binding) is **project-globbed, not feature-scoped** — verified at `src/devforge/lib/_constitute/_forcing_functions/_design_tokens/_cmd.py:66,107,110-136`: the constant `_MANIFEST_GLOB = "specs/*/design-manifest.json"` (line 66) is globbed across the WHOLE project (`_glob_manifests`, line 107) and `_collect_match_refs` (lines 110-136) UNIONS the MATCH data-refs across every manifest found. So the harm depends on project state: with ZERO manifests on disk Check 5 gets an empty MATCH set and is a true no-op (Checks 1–4 are manifest-independent and still run; the gate exits 0); but with ANOTHER feature's manifest present, Check 5 RUNS — against THAT feature's MATCH refs, not the current feature's — i.e. cross-feature contamination, silently producing wrong/irrelevant per-element binding results for the feature being implemented. Either way the current feature's MATCH elements are not the ones checked.
  - `/review` PHASE 2.5 dispatches `design-auditor` ONLY when BOTH `reference.html` AND `design-manifest.json` exist (`src/commands/review/main.md:183,185`) — *"When either is absent, this feature is not UI-against-a-reference work — SKIP this entire sub-step."* A missing manifest reads as "not a design feature," so the runtime conformance gate never dispatches.

  Net: a feature that HAS a `reference.html` but (through a skipped intake) NO manifest sails through `/implement` and `/review` with the design-fidelity guarantee silently void — Check 5 either no-ops (no manifests anywhere) or checks the wrong feature's elements (another feature's manifest present), and the runtime gate never dispatches — and no operator-visible signal distinguishes it from a genuine non-UI feature. This is why WI-2's tripwire trigger is "`reference.html` present + THIS feature's manifest absent": the right trigger, but the harm it heads off is "Check 5 silently no-ops OR runs against the wrong feature's refs," not a pure no-op.

## Framing: preventive, not reactive

This is hardening of a latent structural weakness, **NOT** a fix for an observed production skip. The consumer install that surfaced the manifest-absence was an **ordering / stale-install problem** (the design apparatus post-dated that install's `/breakdown`, so PHASE 2.5 did not exist when the feature was decomposed) — that is out of scope here and is resolved by reinstalling, not by a forge code change. This plan asks a narrower question: *given a current install where PHASE 2.5 exists, what mechanically guarantees the manifest the two downstream gates depend on was actually produced?* Today: nothing. This plan supplies that guarantee. The motivation is the structural gap, validated by reading the apparatus — no claim of a reproduced runtime skip on a current install is made.

## What the fix is NOT

- NOT a change to plan 40's apparatus mechanics — `design_helper`'s four verbs, the manifest schema, the four-way taxonomy, `verify-design-tokens`'s five checks, and `design-auditor`'s hybrid mechanism are all UNCHANGED. This plan adds a TRIGGER guarantee around the existing apparatus, not new fidelity logic.
- NOT a relaxation of the PHASE 2.5 happy path — the gate still SKIPS cleanly for genuine non-UI features (no `reference.html`). The new assertion only fires for the `reference.html`-present case.
- NOT consumer-side remediation. A consumer whose features were decomposed before PHASE 2.5 existed (no manifest for an old UI feature) is a stale-install case; backfilling manifests for already-decomposed features is a NON-GOAL (see below).
- NOT an AskUserQuestion / human-judgment gate. The trigger is a binary filesystem assertion (`reference.html` present ⇒ manifest present-and-valid), HARD-halt no-bypass — the same severity class as plan 38's `verify-agent-roster`.

## Decisions

- **D1 — Mechanical PHASE 3.5 integrity gate, mirroring plan 38.** The fix is a forcing function that walks the filesystem and asserts `reference.html` present ⇒ `design-manifest.json` present-and-valid, sited as a fourth PHASE 3.5 integrity gate alongside `verify-contract-chain` / `verify-ac-coverage` / `verify-agent-roster`. HARD-halt, no Risk-Assessment bypass (the roster gate's precedent — a structurally-required artifact cannot be "deferred"). The prose detect at PHASE 2.5 stays as the PRODUCER step; this gate is the mechanical BACKSTOP that the producer ran.
- **D2 — Reuse `validate-manifest`, do not re-implement validation.** The gate's "present-and-valid" assertion is: (1) if `reference.html` is absent → pass (non-UI feature, nothing to assert); (2) if `reference.html` is present and `design-manifest.json` is absent → HARD fail (the trigger was skipped); (3) if both are present → run the existing `validate-manifest` logic (every element classified, empty gap-list) and fail on any error. Step 3 is exactly `design_helper validate-manifest`'s contract — the new verb COMPOSES it, never forks it. A present-but-half-classified manifest (a partial PHASE 2.5) must also fail, which step 3 already covers.
- **D3 — A new thin verb, plus a finalize-handoff chokepoint.** Mirror plan 38's two-call-site shape: a standalone verb runnable as the explicit PHASE 3.5 gate AND the same assertion folded into `breakdown_helper finalize-handoff` so a `breakdown-handoff.json` physically cannot be written for a `reference.html`-present feature with a missing/invalid manifest. Single shared validation function, two call sites. With the verb homed in `breakdown_helper.py` (D6), `finalize-handoff`'s fold is an INTRA-FILE call — a true plan-38 mirror (plan 38's `_validate_agent_roster` is likewise intra-file). The only `_design` coupling is one deliberate `import validate_manifest` for the clean-check (D6), not a chokepoint dependency.
- **D4 — Tighten PHASE 2.5's detect step to a mechanical existence test. RESOLVED to Option B (maintainer-ratified 2026-06-25): a bash `test -f design/reference.html`, NOT a shared helper call.** The original draft proposed routing PHASE 2.5's detect through the same helper function the PHASE 3.5 gate calls. That is not cleanly implementable: the `--scope-only` mode of `verify-manifest-present` takes `<tasks-dir>` and the tasks dir does not exist yet at PHASE 2.5 (intake runs BEFORE Phase 3 writes task files), so the verb cannot run there as-built. Three options were weighed — (A) reopen Phase 1 to make `--scope-only` ignore the tasks-dir; (B) a mechanical bash `test -f` in PHASE 2.5 with the PHASE 3.5 gate as the authority; (C) drop the D4 re-point. **Option B chosen** because: the load-bearing guarantee is the PHASE 3.5 backstop + the finalize chokepoint (both unaffected by this choice); the only harmful drift direction — PHASE 2.5 wrongly skipping a real reference — is already caught by PHASE 3.5 (reference present + manifest absent → HARD halt); the other direction (wrongly running with no reference) self-corrects (`resolve-reference` exits 2). PHASE 2.5 and PHASE 3.5 now use the SAME mechanical file-existence predicate (`test -f design/reference.html` vs `_reference_present`), and the reference-path literal `design/reference.html` is unavoidably already in PHASE 2.5 (the `resolve-reference --html-path design/reference.html` call), so Option A's "helper owns the existence literal" benefit was cosmetic. Net: the real risk D4 targets — the LLM *eyeballing* the filesystem — is eliminated by making the detect mechanical, at zero cost to the green Phase-1 code.
- **D5 — Defense-in-depth loud-WARN tripwires at the two consumer sites (WI-2).** Independent of the PHASE 3.5 gate, add a loud WARN at `/implement`'s forcing-functions gate site and `/review` PHASE 2.5 for the **legacy/tampered** case — a feature where `reference.html` is present but `design-manifest.json` is absent at CONSUMPTION time (the gate was added after the feature was decomposed, or the manifest was deleted). The PHASE 3.5 gate guards NEW decompositions; the tripwires catch already-decomposed features whose manifest never existed or vanished. WARN (loud, operator-visible, non-blocking) not HALT, because these are CONSUMER commands operating on a feature whose intake already happened — they cannot re-run intake, only surface the void guarantee (severity settled in D7).

- **D6 — Verb home: `breakdown_helper.py` (RESOLVED at Phase 0, was OQ-1).** The new `verify-manifest-present` verb lives in `breakdown_helper.py`, the home of the other three PHASE 3.5 integrity gates. **Rationale — gate-family cohesion:** the verb IS a PHASE 3.5 integrity gate (a breakdown intake-policy concern), sibling to `verify-contract-chain` / `verify-ac-coverage` / `verify-agent-roster`, which all live in `breakdown_helper.py` (`:1411`/`:1480` for the roster verb + function, alongside the others) and share ONE contract — exit 2 + a stdout findings-block + no Risk-Assessment bypass. The new verb adopts that same contract; co-locating it keeps the four gates a single readable family. **Design SEMANTICS stay in `_design`:** the gate DELEGATES the manifest-validity check to `_design`'s `validate_manifest` (a thin, documented import of the validator ONLY — the design-fidelity rules stay single-homed in `_design/_schema.py`); the gate SHIM itself (reference-present test → manifest-absent fail → delegate-validity) is breakdown policy, authored in `breakdown_helper.py`. **F2 cross-package concern, now reduced:** the only `_design` dependency `breakdown_helper.py` gains is that single deliberate `from _design… import validate_manifest` for the clean-check — NOT a chokepoint coupling. Because the verb is intra-file, `finalize-handoff`'s fold (D3) is an intra-file call, a true plan-38 mirror.

- **D7 — WI-2 tripwire severity: loud WARN, non-blocking (RESOLVED at Phase 0, was OQ-2).** The `/implement` + `/review` tripwires WARN (loud, surfaced in the command's user-facing output / report), they do NOT halt. **Rationale:** WI-1's PHASE 3.5 gate already HARD-halts at breakdown for any NEW decomposition, so the WI-2 tripwire only ever fires for a LEGACY feature (decomposed before this fix existed) or a hand-tampered manifest. Hard-blocking mid-`/implement` would stall legacy work the operator cannot fix in place (intake is past — they'd have to abandon and re-`/breakdown`). A loud WARN naming the void guarantee + the remedy is the proportionate signal. (If future evidence shows operators ignore the WARN, escalate then — YAGNI now.)

## Non-goals

- **Consumer remediation / manifest backfill.** Producing manifests for features decomposed before PHASE 2.5 existed is out of scope. The WI-2 tripwires SURFACE the gap; closing it for an old feature is the operator re-running `/breakdown` PHASE 2.5, not a forge migration. No backfill verb, no auto-generation of manifests for historical features.
- **Non-FILE design sources (the design-source-type boundary).** WI-1's trigger keys on the existence of `design/reference.html` — the local HTML+CSS+tokens artifact plan 40's whole apparatus is built around. Non-file design sources — a Figma selection, a hosted design URL, a screenshot — are NOT detected and get NO design-fidelity enforcement. That is NOT a plan-42 trigger bug: both gates correctly SKIP with no false halt/warn when the file is absent (a Figma-only feature looks identical to a non-UI feature to this trigger, by design). It is a plan-40-APPARATUS coverage boundary — enforcing fidelity without a local HTML+CSS artifact needs a whole new backend (Figma-API diff / screenshot diff), out of scope here. Any future generalization MUST key on a structured `design_source` declaration (a spec/config field, e.g. `html:<path> | figma:<url> | screenshot:<path> | none`), NOT prose-scraping the spec/discover text (fuzzy, fragile, and the exact prose-trigger failure mode this plan exists to eliminate). Tracked separately in **plan 43 (NOT STARTED)**.
- **Any change to plan 40's apparatus.** The four `design_helper` verbs, the manifest schema, `verify-design-tokens`'s five checks, `design-auditor`'s mechanism, and constitution §3.8 are untouched. This plan adds a trigger guarantee, not fidelity logic.
- **Relaxing the genuine-skip path.** A feature with no `reference.html` still skips PHASE 2.5 and passes the new gate trivially — that is correct and unchanged.
- **A standalone "design-fidelity status" command.** The assertion lives inside `/breakdown` (gate) and the two consumers (tripwires); no new command surface.
